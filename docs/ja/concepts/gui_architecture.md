# ダッシュボードアーキテクチャ

ARI のダッシュボードは、`ari/viz/` の Python HTTP サーバーが配信する
React/TypeScript のシングルページアプリです。このページは*概念*ビューです:
ダッシュボードが今の形になっている理由を説明する、ごく少数の構造的決定 —
2 世代の画面を 1 つのシェルが載せること、ルートを 1 つのレジストリが所有すること、
サーバー状態を 1 つのキャッシュが所有すること、HTTP とファイルシステムの間に
1 つのシームがあること。

エンドポイント一覧でもクリック手順ツアーでもないのは意図的です:

- [ダッシュボードガイド](../guides/dashboard.md) — 運用者向けツアー: サーバーの
  起動、各ワークスペースが答えること、ディープリンク。
- [ARI アーキテクチャ](architecture.md) — ダッシュボードが観測する研究システム
  （パイプライン、BFTS、チェックポイント）。
- [研究状態とガバナンス状態](research_and_governance_state.md) — ダッシュボードが
  分離しておく必要のある状態語彙。
- [REST API リファレンス](../reference/rest_api.md) — エンドポイント表。

## 全体像

```text
     #/tree2?run=R1&node=N7       ← the URL is navigation truth
               │
               ▼
  ┌──────────────────────────── browser ─────────────────────────────┐
  │  route registry (app/routeRegistry.ts)                           │
  │    · path + legacy aliases  · nav slot  · guiV2 gate             │
  │               │                                                  │
  │               ├──▶ legacy screen  (#/tree, #/results, …)         │
  │               └──▶ v2 workspace   (#/tree2, #/results2, …)       │
  │                     │   both inside the SAME shell/Layout        │
  │                     ▼                                            │
  │  server-state cache (react-query)                                │
  │  key = ['v1', <runId | projectId>, <resource>]                   │
  └────────────┬─────────────────────────────────┬───────────────────┘
    HTTP GET   │                                 │  SSE = invalidations
               ▼                                 ▼
  ┌────────────────── transport: ari/viz/routes.py ──────────────────┐
  │  same-origin CORS · CSP / nosniff / Referrer-Policy ·            │
  │  bearer auth on non-loopback binds · challenges · logs           │
  └────────────┬─────────────────────────────────┬───────────────────┘
               ▼                                 ▼
     v1/router.py (ROUTES table)             v1/events.py (bus)
               │
               ▼
     pure read modules: queries.py · results.py · rqgm.py · logs.py
     (no viz.state writes · no os.environ writes · no ari.rqgm)
               │
               ▼
     {checkpoint}/  tree.json · review_report.json ·
                    rqgm_transitions.jsonl · ear/     ← the truth
```

以下のすべては 1 つの規則の帰結です: **ディスク上のコミット済み成果物だけが
真実であり、その上のどの層も捨てて再計算できる射影にすぎない。**

## 1. ストラングラー構造: 1 つのシェル、2 世代の画面

ダッシュボードはその場で作り直されたわけではありません。レガシー画面と新しい
v2 ワークスペースは同じルーターに並んで登録され、同じ `Layout`（サイドバー、
チェックポイントピッカー）の中で描画されます。新しい画面のために
何かが削除されたことはありません。

| 世代 | ハッシュルート |
|---|---|
| レガシー画面 | `#/home`、`#/experiments`、`#/monitor`、`#/tree`、`#/results`、`#/wizard`（`#/new`）、`#/idea`、`#/workflow`、`#/settings`、`#/paperbench*` |
| v2 ワークスペース | `#/projects`、`#/overview?run=`、`#/tree2?run=&node=`、`#/ideas2?run=`、`#/results2?run=`、`#/governance?run=`、`#/config?run=`、`#/studio` |

2 世代の共存を可能にしている仕組みは 3 つです:

- **並走。** v2 ワークスペースが対応するレガシー画面を編集することはありません。
  `#/tree` と `#/tree2` は同じ成果物に対する別コンポーネントであり、どちらも
  到達可能なままです。
- **ナビの引き継ぎ（`navReplaces`）。** v2 シェルが有効な間、v2 ルートは対応する
  レガシールートの*サイドバースロット*を占有できます — そのスロットのラベル、
  順序、アイコンを継承するので、サイドバーの見た目は同一で、クリックが書き込む
  ハッシュだけが変わります。レガシールートは登録されたままなので URL は動作し
  続け、ブックマークが壊れることはありません。
- **単一のキルスイッチ。** v2 シェルをオフにすると、v2 専用ルートは未知のハッシュ
  とまったく同じように Home へ解決され、サイドバーはそのエントリを隠します。
  再ビルドも再デプロイも不要です — §9 を参照。

したがってこの移行には、スケジュールすべきカットオーバーの瞬間がありません。
ワークスペースはナビスロットを与えることで昇格し、スロットを取り上げることで
ロールバックされます。

この構造が**そうではない**もの — そして最も誤読されやすい点 — は、共有された
アプリケーションサービスの上に薄いレガシー facade が乗っている、という姿です。
`ari/viz/services/` にあるモジュールは 3 つ（`state_service`、`file_service`、
`launch_service`）で、`/api/v1` がそこから呼ぶのは
`launch_service.load_dotenv_files` だけです。共有ヘルパー — チェックポイント
ディレクトリの解決、チェックポイント探索ベース、pid プローブ、バイト保存のツリー
アダプタ、`.env` チェーンの読み取り、アクセスログの書き込み — を除けば、レガシー
ハンドラと v1 read モジュールは、同じ成果物に対するおおむね 2 つの独立した実装
です。ただしレガシー側の関数がすでに単一の真実源である箇所では、v1 モジュールは
それを fork せず意図的に再利用します: `catalogs.py` はレガシーの `/api/models`
ペイロード（`checkpoint_api._api_models`）をそのまま出し、プロバイダの API キー
env 名を 1 フィールドだけ足します。`results.py` は ORS の verdict・スコア・リーフ
数を埋めるために `ear._synth_repro_report_from_ors` を read-only で呼ぶので、
2 つの Results 画面が別々の verdict を出すことはありません。`secrets.py` の書き
込みは `api_settings._upsert_env_key` を通ります。これらの再利用点こそが両者の
歩調を保っているものであり、同時にレガシー削除がほどかなければならないもの
でもあります: レガシーの `/api/models` ハンドラや `ear.py` を消すと `/api/v1` の
read モデルが壊れます（§7）。

設定が run に届く経路も 2 本あります: レガシーの Settings 保存＋起動チェーンは
選ばれたキーを起動する CLI 向けの環境変数へ写し、`/api/v1` の設定エンドポイントは正準リゾルバ
を通ります。両者はすべてで一致するわけではなく、その差分は
[設定](../reference/configuration.md) の dead / env-only な Settings キーとして
列挙されています。

つまり両者の一致は、構造ではなくテストによって保たれています。
`ari-core/tests/test_gui_config_shadow_legacy.py` はレガシー起動の実効設定と正準
リゾルバの結果をリーフ単位で差分し、明示的な allowlist に載っている行だけ乖離を
許します — 載っている行が黙って乖離しなくなった場合も同様に失敗します。
`ari-core/tests/test_gui_state_facade_freeze.py` は凍結された `/state` ペイロード
のトップレベルキー集合を厳密に固定し、追加も削除も拒否します。挙動を変える人に
とっての実務的な帰結は: 変更は 2 回必要だと見込むこと、そして 1 回しか変えなかっ
たことを教えてくれるのがこの 2 つのスイートだ、ということです。

## 2. ルートが存在する場所はルートレジストリだけ

`app/routeRegistry.ts` は 1 つの `ROUTE_REGISTRY` 配列を保持します。各エントリは
ルートの `id`、ハッシュ `path`、遅延 `load` サンク、任意のナビメタデータ
（`navLabelKey`、`navOrder`、`navIcon`、`navPath`）、`legacyAliases`、そして移行
マーカー `guiV2` / `navReplaces` を持ちます。

2 つの消費側はいずれも手で保守されるのではなく*導出*されます:

- `App.tsx` は遅延コンポーネントマップとディスパッチをレジストリから構築します
  （`resolveRoute` は `#/` 接頭辞とクエリ文字列を剥がし、空ハッシュを `home` と
  みなし、`new` → `wizard` のようなレガシーエイリアスを適用します）。
- `Sidebar.tsx` は `navItems()` からナビ表を構築し、`navReplaces` エントリを
  ターゲットのスロットへ実体化して `navOrder` でソートします。サイドバーは
  さらにウィザードのエントリをプライマリアクションとして抜き出し、残りを
  4 つの固定グループ（portfolio / research / quality / system）に並べます。

2 つの凍結リテラルテストが結果をピン留めしているため、ナビには存在するのに
ルーターには存在しない（またはその逆の）ルートへドリフトすることはできません。
ここから落ちてくる実務規則:

- **ハッシュ URL はデプロイ契約です。** ユーザーがブックマークし、ドキュメントが
  引用するものなので、レジストリは歴史的な綴りを整理せず保存します（ウィザードは
  今も `#/new` へ遷移します）。
- **到達可能だが非掲載、を表現できます。** `#/paperbench/import|run|results` は
  ナビエントリを持たないルートとして存在します。前の 2 つは PaperBench レジストリ
  ページのボタンから開かれますが、`#/paperbench/results?job=<job_id>` はアプリ内の
  どこからもリンクされておらず、URL を貼り付けたときにだけ到達します。
- **未知のハッシュはエラーではなく Home へフォールバックします。** この
  フォールバックは、一方では設計上不可欠で、他方では既知の欠陥です。キル
  スイッチにとっては意図的です: v2 シェルをオフにしたとき、v2 専用ルートは
  未知のハッシュとまったく同じように解決されなければ、レガシーの面が欠けて
  しまいます（*capability とキルスイッチ*の節を参照）。一方、単なる打ち間違い
  にとっては欠陥です — 利用者は説明のないまま Home に着き、「このルートは存在
  しません」という明示的な解決画面は今も未着手です（`App.tsx` に `TODO` として
  記されています）。*run が無い*場合のほうは既に意図どおりです: `?run=` 無しで
  開かれた v2 ワークスペースは、グローバルな選択を黙って採用せず、明示的な
  プロンプトを表示します。

**レジストリが持たないもの。** `RouteDefinition` は誰も読まないフィールドを
2 つ宣言しています: `breadcrumbKey` と `requiredContext`。ダッシュボードの
どこにもパンくずコンポーネントは無く、ルートレベルの必須コンテキストガードも
ありません — 代わりに各 v2 ワークスペースが自前の「run が選ばれていません」
プロンプトを出します。GUI 刷新が定めたシェルの面のうち 2 つも同様に未実装
です: コマンドパレットも通知センターも存在しないため、ランやガバナンスの警告は
それを描画するページ上でしか見えません。パレットに定められていた探索範囲は、
消える前に記録しておく価値があります — 1 つの入力欄でルート・ラン・成果物・
アクションを検索し、呼び出し元の権限と capability で絞り込む、というものでした
— なぜならその絞り込みの半分は、そもそもここでは仕様どおりに作れなかったから
です。ルートは権限述語を持たず、サーバーにユーザーモデルが無い限り必要にも
なりません — bearer トークンは全か無かであり、セッションとマルチユーザーは
対象外です。capability によるゲートはマーカー
1 つだけです: レジストリエントリの `guiV2` と、`App.tsx` の `V2_ONLY_ROUTES`
ディスパッチ集合。

**ルートは自分のフラグ名を持ちません。** 刷新がルートレコードに定めた
フィールドは、さらに 2 つが宣言されないままです: `capability` 述語と、名前付きの
`featureFlag`。その両方の代わりを務めるのが真偽値の `guiV2` ですが、これはルート
が選ぶフラグ名ではなく、1 つの環境スイッチ `ARI_GUI_V2`（§9）に対する固定の
マーカーです — したがってルートを個別に切り替えることはできません。スイッチを
オフにすると、マークされた 8 ルートはまとめて Home へ解決され、8 つのナビ
エントリもまとめて消え、レガシースロットを奪っていた 3 つはそれを返します。
それでも段階的展開はスライス単位です:
[GUI カットオーバーランブック](../guides/gui_cutover_runbook.md) は「3. 段階的展開」
の節でワークスペースを 1 つずつ進め、戻す必要が生じたスライスはナビスロットを
取り上げることでロールバックされます（§1）— しかし同ランブックの「1. レバー」の
節にあるフラグのレバーは、v2 の面全体に効くこの 1 つのスイッチです。

`capability` フィールドが無いことは、この 1 つの事実についてレジストリから単一
ソース性も奪っています。v2 ゲートへの所属は 2 か所に書かれます: サイドバーが
フィルタに使うレジストリエントリの `guiV2: true` と、ディスパッチがフォール
バックに使う `App.tsx` の手書き集合 `V2_ONLY_ROUTES` に載ったルートの*パス*です。
凍結リテラルテストはレジストリ側のマーク済み 8 つの id を固定し、App 全体を描画
するスイートは 8 パスのうち 5 つについて Home へのフォールバックを 1 ハッシュ
ずつ確認しますが、2 つのリストを突き合わせるものはありません。9 本目の v2 ルート
を片方のリストにだけ足せば、ナビエントリが消えたまま URL は生き続ける（あるいは
その逆になる）のに、どのテストも落ちません。

**エラーバウンダリはルートに 1 つだけ。** ダッシュボードの React エラー
バウンダリは `main.tsx` の 1 つだけで、ルーターの外、`Layout` の外にあります。
ルート内部の描画失敗は — `App.tsx` の `Suspense` がフォールバックは供給する
もののバウンダリは供給しないため、遅延チャンクのロード失敗も含めて —
サイドバーごとシェル全体を「ARI Dashboard Error」画面に置き換えます。スタックが
出るのは開発者モードのときだけで、復旧手段はページの再読み込みだけです。
リトライアクションを備えたルート単位のバウンダリは仕様にはありましたが未実装
であり、チャンクのロード失敗に対するテストもありません。

## 3. URL がナビゲーションの真実

ダッシュボードはハッシュルーターであり、*選択*はハッシュのクエリ文字列に住みます:
`#/overview?run=<run_id>`、`#/tree2?run=<run_id>&node=<node_id>`。ルートの
ディスパッチはクエリ文字列を無視するので、各 v2 ワークスペースが自分の
パラメータを所有します — マウント時に読み、`hashchange` で読み直し、選択の変更を
ハッシュへ書き戻します。

概念的に重要な理由: ワークスペースの描画内容はその URL だけの関数である、という
ことです。これによりあらゆるビューがリロード可能・ブックマーク可能・共有可能に
なります — 「ラン R1 のノード N7 を見て」はクリック手順ではなくリンクです。

レガシー経路がこの規則の動機となる対比です。レガシー Experiments の行から
レガシー Results ページへ至る経路は今も*暗黙の*受け渡し（`sessionStorage` の
キー + 裸の `#/results` ハッシュ）を通り、レガシーシェルはさらにプロセス全体の
*アクティブチェックポイント*を持ちます。どちらも v2 ワークスペースの妥当な入力
ではありません: v2 ルートは run を明示するからこそ、2 つのタブで 2 つのランを
開いても互いを踏まないのです — v2 の行は代わりに `#/results?run=<run_id>` へ
リンクし、Results ページはそのパラメータを権威として扱い、`sessionStorage` の
キーは古い呼び出し元向けのフォールバックとしてのみ残しています。

このキーには固定しておく価値のある名前があります。ページ内の私的なストレージ
ではなく、ページ間の契約だからです: `ari_selected_checkpoint`。レガシー
Experiments の行は `#/results` へ遷移する前にこれを書き、v2 の Projects の行も
明示的な `#/results?run=<run_id>` リンクと併せて今なおこれを書きます。Results
ページは、ハッシュに `?run=` が無いときに*だけ*これを読み、いずれの場合も
読み終えたら消します。もう 1 つのキー `ari_tree_nodes` は、レガシー
Experiments ページが `#/tree` へ遷移する前に書きますが、どこからも読まれません
— Tree ページはノードを共有のレガシーコンテキストから取るからです。これは死んだ
状態であり、この書き込みの削除は挙動の変更ではなくレガシーページ削除の一部です。

**ハッシュには所有者が 2 つ、パーサーも別々に 2 つあります。** `App.tsx` は
`resolveRoute` で解決し、これは `#/` 接頭辞*と*クエリ文字列を剥がしてレガシー
エイリアスを適用します。`context/AppContext.tsx` は自前の `currentPage` を持ち、
自前の `hashchange` リスナーから、そのどちらもしない裸の接頭辞剥がしで初期化・
更新します。2 つは素朴なレガシーハッシュでは一致し、刷新が導入したまさにその
URL で食い違います: `#/tree2?run=R1&node=N7` では、ルーターが `tree2` を
ディスパッチする一方、コンテキストは文字列まるごと `tree2?run=R1&node=N7` を
保持します。

サイドバーが描画に使うのは後者の値です。`Sidebar.tsx` はナビエントリのハッシュ
キーを `currentPage` と比較して `active` クラスと `aria-current` の両方を決める
ので、クリック直後のハイライトは正しく — クリックは `#/<key>` を書き、
`currentPage` にはその裸のキーが入ります — ワークスペースが自分の選択をハッシュ
へ書き戻した瞬間（`TreeV2Page.tsx`、`ConfigStudioPage.tsx` がそうします）に
失われ、クエリ文字列付きで届いたディープリンクでは最初からありません。つまり
刷新の完了基準 — サーバー / URL / フォーム / 設定 / 刹那的状態がそれぞれ
ちょうど 1 つの所有者を持ち、重複しないこと — は、ナビゲーション状態については
成り立っていません: 1 つの URL に所有者が 2 つあり、2 つ目は §4 が本来リモート
データに限定しているレガシーコンテキストです。

この食い違いを捕まえるものはありません。マウント済みのシェルに対してハッシュを
変更するテストが 1 つも無いからです。`App` 全体をマウントする 2 つのスイート —
`src/__tests__/routeRenderBaseline.test.tsx` と
`src/__tests__/shellA11yBaseline.test.tsx` — は `window.location.hash` を代入して
*から*描画し、しかも常に裸の `#/<route>` なので、初回描画時の解決しか動きません。
ブラウザの戻る／進むを動かすものも無く、`aria-current` を検証するテストもどこにも
ありません。戻る／進むのカバレッジは刷新のテスト一覧にありましたが、既知の
ギャップです。

## 4. サーバー状態はランをキーとするキャッシュに住む

`/api/v1` のすべての読み取りは 1 つの react-query クライアントを通ります。クエリ
キーの形は `['v1', <projectId | runId>, <resource>]` — 識別子はキーの*内側*に
あります。

この 1 つの決定が 3 つの性質を買います:

- **2 つのランが混ざることは決してありません。** ラン単位のエントリは別々の
  キャッシュエントリなので、ランを切り替えても前のランのデータが現在のビューへ
  滲むことはありません。
- **無効化の粒度がちょうど正しくなります。** `['v1', runId]` を落とせば 1 ランの
  サーバー状態だけが落ちます; リソースに属するフィルタ（監査ログのレコード種別、
  エポック）もキーに入るので、それを変えると陳腐化したページ連鎖へ追記するのでは
  なく新しいページ連鎖が始まります。
- **鮮度ポリシーが 1 箇所に集まります。** クライアントの既定は `staleTime`
  5000 ms（従来のポーリング周期に合わせてあるので、その窓の内側での再マウントは
  キャッシュを返します）、リトライ 1 回、ウィンドウフォーカス時の再取得なし —
  ローカルダッシュボードがフォーカスのばたつきをチェックポイントスキャナへの
  リクエスト嵐に変えてはなりません。この 1 つの既定値が*ポリシーのすべて*でも
  あります: これを上書きするクエリは 1 つも無いので、ほぼ静的なスキーマ読み取りも
  生きたツリーとまったく同じに扱われ、鮮度バナーはリソースごとの経過時間では
  なく最後のスナップショット時刻を報告します。エンティティごとの stale time と
  エンティティごとの鮮度ラベルは刷新 GUI の仕様にはありましたが未実装です。

**重複排除の予算が成り立つのは `/api/v1` の面であって、ダッシュボード全体では
ありません。** 刷新はこの設計に 1 つの数値を付けました: 同一クエリキーに対する
in-flight の重複読み取り 0 件。`/api/v1` 上でこの数値は測定されたものではなく
構造によるものです — クエリクライアントは同一キーの同時取得を 1 本にまとめるので、
同じクエリをマウントした 2 つのコンポーネントが出すリクエストは 1 つです — そして
その射程はこの面とちょうど同じ広さで、それ以上ではありません。ツリーの中にこれを
測るものはありません。

レガシー側は昔からこのクライアントの外で自前のトラフィックを出しています。
`context/AppContext.tsx` は `/state` とチェックポイント一覧を 5 秒周期の
`setInterval`（`STATE_POLL_MS = 5000`）で取り直し、`AppProvider` はルーターより
上にいるのでこれはセッションのあいだずっと続きます。`Monitor/MonitorPage.tsx` は
`/api/resource-metrics` に対して 2 本目の独立した 5 秒周期を、その画面がマウント
されているあいだ回します。どちらもクエリクライアントを通らず、互いを見ることも
できず、タブが隠れても止まりません — フロントエンドに `visibilitychange` を
聴くものは 1 つも無いので（§6）、背面に回ったダッシュボードは 2 本の周期を
フルレートで回し続けます。隠れタブのポーリングを止め、それらの読み取りを
ストリーム無効化＋スナップショットクエリへ移すことは刷新の仕様にありましたが
未実装であり、既知のギャップです。予算はこの射程で読んでください: `/api/v1` の
読み取りに対しては構成上成り立ち、それらのポーラーが消えるまでは動いている
ダッシュボード全体を記述しません — `AppContext` のリモート状態と、その背後の
`/state` ファサードは、[GUI カットオーバーランブック](../guides/gui_cutover_runbook.md)
「6. レガシーの撤去」の撤去順序における項目 2 と 3 であり、その撤去順序は
Monitor の周期に名前すら与えていません。

**ランの隔離はシームで証明されており、端から端までではありません。**
`hooks/__tests__/useRunEvents.test.tsx` は、あるランのイベントがそのランのキーと
ラン一覧だけを無効化すること、`tree` イベントがそのランのツリーキーだけに触れる
こと、オフラインのポーリング刻みが購読スコープの内側に留まること、アンマウントで
無効化が止まることを示します。`shared/realtime/__tests__/eventStream.test.ts` は
フィルタ済みのストリーム URL、`Last-Event-ID` カーソル、バックオフの予定表、
接続の状態マシンを固定します。どのテストもしていないのは、2 つのランに対して
2 つのワークスペースをマウントし、両者が混ざらないことを示すことです。
[ダッシュボードガイド](../guides/dashboard.md) は「run を明示する URL と
ディープリンク」の節で、異なる `?run=` を持つ 2 つのタブを開いても安全だと
運用者に告げています。この約束が乗っているのは上のキー構成とサーバー側の
`run_id` フィルタ（§6）であって、2 タブそのもののテストではありません。それは
刷新のテスト一覧にありましたが、既知のギャップです。

クライアント専用の状態（どのタブが開いているか、フィルタ欄のテキスト、サイドバー
幅）はこのキャッシュに*入りません*。分担はこうです: サーバー状態はキャッシュされ
無効化され、ビュー状態はローカルで刹那的、ナビゲーション状態は URL にある（§3）。

**mutation は決して optimistic ではありません。** 予測した結果をキャッシュへ
書き込む画面はありません。書き込みを送り、サーバーの答え — 新しい `revision`
か `409 revision_conflict` — を UI が採用し、該当するクエリキーを無効化するので、
次の描画は再取得したスナップショットから来ます。だからこそ競合した保存は黙って
勝つのではなく明示的な再読み込みの導線を出し、未保存の編集をローカルに保ちます。
そして、サーバーが受理していない状態が画面上に現れることはありません。

**刷新がキーに定めた構成要素のうち、revision だけは着地しませんでした。**
`v1Keys` ファクトリ（`hooks/useV1.ts`）のどのキーもそれを持ちません。キーは
リテラル `'v1'`、1 つの識別子またはグローバルなリソース名、リソース、そして
それを絞り込むフィルタ — `rqgmAudit(runId, recordType, epoch)` や
`rqgmNodeLineage(runId, nodeId)` が最後の形の例です — であり、語彙はそれで
全部です。`gui_store` ドキュメントが持つ整数 `revision` は書き込み側でのみ
使われ、`PATCH` が送り返す `If-Match` の値になります（§7）。書き込みが
キャッシュへ届く経路は、新しいキーを作ることではなく該当キーの無効化です。
したがって revision ごとのキャッシュエントリは存在せず、1 つのリソースの
2 つの revision を並べて保持する方法もなく、保存によるキーの入れ替わりも
ありません: 次の描画は同じキーの再取得から来ます。

**`AppContext` はレガシー専用スコープです。** これはレガシー画面だけの
リモートデータストアであり — 5 秒ごとの `/state` ポーリング、ツリー WebSocket の
ミラー、プロセス全体のアクティブチェックポイント — v2 ワークスペースはこれを
import してはなりません: v2 は `useV1` フック経由で `/api/v1` を読み、run は
`?run=` から取ります。この規則はレビューではなく構造で強制されています —
`src/__tests__/` にあるソーススキャンが v2 コンポーネントディレクトリ配下の
非テストファイルをすべて読み込み、`AppContext` の import 指定子があれば失敗
します。ピン留めされた例外はちょうど 1 つ、IdeasV2 の研究ゴールカードで、
run 同一性チェックの後ろで `/state` からゴールを読みます（ゴールを返す
run スコープの v1 エンドポイントがまだ無いため）。この例外リストを縮めるのは
歓迎ですが、増やすのは退行です。v2 画面が依存している限り `AppContext` は
削除できないからです。

**シェルのレガシー側は domain の成果物をパースします。** 刷新はシェル自身が
それをしないことも求めていましたが、`AppProvider` は `App.tsx` でルーターと
`Layout` より上にマウントされ、`nodesData: TreeNode[]` — そのランのノード一覧 —
を公開します。値は、ツリー WebSocket が何か届けていればそちらから、そうでなければ
`/state` ペイロードの `nodes` から取られます。この優先順位規則はルーターより上に
住む domain ロジックであり、レガシー画面 2 つ（`Tree/TreePage.tsx`、
`Monitor/MonitorPage.tsx`）は自前で取得せずシェルからノードを受け取ります。
`Sidebar.tsx` は同じ結合の小さい版を抱えています: `checkpointLabel()` は
チェックポイント id を `^(\d{8})(\d{6})_(.+)$` に照合してピッカーのラベルを作る
ので、シェルは §5 の run id 規約をハードコードしており、さらにランの状態ラベルと
実行中フラグを `/state` からそのまま描画します。v2 ワークスペースにはこれが
ありません。したがってこの不変条件は新しい面では成り立ち、古い面では破れており、
どこでも真にするのはシェルの変更ではなくレガシー削除です。

**永続的な設定にストアはありません。** ロケール（`ari_lang`、既定 `ja`）、
開発者モード（`ari_dev_mode`）、リモート用 bearer トークン（`ari_gui_token`）は、
いずれも直接 `localStorage` を触りますが、それぞれ 1 キー専用のアクセサ
（`i18n.storedLang()`、`useDevMode.isDevMode()`、`client.getGuiToken()`）の背後に
あります。Settings ページは今も `ari_lang` を自分で `localStorage` から読みます。
3 つをまとめる preference store の抽象も、これらのキーのスキーマも、マイグレー
ション経路もありません。したがって名前や型の変更はキーごとの編集になり、1 か所で
済ませる場所はありません。刷新されたシェルの仕様には preference 層がありましたが
未実装です。この 3 つのキー名を実際の契約とみなしてください。

**フォームのドラフトには所有層がまったくありません。** フロントエンドの依存
（`@tanstack/react-query`、`d3`、`pdfjs-dist`、`react`、`react-dom`、`reactflow`）
にフォームライブラリは無く、共有のフォームモジュールもないので、編集面はどれも
自前のドラフト状態と自前の競合規律を手で組みます。
`ConfigStudio/ConfigStudioPage.tsx` が真似すべき型です: サーバードキュメントの
上に変更値だけを載せる `pending` マップ、`If-Match` として送られるそのドキュメント
の整数 `revision`、そして `revision_conflict` を、未保存の編集を残したまま明示的な
再読み込みとして見せること。`Workflow/WorkflowPage.tsx` は 2 つ目の規律です —
`/api/workflow` が返す弱い内容 `revision` を書き込み時に任意の `base_revision`
として送り返し、サーバーの拒否は throw されたレガシー転送エラーのメッセージ照合で
見分けます（§7）。`Settings/SettingsPage.tsx` は 3 つ目で、競合の経路をそもそも
持ちません: 1 つのコンテナに 37 個の `useState` フックを置き、凍結された保存
ペイロードがドリフトしないよう意図的に集約しています。これらは 1 つの仕組みの
変種ではなく、最初と最後は §1 が述べる重なり合う設定面に対する 2 つの独立した
フォーム所有者です — `ari-core/tests/test_gui_config_shadow_legacy.py` が取り除く
のではなく取り締まっている、あの重なりです。単一のフォーム状態所有者は刷新 GUI の
仕様にありましたが、これは既知のギャップです。

## 5. エンティティモデルは 1 階層しかない

v1 のサーフェスは `project → run` の階層のかたちをしていますが、実在するのは
下の階層だけです。`GET /api/v1/projects` はちょうど 1 つのプロジェクト —
仮想の `default` — だけを返します。その `checkpoint_roots` は実在する
チェックポイント探索ベースであり、ラン一覧はそれら全体にまたがるチェックポイント
ディレクトリの走査（名前フィルタとスキップ集合はレガシーの一覧と同じ）です。
`GET /api/v1/projects/{project_id}/runs` は `default` 以外の id に対して型付きの
`404` を返し、Projects ワークスペースはそれ以上探さずに `projects[0]` を読みます。

設計時に前提としてはならない帰結が 3 つあります:

- **プロジェクトのライフサイクルは存在しません。** `ROUTES` テーブルに
  プロジェクトの作成・改名・削除はありません。プロジェクトを対象とする
  エンドポイントは他に `/api/v1/projects/{project_id}/config` の `GET` /
  `PATCH` があるだけで、どちらも `default` 以外の id を拒否します。読み書き
  されるのは単一のドキュメント `gui_store/project_config.json` です。
- **ランはプロジェクト単位に区切られていません。** ラン単位のエンドポイントは
  すべて `/api/v1/runs/{run_id}/…` でプロジェクトのセグメントを持たないため、URL や
  キャッシュキー（§4）に現れる `project_id` は何も絞り込みません。`default` は
  これらの形を安定させる固定のプレースホルダとして読むべきであり、ランどうしが
  隔離されている証拠として読んではなりません。
- **ラン*は*チェックポイントです。** `run_id` は文字どおりチェックポイント
  ディレクトリ名（`YYYYMMDDHHMMSS_<slug>`）です。チェックポイントは 1 つのランが
  複数持てる保存点としてはモデル化されておらず、ラン間の系譜を表す v1 の
  エンドポイントも DTO もありません — `meta.json` は `parent_run_id` を記録
  しますが、`/api/v1` 配下でそれを読むものはありません。

フィールドレジストリはプロジェクトより*上*の階層も名前だけ持っています。その
`scope` 語彙は `preference` / `installation` / `project` / `template` / `run`
（[設定](../reference/configuration.md) を参照）ですが、5 つのうち実際に
割り当てられるのは 3 つだけです: 現在レジストリが構築するリーフは、単一の
`installation` リーフ `llm.api_key` を除いてすべて `run` か `project` です。
しかもそのリーフは `secret_reference` なので、値は `/api/v1/secrets/*` の背後に
ある `.env` チェーンに住み、GUI ドキュメントには決して入りません。そもそも
ドキュメントストアには preference も installation も置き場所がありません:
保持するのは `project_config.json`、`run_templates/`、`run_drafts/`、
`launches/` だけです（§7）。

実在するプロジェクト（再利用可能な設定の境界）と、ラン（ライフサイクルの境界）と、
チェックポイント（保存点の境界）を分離することは、予約された設計であって実装では
ありません。ツリーの中にそれを実装したものはないので、すでにあるかのように
クライアントを書いてはなりません。

**バージョン付きサーフェスがそもそもモデル化しなかったエンティティが 2 つ
あります。** GUI リフレッシュのドメインモデルは、ラン配下の `Artifact` と
プロジェクト配下の `WorkflowDefinition` も挙げていました。どちらも仕様には
ありましたが未実装です。それぞれの欠落のかたちが、v2 の画面に何ができるかを
決めています。

*アーティファクトというリソースはありません。* `ROUTES` テーブルにはラン配下の
`artifacts` コレクションも、その中のアドレス可能なメンバーもなく、コミット済みの
`openapi.json` にアーティファクトを指すパスは 1 つもありません。`/api/v1` が
提供するのは、名前の決まった射影の固定集合 — `idea`、`results`、`ear`、`logs`、
そして RQGM 一族 — であり、それぞれが知っているファイルに直接結線されています
（§8）。その中で唯一の*ファイル*一覧である `GET /api/v1/runs/{run_id}/ear` は、
`{ckpt}/ear/` という単一のサブツリーだけを走査し、エントリごとに
`path` / `kind` / `size` を返します。上限は先頭 500 エントリで、それを超えると
`truncated: true` になりますが、`file_count` は依然としてすべてのファイルを
数えます。したがって「このランのファイル X」に対応する安定した id はなく、ランが
実際に何を書いたかを列挙するものもなく、新しい種類のアーティファクトはエンド
ポイントの追加と契約の再生成なしには表に出せません。任意のファイルの閲覧は、
チェックポイントをキーとするレガシー面に残りました —
`/api/checkpoint/<id>/files`、`/file`、`/file/raw`、`/filetree`、`/filecontent`
の一族と `GET /codefile?path=` です（[REST API リファレンス](../reference/rest_api.md)
の「チェックポイントブラウジング」と「静的ファイル + フロントエンド」）。
そのため「アーティファクト」は [用語集](../reference/glossary.md) の
「状態と公開」が与えるディスクレベルの意味 — ノードの work_dir 内で生成された
メタデータでないファイル — のままです。

*ワークフローというドキュメントもありません。* パイプライン定義はただのファイル
`{ckpt}/workflow.yaml` であり、`/api/v1` がそれに触れるのはちょうど 2 通りだけで、
どちらもリソースとしてではありません: `POST /api/v1/runs` が同梱の
`config/workflow.yaml` からコピーオンライトで種を作り、その複製へ起動時のモード
ブロックをマージすること。そして `GET /api/v1/runs/{run_id}/resolved-config` の
背後にあるリゾルバが、それを `workflow` プロヴェナンス層として読み、その mtime を
`resolved_at` の入力に数えることです。ドキュメントとしてアドレスするルートは
ありません: id を持たず、`gui_store/` のドキュメントでもなく（§7）、ラン間で
再利用もされません — チェックポイントごとに自分のコピーを持ちます。編集は今も
レガシーの 4 つの書き込み — `POST /api/workflow`、`/api/workflow/flow`、
`/api/workflow/skills`、`/api/workflow/disabled-tools` — であり、その並行制御は
ストアのものとは別の機構です: MN-3 の `revision` は配信したバイト列の sha256
プレフィックスで、
`base_revision` は*任意*なので、それを省いた呼び出し元は last-write-wins のまま
です。一方 `gui_store/` のドキュメントは整数の `revision` を持ち、`If-Match` を
伴わない変更を拒否します（[Configuration Studio](../guides/configuration_studio.md)
の「If-Match の衝突」）。

**ワークフローの編集は 1 つのチェックポイントに閉じており、新しいランがそれを
受け継ぐことはありません。** ワークフローの書き込みは必ず*アクティブ*な
チェックポイントのコピーに着地します: `api_workflow.py` は使えるチェックポイントが
アクティブでないとき書き込みそのものを拒否し、そうでなければ編集を適用する前に
同梱ファイルから `{ckpt}/workflow.yaml` をコピーオンライトで種付けするので、
同梱の既定ファイルが GUI から書き換えられることはありません。そして起動経路は
どちらも、新しいチェックポイントの種をその*同梱*ファイルからのみ作ります:
`POST /api/v1/runs`（`ari/viz/v1/launch.py`）は `config/workflow.yaml` を新しい
チェックポイントへコピーし、その複製へ起動時のモードブロックをマージします。
レガシーのウィザード起動 `POST /api/launch`（`ari/viz/api_experiment.py`）は同じ
同梱ファイルをコピーするか、フェーズトグルのいずれかがオフのときは、オフにされた
ステージを `enabled: false` にし、下流のすべての `depends_on` からも取り除いた
変種を書き出します。どちらも直前までアクティブだったチェックポイントを読まないので、
編集済みのコピーが種になる経路はありません。編集済みのコピーが読み返されるのは
*同じ*チェックポイントがもう一度走るときだけです: BFTS ループ
（`ari/cli/bfts_loop.py`）と論文パイプライン（`ari/core.py`）は、どちらも
`{ckpt}/workflow.yaml` をパッケージのコピーより先に解決します。

**既知のギャップ — その適用範囲を画面上で述べるものがありません。** 刷新は、保存が
どのランに効く編集なのかを宣言することを求めていました。`Workflow/WorkflowPage.tsx`
がツールバーに描画するのは配信されたファイルパスだけで — 適用範囲の手がかりは
それしかありません — それ以上はありません: どのランに効くのかの記述も、保存時の
警告も、パイプラインを次のランへ適用するルートもありません。しかも 2 つの起動経路の
違いも表に出ません: レガシーのウィザード起動はプロセス全体のアクティブ
チェックポイントを新しいランへ切り替えるのでエディタは黙って対象を移し、
`POST /api/v1/runs` は意図的にそれを切り替えないのでエディタは以前のランを
指したままになります。ワークフローの編集は設定ではなく、1 つのチェックポイントの
属性として扱ってください。

もっとも近い再利用可能なドキュメントはランテンプレート
ですが、テンプレートが運ぶのは設定の `values` であってパイプラインではありません。

## 6. リアルタイムは無効化であって真実源ではない

`GET /api/v1/events/stream` はサーバー側で `run_id` / トピックをフィルタする
Server-Sent Events ストリームです。イベントは小さな通知
（`{event_id, run_id, topic, revision, occurred_at, kind, resource, payload}`）
であり、消費側の唯一の反応は一致するキャッシュキーを無効化して HTTP スナップ
ショットを再取得することです。

イベント*から*描画されるものは一切ありません。この設計の理由はその帰結にあります:

- **重複と順序入れ替えは無害です。** 何が真かを決めるのはスナップショット
  エンドポイントであり、イベントは*いつ聞き直すか*を決めるだけです。
- **ストリームの切断は鮮度の問題であって、状態変化では決してありません。**
  最後のスナップショットが陳腐化バナー付きで画面に残ります。切断が「ランが
  停止した」として提示されることはありません。
- **再接続は安価で有界です。** 指数バックオフ（1 秒 → 上限 30 秒）と
  `Last-Event-ID` カーソル; エラーが 1 分を超えて続くと接続は `offline` へ
  移り、これがサブスクリプション自身のスコープに対する有界な 10 秒ポーリング
  フォールバックを有効にする*唯一の*状態です。
- **バスは小さく保たれます。** イベントは固定上限を持つ追記専用のインメモリ
  リングバッファに住み、ハートビートコメントと有界なストリーム窓により、
  アイドルなプロキシや固まったクライアントがワーカーを永久に占有できないように
  なっています。

イベントは自身の `run_id` を持つので、ラン B のイベントがラン A のキャッシュ
エントリに触れることはありません — §4 と同じ隔離性が、キャッシュの書き込み側でも
強制されています。

**所有者は 1 つ、正直な例外が 2 つ。** `/api/v1` 上のリアルタイムの所有者は
ちょうど 1 つ、`shared/realtime/eventStream.ts` です。ページは
`subscribe(runId, topics, callbacks)` を — 通常は `useRunEvents` フック経由で —
呼ぶだけで、自分で `EventSource` を組み立てることはありません。だからバック
オフのスケジュール、`last_event_id` カーソル、3 状態の接続マシン、オフライン時の
ポーリング刻みは 1 箇所にだけ存在し、1 度だけテストされます。この所有権の外に
あり、かつそれ以前から存在するチャネルが 2 つあります: HTTP ポート + 1 の
レガシーツリー WebSocket と、ジョブ実行中に PaperBench のログストリームへ自前の
`EventSource` を開く PaperBench ジョブログビューアです。どちらも真似すべき
パターンではなく、削除の候補です。

**購読はマウントされたルートとその run に従います。** ページは自分の生存期間
だけ購読し、`run_id` / `topics` のフィルタはサーバー側で行われるので、ページが
描画しないイベントの代金を払うことはありません。ただし隠れたタブを絞る仕組みは
ありません: クライアントは `visibilitychange` を購読していないため、背面に回った
タブもストリームを開いたままバックオフで再接続を続け、10 秒のオフライン
ポーリングを刻み続けます。バックグラウンドタブの負荷制御は仕様にはありましたが
未実装であり、古いタブが複数あればそれぞれがストリームを 1 本ずつ保持します。

## 7. バックエンドのシーム

サーバーは 4 層であり、各層は 1 つ下の層についてだけ知ることが許されます。

このシームの下に Web フレームワークはありません。転送は Python 標準ライブラリ
です: `server.py` はホストごとに `ThreadingHTTPServer` を 1 つずつバインドし
（ループバック既定は両方のファミリを要求し、片方が使えなくても許容します。
2 つ目以降のサーバーはデーモンスレッド上で `serve_forever()` を回します）、
リクエストは `routes.py` にある唯一の `BaseHTTPRequestHandler` サブクラスが
処理します。旧来の面はリクエストパスに対する明示的な `if`/`elif` の連鎖で
ディスパッチされ、`/api/v1/` 配下は
宣言的な `ROUTES` テーブルへ委譲されます（`/api/v1/events/stream` だけは 1 つ
手前の分岐で捕まえます。ディスパッチャは dict を返すのに対し、SSE は長命な
ストリームを書き続ける必要があるためです）。asyncio なのはツリー WebSocket
だけです: `_main` が唯一の asyncio エントリポイントであり、ウォッチャと HTTP
サーバーをデーモンスレッドで起動したあとは、HTTP ポート + 1 の `websockets`
サーバー以外は何もホストしません。ここから 2 つの帰結が本節全体に効いてきます。
API 層がルーティングもエラーエンベロープも OpenAPI 生成も自前で持つのは、
継承元となるフレームワークが存在しないからです — 設定するのではなく、ここで
作られています。そして 1 本の接続は開いている間ずっとワーカースレッドを 1 つ
占有します: ハンドラが `protocol_version = "HTTP/1.1"` を設定するのは、短い
ポーリングが 1 本の接続を再利用してブラウザのオリジンあたりの接続プールを
枯渇させないためであり、一方で長命なストリーミング系エンドポイントは
`Connection: close` を返して keep-alive のスロットに居座らないようにします。
したがってハンドラ内でブロックする処理のコストは、コルーチンではなく
スレッドです。

| 層 | モジュール | 責務 |
|---|---|---|
| 転送 | `ari/viz/routes.py`（+ `auth.py`、`server.py`、`health.py`） | ソケットレベルのポリシー: same-origin CORS のエコー、SPA / 静的レスポンスへの `Content-Security-Policy` / `nosniff` / `Referrer-Policy`、非ループバックバインド時の bearer トークン認証、アクセスログ、`/health/live` と `/health/ready`。 |
| API | `ari/viz/v1/router.py` | `(method, path template, handler)` の宣言的な `ROUTES` テーブル 1 枚。ディスパッチごとに `request_id` を発行し、成功ペイロードまたは型付きエラーエンベロープへ通します; `PATCH`/`DELETE` で `If-Match` の楽観的並行制御を強制します; 同じテーブルがコミット済みの `openapi.json` を生成するため、契約がディスパッチャからドリフトすることはありません。 |
| 読み取りモデル | `queries.py`、`results.py`、`rqgm.py`、`logs.py`、`catalogs.py` | チェックポイントディレクトリから DTO への純粋関数。`viz.state` の変更なし、`os.environ` への書き込みなし、ファイル書き込みなし — GET に副作用はありません。 |
| 真実 | `{checkpoint}/…`、および GUI 専用文書のための `{workspace_root}/gui_store/` | コミット済み成果物。 |

**この 4 層は記述であって、パッケージ構成ではありません。** `ari/viz/` に
`transport/`、`application/`、`domain/`、`infrastructure/`、`legacy/` という
パッケージはなく、いかなる意味でもドメイン層はありません: 読み取りモジュールと
ワイヤの間には何も挟まっておらず、チェックポイントの `Path` がそのまま pydantic の
DTO になります。GUI リフレッシュはまさにその分割を — バージョンなしのハンドラを
アダプタモジュールの背後へ移すことも含めて — 仕様に挙げていましたが、実装され
ませんでした。レガシーのハンドラは元の場所に残り、`routes.py` の `if`/`elif` の
連鎖がそれぞれの `api_*` モジュールから直接インポートしています
（[内部境界](../reference/internal_boundaries.md) の
「GUI の HTTP ディスパッチ境界」）。

同じ提案にあったプロセススーパーバイザも、同じ条件で欠けています。
`POST /api/v1/runs` は CLI を
`subprocess.Popen(..., start_new_session=True)` で起動し、そのハンドルを
`ari/viz/state.py` のモジュールグローバルな `_running_procs` マップへ、解決済みの
チェックポイントパスをキーとして記録します — レガシーの起動ハンドラが書き込むのと
同じマップです。これらの子プロセスを監督・再起動・回収するものは何もありません。
エントリがマップから消えるのは日和見的な場合だけです: レガシーのチェックポイント
一覧が次に子プロセスの終了に気づいたとき、同じ一覧がチェックポイントディレクトリの
消えたエントリを剪定するとき、あるいはチェックポイントが削除されたときです。この
マップはプロセスローカルなので、サーバーを再起動すればすべてのハンドルを忘れます。
v1 の読み取りモデルはこれを一切参照せず、ランの状態はファイルシステムから
導出します（下記）。そして `/api/v1/diagnostics` が公開するのはその長さだけ、
`process.tracked_runs` としてです。このシームは、パッケージ境界のように何かが強制
できるものではなく、読み取りモジュール自身の規律とそれをピン留めするテストによって
保たれているものとして扱ってください。

このシームの 3 つの性質は侵食されやすいので明示しておく価値があります:

- **`GET` は副作用フリーです。** 読み取りモジュールは、読まれた副作用として状態を
  変更する旧ハンドラのようにサーバーのプロセス追跡状態を参照・剪定するのではなく、
  意図的にファイルシステムからラン状態を再導出します（pid プローブ → ツリーによる
  精緻化 → レビューレポート）。
- **書き込みは狭く明示的です。** GUI 自身の文書 — プロジェクト既定値、ラン
  テンプレート、ランドラフト、起動の冪等性レコード — はグローバルなホーム
  ディレクトリではなく `{workspace_root}/gui_store/` に住み、アトミック書き込みと、
  `ETag` / `If-Match` へ 1:1 対応する整数 `revision` を持ちます。これらは便宜層
  です: 起動時にすべての実効値がチェックポイントへ実体化されるため、CLI がランを
  再現するために `gui_store/` を読む必要は決してありません。
- **鋳造されるタイムスタンプは時計ではなくファイルシステム由来です。** 読み取り
  リソースのためにサーバーが*導出する*時刻フィールドは、`datetime.now()` では
  なくソースファイルの mtime から取った UTC ISO 8601 文字列です: ランサマリの
  `mtime_utc` はチェックポイントディレクトリの mtime、ランテンプレートやラン
  ドラフトの `updated_at` はそのドキュメントファイルの mtime、解決済み設定の
  `resolved_at` はリゾルバのソースファイル群のうち最新の mtime（どれも無ければ
  チェックポイントディレクトリの mtime）です。これにより、変化していないランを
  続けて 2 回 GET すると、ルーターがディスパッチごとに発行する `request_id` を
  除いて同一になり、キャプチャした 2 つのペイロードの差分は「時間が経った」では
  なく「何かが変わった」を意味します —
  `ari-core/tests/test_gui_config_precedence_matrix.py` が
  `test_resolved_at_mtime_stable_and_deterministic` でリゾルバについてこれを
  ピン留めしており、`request_id` を落としたうえで 2 つのレスポンスがそれ以外
  等しいことを表明します。コミット済み成果物から*コピーされた*タイムスタンプは、その成果物
  自身の値のままです（RQGM トランジションの `committed_at`、公開レコードの
  `timestamp`）。時計を読むのは、読むべきファイルが存在しない箇所だけです:
  イベントの `occurred_at`（§6）とチャレンジの `expires_at` です。

**このシームのブラウザ側には、意図的に統一されていない 3 つの転送レジームが
あります。** `services/api/client.ts` は 3 組のラッパーを公開していて、どの組を
使うかは契約の一部です。6 つのうち 5 つは 1 つの `request` プリミティブを共有
しますが、6 つ目の `v1Send` は意図的に自前の `RequestInit` を組み立てます —
このプリミティブのオプション形状自体が凍結されたレガシーのワイヤ契約の一部
なので、v1 のミューテーション転送は `If-Match` ヘッダも含めて `request` の中では
なく隣に置かれています:

- `get` / `post` は、2xx 以外なら
  `Error('<METHOD> <path> failed: <status>')` を throw します。レガシーの
  `useApi` フックとその呼び出し元は、この throw に依存しています。
- `pbGet` / `pbPost` は決して throw しません。PaperBench のハンドラは HTTP 200 と
  `{error: …}` ボディで答えるので、アプリケーションエラーはボディで届き、
  呼び出し元がその場で扱います。
- `v1Get` / `v1Send` はステータスにかかわらずパース済みボディで resolve します。
  `/api/v1` は本物の 2xx 以外のステータスを返し、そのボディ*こそ*が型付き
  エラーエンベロープだからです — throw するクライアントは、UI が必要とする
  ペイロードをまさに捨ててしまいます。そのうえで `services/api/v1.ts` が
  あらゆる失敗（型付きエンベロープ、ネットワークエラー、パースできないボディ）を
  1 つの throw される `ApiErrorV1`
  `{code, message, details, request_id, retryable}` へ正規化します。

この非対称性は整理されずに保存されています: 最初の 2 つのレジームは挙動を凍結する
テストでピン留めされており、統一すればレガシーの呼び出し元すべてが見るものを
黙って変えてしまいます。新しいコードは `/api/v1` のレジームを使ってください。

このクライアントには、無いこと自体をポリシーと取り違えやすい欠落が 2 つあります:

- **クライアント側の abort も timeout もありません。** 共有の `request`
  プリミティブも `v1Send` も `AbortSignal` を渡さず、期限も設定しません。
  したがって固まったリクエストはブラウザが諦めるまで固まったままで、ページを
  離れても実行中の fetch はキャンセルされません。リトライ方針は react-query の既定（1 回）に、
  エラーエンベロープ上のサーバー申告 `retryable` フラグを加えたものですが、後者は
  呼び出し元が参照できるだけで自動的に消費するものはありません。冪等性はメソッド
  メタデータではなくエンドポイント単位です: `idempotency_key` を持つのはラン起動
  だけで、レビュー承認ごとに 1 つ発行されるため、ダブルクリックやリトライは
  2 本目のランを産まず同じランを再生します。メソッド単位の
  abort / timeout / retry / 冪等性メタデータは仕様にはありましたが未実装です。
- **スキーマのドリフトはビルド時に捕まえ、実行時には捕まえません。** 生成 DTO
  モジュール `services/api/v1types.gen.ts` は `ari/viz/v1/openapi.json` から
  生成され、ドリフト検査テストがバイト単位で比較するので、再生成を忘れた契約変更は
  CI で落ち、出荷されません。実行時には互換性チェックがありません: 生成 DTO と
  一致しないレスポンスは検出されず、そもそもパースできないボディは
  `code: 'internal'` / `retryable: true` へ正規化されるため、転送の一時的な不調と
  区別がつきません。「このバンドルはこのサーバーと一致しません」という専用の互換性
  エラーは仕様にはありましたが未実装なので、バンドルとサーバーの不一致は普通の
  internal エラーとして、あるいはフィールド欠落による空白として現れます。

## 8. 読み取りモデルは使い捨ての射影

*読み取りモデル*とは、コミット済み成果物から要求時に計算される有界な射影です。
読み取りモデルをすべて削除しても情報は失われませんが、成果物を削除すればそれは
失われます。この非対称性こそが要点です。

**「要求時」は文字どおりです: 毎回再計算し、キャッシュしません。** `/api/v1` の
GET は、射影する成果物を毎回読み直します。`ari/viz/v1/` 配下のどこにも射影の
インデックスもメモ化も無効化テーブルもありません — このパッケージが持つ唯一の
キャッシュは `launch.py` の冪等性リプレイマップで、これは読み取りではなく重複した
起動 POST に応えるためのものです。ファイル identity・サイズ・mtime・内容ダイジェスト
で無効化される永続的な読み取りモデルインデックスは GUI リフレッシュの仕様には
ありましたが未実装です。ワイヤはそれを隠さず明言していて、
`GET /api/v1/diagnostics` はリテラルのフィールド `cache: false` を運びます。
代わりにコストを有界に保つのはエンドポイントごとの規律です — バイトオフセットの
カーソル、上限のあるページサイズ、ログリーダーのリクエストあたり 1 MiB の走査窓
（[REST API リファレンス](../reference/rest_api.md) の「カーソル規約」）— に加えて、
同じスナップショットが二度取得されずに済む場所である §4 のクライアント
キャッシュです。そうした上限を持たないエンドポイントは毎リクエストで満額の
コストを払います。ノード一覧を丸ごと返す `GET /api/v1/runs/{run_id}/tree` が
その最も分かりやすい例です。

ガバナンス読み取りモデルは最も厳格な実例であり、「射影」が実務上何を意味するかを
示します:

- **どの判断も再実行しません。** `ari/viz/v1/rqgm.py` は `ari.rqgm` を決して
  インポートしません。コミット済み成果物（`rqgm_state.json`、
  `rqgm_transitions.jsonl`、`rqgm_audit.jsonl`、`rqgm_registry.json`、ノード
  メトリクスのセンチネル…）をパースし、それらが言っていることを報告します。GUI が
  ガバナンスの評決を捏造できないのは、評決を生むカーネルを一度も実行しないから
  です。
- **コミット済みレコードのみ。** 現在状態は*コミット済み*遷移の replay です。
  途切れた末尾の JSONL 行は無視され、対応する commit を持たない prepare 以降の
  イベントは決して採用されません。rollup スナップショットは、replay と一致するか
  検証するためだけに読まれます。
- **壊れるのではなく縮退する。** 成果物が壊れていても存在しなくても HTTP 200 と
  正直なフラグを返します: 整合性は三値（`true` 検証済み / `false` 破損 / `null`
  ソース不在）で、`degraded_reasons` リストがペイロードに同行します。存在しない
  ソースがクリーンとして描画されることも、ゼロとして描画されることもありません。
- **構造上有界です。** 要約は埋め込みエントリ一覧ではなく件数を持ち、長いログは
  安定オフセット上のカーソルでページングされます。ファイルを丸ごと読み出すのは
  `/rqgm/policies` と `/rqgm/epochs/{epoch_id}` が返す統治済みポリシー本体だけで、
  そのバイト列が登録済みの `prompt_hash` に一致しなくなった場合は、degraded の
  理由として明示したうえで本体そのものを出しません。

ダッシュボードを拡張する人への運用規則はこうです: GUI の表示を変えたいなら射影を
変えること — 成果物を変えてはならず、カーネルが既にコミットした判断を再計算しても
なりません。

## 9. capability とキルスイッチ

ダッシュボードは「これは利用できません」を 2 種類に区別し、どちらもエラーでは
ありません。

**サーバー capability — このビルドが提供するもの。** `GET /api/capabilities` が
`gui_v2` フラグ（`ARI_GUI_V2`、既定オン）を報告します。フロントエンドはマウント時
に一度取得し、取得の*失敗*をオンとして扱うため、API の一時的な不調でローカル
ユーザーがフォールバックシェルに取り残されることはありません。

**ラン capability — このランの成果物が支えるもの。** 成果物の存在のみから検出
されます: `rqgm_state.json` があるからランはガバナンス下であり、
`paper_archive_state.json` があるからアーカイブ論文モードです（両者は独立した軸）。
ガバナンスの無いランには、空画面や捏造されたゼロではなく、理由を挙げた
「このランではガバナンスが有効でない — これは capability の状態であってエラーでは
ない」というパネルが表示されます。

刷新された GUI で導入されたリスクのある挙動にはすべて環境変数のキルスイッチが
付属しており、リリースを巻き戻さずに 1 つの決定だけを戻せます。すべて
`scripts/setup/setup_env.sh` に文書化されています:

| 変数 | 既定 | オフにすると戻るもの |
|---|---|---|
| `ARI_GUI_V2` | オン | レガシーシェルのみ（v2 専用ルートは Home へフォールバック） |
| `ARI_GUI_BIND` | ループバック（`127.0.0.1` + `::1`） | より広いバインド。例: 全インタフェースの `::` |
| `ARI_GUI_TOKEN` / `ARI_GUI_AUTH` | 非ループバックバインドでは認証を強制 | 未認証のリモートバインド（例: 認証を行うプロキシの背後） |
| `ARI_GUI_CORS_ANY` | オフ（same-origin エコー） | レガシーの `Access-Control-Allow-Origin: *` ワイルドカード |
| `ARI_GUI_CSP` | オン | CSP / nosniff / Referrer-Policy ヘッダの無いレスポンス |
| `ARI_GUI_CHALLENGES` | オン | 確認チャレンジ無しの直接的な破壊的エンドポイント |
| `ARI_GUI_HEALTH` | オン | ヘルスプローブ導入前のレスポンス（diagnostics エンドポイント無し） |

これらのスイッチが守るセキュリティ既定値は一度述べておく価値があります: サーバー
はループバックのみにバインドするので、既定のローカル体験に認証は不要です; 非
ループバックバインドは bearer トークンを要求することで*フェイルセキュア*します
（未設定なら起動時に生成され一度だけ表示されます）; そして 3 つの破壊的操作
（チェックポイント削除、停止、GPU モニタ停止）はサーバー発行の単回使用確認
チャレンジを要求し、無い場合は `428` を返します。

## 10. フロントエンドのコードが置かれる場所

フロントエンドは*画面*単位でグループ化されており、その上にある合成層は
ルートレジストリだけです。`ari-core/ari/viz/frontend/src/` の下は次のとおりです:

| ディレクトリ | 置かれるもの |
|---|---|
| `app/` | どの画面も所有しないシェル配線: ルートレジストリ（§2）と react-query クライアント（§4）。 |
| `components/<Screen>/` | 画面ごとに 1 ディレクトリ。レガシーと v2 が並んで置かれ（`Tree/` と `TreeV2/`、`Results/` と `ResultsV2/`）、それぞれがレジストリの遅延ロード対象のページコンポーネントを export します。加えて表示用プリミティブの `common/` と、サイドバーおよびアクティブページを包むページフレームの `Layout/`。 |
| `context/` | レガシーの `AppContext` — `/state` ポーリングとプロセス全体のアクティブチェックポイント。 |
| `hooks/` | 画面横断のフック: `useV1`、`useRunEvents`、`useApi`、`useWebSocket`、`useDevMode`。 |
| `services/api/` | 1 つのトランスポートコア（`client.ts`）と、エンドポイントファミリごとの 1 モジュール。`services/api.ts` のバレルが再 export するので、古い import パスもそのまま解決します。 |
| `shared/` | 横断的なプラットフォームコード — 現時点では SSE クライアントである `realtime/` のみ。 |
| `i18n/`、`styles/`、`types/` | 3 言語の文字列表、CSS のトークン／レイアウトシート、共有 DTO 型。 |
| `__tests__/` | どの画面も所有しないアプリ全体のガードスイート: ルート↔ナビのパリティ、App 全体のルート描画、シェルの a11y、開発者モードのゲーティング、生成型のドリフト。 |

`pages/` 層はありません。レジストリエントリの `load` サンクが画面コンポーネント
を直接 import するので、ルートの合成*そのもの*がレジストリエントリです。

**feature / entity への分割は仕様化されましたが、作られていません。** GUI 刷新は
さらに `features/` と `entities/` へ分けること、そして feature は他の feature の
internal module を import せず、entity / shared の contract、あるいはそれらを
合成する page を介すること、を求めていました。そのどれも存在しません: `features/`、`entities/`、`pages/` の各
ディレクトリは無く、再利用のほうが安いところではツリーが既に画面境界を跨いで
います — `ConfigStudio` は `ConfigBrowser` の読み取り専用 config テーブルを
（2 つの config 面がドリフトしないよう意図的に）import し、`Monitor` と `TreeV2`
はどちらもレガシーの `Tree` ビジュアライゼーションを import しています。

レイヤ境界を強制する仕組みもありません。フロントエンドの `package.json` には
lint ステップも lint 依存も無いので、ツリーにある唯一の構造的 import ガードは
テストです — `src/__tests__/appContextScope.test.ts` が v2 画面ディレクトリ配下の
非テストファイルをすべて走査して `AppContext` の import 指定子を探し、ピン留め
された 1 つの例外を超えるものがあれば失敗します。このガードが守るのはレガシー
削除ゲートであって feature / entity 境界ではなく、画面間の import を制約する
走査はいっさい存在しません。

この分割は、ツリーが従っている構造ではなく進むべき方向として読んでください。
今日実際に守られているのはもっと浅い配置規則です: 表示用プリミティブは
`components/common/`、横断的なプラットフォームコードは `shared/`、シェル配線は
`app/`、そして画面ディレクトリが所有するのは自分の画面だけ、というものです。

**デザイントークンは 3 層ではなく 2 層です。** カスタムプロパティを*定義*して
いるファイルは `styles/tokens.css` だけです。`motion.css` はそのうち 3 つ —
`--t-fast`、`--t-med`、`--t-slow` — を `prefers-reduced-motion: reduce` の下で
ゼロに再定義し、`Layout/Sidebar.tsx` はインラインで `--sidebar-width` を書き
ますが、これはレイアウトシートが読む寸法であってトークンではありません。それ
以外はすべて 1 つの `:root` ブロックに、2 つの名前付きレイヤとして入っています。
**プリミティブ**レイヤは生のスケールです: 色相（`--bg`、`--sidebar`、`--card`、
`--border`、`--text`、`--muted`、`--blue`、`--blue-light`、`--green`、`--red`、
`--yellow`、`--purple`、それに別名の `--primary`）、`--sp-1` から `--sp-8` まで
の間隔ステップ（4px から 32px、`--sp-7` は欠番）、角丸とフォーカスシャドウ、
タイプスケール、モーション時間。**セマンティック**レイヤは役割に名前を与え、
それぞれをプリミティブか、プリミティブの `color-mix()` に解決します — 新しい
色相はここでは 1 つも導入されません: `--surface-canvas` / `--surface-raised` /
`--surface-overlay`、`--text-primary` / `--text-muted` / `--text-inverse`、
`--border-default` / `--border-focus` / `--focus-ring`、3 つのリンク色、4 つの
`--status-*` 前景色とそれぞれの `-bg` ティント（うち 2 つはプリミティブの隣で
宣言される `-border` ティントも持ちます）、`--score-penalty`、5 つの `--state-*`
ノードスコア色、10 個の `--reg-*` レジストリライフサイクル色です。

3 層目の**コンポーネント**層は、この 2 層の上に仕様化され — あるコンポーネント
の 1 つの役割に名前を付けたトークン、たとえばプライマリボタンの背景や、選択
されたグラフノードの塗り — 作られませんでした。セマンティック層より上の役割
トークンはツリーのどこにも存在しません。*名前*がコンポーネントに由来する唯一の
カスタムプロパティはプリミティブの面色 `--sidebar` で、これは最上層の上に立つ
役割ではなく最下層の生の値です。コンポーネント層が入るはずだった場所では、
代わりに CSS クラスがセマンティックトークンを直接消費します: `components.css`
は 10 個のレジストリステータスそれぞれに `.reg-badge--<status>` ルールを、5 つの
ノードスコア状態それぞれに `.nodestate-badge--<state>` ルールを定義し、いずれも
対応する `--reg-*` / `--state-*` トークンから `color` を取ります。2 つのクラス
系列は意図的に交わりません。これは固定パレットの目的そのもの — どちらの語彙も
他方の色を借りられないこと、
[研究状態とガバナンス状態](research_and_governance_state.md) の
「4. レジストリのライフサイクル対ノードのスコア状態」が要求するもの — を実現
しますが、トークンの 3 層目ではなくクラス名によって実現しています。

**既知のギャップ — セマンティック層より上がその層を越えてプリミティブ色へ手を
伸ばさない、というルールは強制されておらず、ツリーもそれに従っていません。**
上で述べたとおり `package.json` に lint ステップはなく、テストも
`scripts/quality/` 配下のチェッカーもスタイルシートをいっさい読みません
（バンドル重量ゲートが量るのは `.js` チャンクだけです）。したがって違反で落ちる
ものが何もありません。13 個のプリミティブ色名に対する `var(…)` の使用箇所を
数えると、458 箇所が `components/` 配下の非テスト `.tsx` 53 ファイルにあり、
さらに 140 箇所がスタイルシート自身にあります（`components.css` 66、
`widgets.css` 47、`layout.css` 21、`responsive.css` 6）— 同じファイル群で
セマンティック層全体の使用は 113 箇所です。v2 ワークスペースはこの偏りのまし
な側ですが、きれいでもありません: `.tsx` の使用のうち 38 箇所が v2 ワークス
ペース、2 箇所が `components/common/` にあり、そのすべてが `--muted`、
`--border`、`--bg`、`--red` のいずれか — つまり `--text-muted`、
`--border-default`、`--surface-canvas`、`--status-danger` という、代わりを
務められるセマンティック名を持つものです。セマンティック層は additive で部分的
にしか採用されていない、と読んでください: 上の分割が構造に対してそうであるのと
同じく、色についての進むべき方向であって、ツリーが従っている境界ではありません。

**既知のギャップ — セマンティック層はテーマを持ちません。** その存在理由は、
light / dark / high-contrast のバリアントを差し替える単一の場所になり、
プリミティブとコンポーネントには手を触れずに済ませることでした。ダッシュボード
が出荷するテーマはちょうど 1 つで、`tokens.css` はそれをルートで明言しています:
`color-scheme: dark` を宣言するのは、CSS が届かないコントロール — チェック
ボックスやラジオのグリフ、スクロールバー、`<select>` のポップアップ — を UA が
面に明るい穴を開ける代わりにダークで描くようにするためであり、チェック状態は
`accent-color` で固定されています。`prefers-color-scheme` ブロックはフロント
エンドのどこにも無く、テーマスイッチも無いので、2 組目のセマンティック値は一度
も書かれていません。スタイルシートが実際に尊重する唯一のユーザー設定は、
`motion.css` にある `prefers-reduced-motion: reduce` です。

## 11. 開示レベル: 尋ねる前に画面が見せるもの

ダッシュボードは複数の種類の読み手を同時に相手にします — 最初のランを起動する人、
探索木を読む人、止まったプロセスを診断する人、ガバナンスの判断を監査する人、
生の成果物を読む人。刷新はこれに対し、読み手ごとに別のアプリを作るのではなく、
主題ごとに 1 つの画面を置き、その*深度*を変えることで答えました。この帰結は
述べておく価値があります。設計のカテゴリがまるごと 1 つ存在しない理由がこれだから
です: 役割を意識する画面は無く、権限述語を持つルートも無く（§2）、そもそも
プロダクトの中に読み手をモデル化したものがありません。深度は読み手が自分で開く
ものであって、与えられるものではありません。

深度は P1 から P5 までの 5 段のはしごで記述されます。レベル名は飾りではなく、
ある情報がどこに属するかをソースが決めるときに使う語彙であり、コンポーネントの
コメントとテスト名にそのまま現れます。

| レベル | 内容 | 意図された既定 |
|---|---|---|
| P1 | run の状態、現在の phase、ブロックされている理由、次の操作 | 常時表示 |
| P2 | スコア要約、ツリー、エポック、主要な成果物 | 常時表示 |
| P3 | 根拠、遷移の理由、config の差分、リソース詳細 | 操作 1 回 |
| P4 | トレース、ログ、ノードごとの系譜、生イベントへのリンク | 操作 1〜2 回 |
| P5 | 生の JSON / YAML、内部 ID、デバッグペイロード | 開発者モードのみ |

最後の列は意図として読んでください。5 段のうち作られているのは 3 段であり、
ツリーが表から外れている箇所については、どちらへ外れているかを知る価値が
あります。

**はしごが実装されている場所。** ラン Overview（`#/overview?run=`）が明示的に
これに沿って作られた唯一の画面であり、そこに存在するのも P1・P2・P4 の 3 段だけ
です。P1 はラベル付き行のブロック — ライフサイクルバッジ、リサーチ phase、最終
更新の鮮度、そしてガバナンス下のランでは現在のエポックと utility ポリシー
ハッシュを載せた独立したガバナンスステージ行 — で、その上に blocker パネルが
出ます。パネルが出るのは、ガバナンス下のランの読み取りモデルが degraded reason を
報告したとき、または 3 つの整合性フラグ（トランジション連鎖、レジストリ
スナップショット、監査連鎖）のいずれかが偽のときです。P2 は 3 つのカウンタ
（探索ノード数、レビュースコア、ベスト指標）と、ツリー・config ブラウザ・
（ガバナンス下のランでは）Governance へのワークスペースリンクです。P4 は開閉
できるログエクスプローラで、ここでの「遅延」が何を意味しなければならないかを
示す段でもあります: パネルが閉じている間は何ひとつ取得されず、そのテストは
マークアップが隠れていることではなくこの点を直接表明します。描画してから内容を
隠す段は、段ではありません。

作られている範囲の中に 1 つだけ表からのずれがあります: エポックとポリシー
ハッシュは表では P2 にありますが、描画されるのは P1 の行ブロックの中です。
ガバナンス下のランにとって、それらは「このランはどこにいるか」の一部であって、
「どう採点されているか」の一部ではないからです。

**P3 は層としては作られませんでした。** ラベル付きの P3 段を持つ画面はなく、この
レベル名はどのソースファイルにも現れません。P3 が名指す素材そのものは存在しますが、
そこへ届くのはその場で何かを開くことではなく、別のワークスペースへ行くことです:
Governance のエポックタイムラインタブにあるコミット済みエポックの詳細（封印された
ポリシー本体と、生ソースのオフセット付きの開始／終了境界トランザクション）、
config ブラウザのリーフごとのプロヴェナンス、Studio の起動パネルにある既定値との
実効設定差分、レガシー Monitor ページのリソースとプロセスの詳細。P3 は素材の記述
として読むべきであり、何クリックで届くかの約束としてではありません。

**P5 は開発者モードであり、しかもレガシー画面だけです。** フラグは
`localStorage['ari_dev_mode']` で、1 つのフック（`hooks/useDevMode.ts`）を通して
読まれ、それを参照する面はすべてレガシーです: Monitor のセクションとその GPU
モニタ、レガシー Results の `publish.yaml` エディタ、ウィザードのリソース
ステップ、レガシー Tree の詳細パネル、トグルを所有する Settings ページ、そして
ルートのエラーバウンダリのスタックトレース（§2）。v2 ワークスペースでこのフックを
import するものは無いので、v2 画面には開くべき P5 段がそもそもありません。仕様は
P5 に権限チェックも組み合わせていましたが、その半分はここでは存在し得ません。
bearer トークンは全か無かであり、ユーザーをモデル化するものが無いからです（§2）。
開発者モードが変えるのは表示密度だけです。認可境界ではなく、そこで見えるものは、
API を直接叩く未認証の呼び出し元から隠されているわけでもありません —
[ダッシュボードガイド](../guides/dashboard.md) の「レガシー画面と、その使いどころ」
を参照してください。

**グローバルなラン文脈の要素は存在しません。** P1 は*すべての* run スコープ画面に
常時あることが仕様でした — プロジェクトとランの識別、ライフサイクル、phase と
鮮度、実行モードと論文モード、エポックとポリシーハッシュを伴うガバナンス
capability、アラート数付きのリソース／コスト要約、接続状態を運ぶ、1 つの持続的な
シェル要素として。その要素は存在しません。これは known gap（既知の欠落）であり、
しかも一様ではありません: P1 が挙げるものの大半はどこかの画面には出ていて、ただ
1 か所にまとまっておらず、すべての画面に出てもいない、という形です。

シェル自身が持つのは、ナビゲーションの上にあるレガシーのアクティブチェックポイント
ピッカーです — チェックポイント数、プロセス全体のアクティブチェックポイントに
束ねられた `<select>`、そして `/state` からそのまま読んだ稼働ドット付きの
ステータスラベル（§4）。v2 ワークスペースはそのどれも読みません。そう保っている
のは `src/__tests__/appContextScope.test.ts` の構造スキャンで、v2 は代わりに
`?run=` からランを取ります。したがってピッカーが説明しているのはプロセス全体で
選ばれているチェックポイントであって、開いているワークスペースが表示している
ランとは限りません。

残りは画面ごとに散っています。ライフサイクルとリサーチ phase を描画するのはラン
Overview だけです。現在のエポックと utility ポリシーハッシュは、ガバナンス下の
ランでは Overview のガバナンス行に、そして Governance ワークスペースの中にも
描画されます — 実行モードと論文モードが、語彙の求める 2 つの独立したチップとして
現れる唯一の場所もそこであり、値は RQGM の capability モデルから読まれます（§9）。
ラン識別は画面ごとです: run スコープの v2 ワークスペースはどれも自分の `?run=`
値を表示します。接続状態も同じで、ラン Overview・Tree ワークスペース・
Governance・Projects ポートフォリオはイベントストリームが live でないときに
それぞれ自前の鮮度バナーを出し、config ブラウザはキャッシュ済みデータの上で
再取得が失敗したときに出し、Ideas と Results のワークスペースはストリームを購読
せず鮮度をまったく表示しません。

P1 の項目のうち 2 つは、run スコープの居場所がまったくありません。リソース／コスト
要約はレガシー側の数字です: `/state` が `cost_summary.json` をパースしたものを
`cost` として運び（[REST API リファレンス](../reference/rest_api.md) の
「型付き契約（安定エンドポイント）」を参照）、レガシー Monitor ページがそれを
リソースカードの隣に描画します。一方 `/api/v1` の下には cost に触れるものが
ありません。したがって、たとえシェルに置き場所があったとしても、v2 ワークスペースに
出せる数字がありません。そしてアラート数に最も近いのは Projects ポートフォリオの
「Needs attention」タイルで、これは状態が `failed`・`stopped`・`unknown` のランを
数えます: ポートフォリオの統計であって、ラン 1 件のバッジではありません。P1 が
約束する「次の操作」はさらに薄く、空の Projects ページにある作成・インポート・
再開の 3 リンクだけで、3 つとも起動ウィザードを開きます。ブロックされたランは
blocker を並べ、そこで止まります。

「P1 は常時見える」は、ラン Overview が満たし、他のどの画面もそう作られなかった
画面単位の意図として扱ってください。
