# ダッシュボードアーキテクチャ

ARI のダッシュボードは、`ari/viz/` の Python HTTP サーバーが配信する
React/TypeScript のシングルページアプリです。このページは*概念*ビューです:
ダッシュボードが今の形になっている理由を説明する、ごく少数の構造的決定 —
2 世代の画面を 1 つのシェルが載せること、ルートを 1 つのレジストリが所有すること、
サーバー状態を 1 つのキャッシュが所有すること、HTTP とファイルシステムの間に
1 つのシームがあること。

エンドポイント一覧でもクリック手順ツアーでもないのは意図的です:

- [ダッシュボードガイド](../guides/dashboard.md) — 運用者向けツアー: サーバーの
  起動、各ワークスペースが答えること、ディープリンク。
- [ARI アーキテクチャ](architecture.md) — ダッシュボードが観測する研究システム
  （パイプライン、BFTS、チェックポイント）。
- [研究状態とガバナンス状態](research_and_governance_state.md) — ダッシュボードが
  分離しておく必要のある状態語彙。
- [REST API リファレンス](../reference/rest_api.md) — エンドポイント表。

## 全体像

```text
     #/tree2?run=R1&node=N7       ← the URL is navigation truth
               │
               ▼
  ┌──────────────────────────── browser ─────────────────────────────┐
  │  route registry (app/routeRegistry.ts)                           │
  │    · path + legacy aliases  · nav slot  · guiV2 gate             │
  │               │                                                  │
  │               ├──▶ legacy screen  (#/tree, #/results, …)         │
  │               └──▶ v2 workspace   (#/tree2, #/results2, …)       │
  │                     │   both inside the SAME shell/Layout        │
  │                     ▼                                            │
  │  server-state cache (react-query)                                │
  │  key = ['v1', <runId | projectId>, <resource>]                   │
  └────────────┬─────────────────────────────────┬───────────────────┘
    HTTP GET   │                                 │  SSE = invalidations
               ▼                                 ▼
  ┌────────────────── transport: ari/viz/routes.py ──────────────────┐
  │  same-origin CORS · CSP / nosniff / Referrer-Policy ·            │
  │  bearer auth on non-loopback binds · challenges · logs           │
  └────────────┬─────────────────────────────────┬───────────────────┘
               ▼                                 ▼
     v1/router.py (ROUTES table)             v1/events.py (bus)
               │
               ▼
     pure read modules: queries.py · results.py · rqgm.py · logs.py
     (no viz.state writes · no os.environ writes · no ari.rqgm)
               │
               ▼
     {checkpoint}/  tree.json · review_report.json ·
                    rqgm_transitions.jsonl · ear/     ← the truth
```

以下のすべては 1 つの規則の帰結です: **ディスク上のコミット済み成果物だけが
真実であり、その上のどの層も捨てて再計算できる射影にすぎない。**

## 1. ストラングラー構造: 1 つのシェル、2 世代の画面

ダッシュボードはその場で作り直されたわけではありません。レガシー画面と新しい
v2 ワークスペースは同じルーターに並んで登録され、同じ `Layout`（サイドバー、
ヘッダー、チェックポイントピッカー）の中で描画されます。新しい画面のために
何かが削除されたことはありません。

| 世代 | ハッシュルート |
|---|---|
| レガシー画面 | `#/home`、`#/experiments`、`#/monitor`、`#/tree`、`#/results`、`#/wizard`（`#/new`）、`#/idea`、`#/workflow`、`#/settings`、`#/paperbench*` |
| v2 ワークスペース | `#/projects`、`#/overview?run=`、`#/tree2?run=&node=`、`#/ideas2?run=`、`#/results2?run=`、`#/governance?run=`、`#/config?run=`、`#/studio` |

2 世代の共存を可能にしている仕組みは 3 つです:

- **並走。** v2 ワークスペースが対応するレガシー画面を編集することはありません。
  `#/tree` と `#/tree2` は同じ成果物に対する別コンポーネントであり、どちらも
  到達可能なままです。
- **ナビの引き継ぎ（`navReplaces`）。** v2 シェルが有効な間、v2 ルートは対応する
  レガシールートの*サイドバースロット*を占有できます — そのスロットのラベル、
  順序、アイコンを継承するので、サイドバーの見た目は同一で、クリックが書き込む
  ハッシュだけが変わります。レガシールートは登録されたままなので URL は動作し
  続け、ブックマークが壊れることはありません。
- **単一のキルスイッチ。** v2 シェルをオフにすると、v2 専用ルートは未知のハッシュ
  とまったく同じように Home へ解決され、サイドバーはそのエントリを隠します。
  再ビルドも再デプロイも不要です — §9 を参照。

したがってこの移行には、スケジュールすべきカットオーバーの瞬間がありません。
ワークスペースはナビスロットを与えることで昇格し、スロットを取り上げることで
ロールバックされます。

この構造が**そうではない**もの — そして最も誤読されやすい点 — は、共有された
アプリケーションサービスの上に薄いレガシー facade が乗っている、という姿です。
`ari/viz/services/` にあるモジュールは 3 つ（`state_service`、`file_service`、
`launch_service`）で、`/api/v1` がそこから呼ぶのは
`launch_service.load_dotenv_files` だけです。共有ヘルパー — チェックポイント
ディレクトリの解決、チェックポイント探索ベース、pid プローブ、バイト保存のツリー
アダプタ、`.env` チェーンの読み取り、アクセスログの書き込み — を除けば、レガシー
ハンドラと v1 read モジュールは、同じ成果物に対するおおむね 2 つの独立した実装
です。ただしレガシー側の関数がすでに単一の真実源である箇所では、v1 モジュールは
それを fork せず意図的に再利用します: `catalogs.py` はレガシーの `/api/models`
ペイロード（`checkpoint_api._api_models`）をそのまま出し、プロバイダの API キー
env 名を 1 フィールドだけ足します。`results.py` は ORS の verdict・スコア・リーフ
数を埋めるために `ear._synth_repro_report_from_ors` を read-only で呼ぶので、
2 つの Results 画面が別々の verdict を出すことはありません。`secrets.py` の書き
込みは `api_settings._upsert_env_key` を通ります。これらの再利用点こそが両者の
歩調を保っているものであり、同時にレガシー削除がほどかなければならないもの
でもあります: レガシーの `/api/models` ハンドラや `ear.py` を消すと `/api/v1` の
read モデルが壊れます（§7）。

設定が run に届く経路も 2 本あります: レガシーの Settings 保存＋起動チェーンは
選ばれたキーを起動する CLI 向けの環境変数へ写し、`/api/v1` の設定エンドポイントは正準リゾルバ
を通ります。両者はすべてで一致するわけではなく、その差分は
[設定](../reference/configuration.md) の dead / env-only な Settings キーとして
列挙されています。

つまり両者の一致は、構造ではなくテストによって保たれています。
`ari-core/tests/test_gui_config_shadow_legacy.py` はレガシー起動の実効設定と正準
リゾルバの結果をリーフ単位で差分し、明示的な allowlist に載っている行だけ乖離を
許します — 載っている行が黙って乖離しなくなった場合も同様に失敗します。
`ari-core/tests/test_gui_state_facade_freeze.py` は凍結された `/state` ペイロード
のトップレベルキー集合を厳密に固定し、追加も削除も拒否します。挙動を変える人に
とっての実務的な帰結は: 変更は 2 回必要だと見込むこと、そして 1 回しか変えなかっ
たことを教えてくれるのがこの 2 つのスイートだ、ということです。

## 2. ルートが存在する場所はルートレジストリだけ

`app/routeRegistry.ts` は 1 つの `ROUTE_REGISTRY` 配列を保持します。各エントリは
ルートの `id`、ハッシュ `path`、遅延 `load` サンク、任意のナビメタデータ
（`navLabelKey`、`navOrder`、`navIcon`、`navPath`）、`legacyAliases`、そして移行
マーカー `guiV2` / `navReplaces` を持ちます。

2 つの消費側はいずれも手で保守されるのではなく*導出*されます:

- `App.tsx` は遅延コンポーネントマップとディスパッチをレジストリから構築します
  （`resolveRoute` は `#/` 接頭辞とクエリ文字列を剥がし、空ハッシュを `home` と
  みなし、`new` → `wizard` のようなレガシーエイリアスを適用します）。
- `Sidebar.tsx` は `navItems()` からナビ表を構築し、`navReplaces` エントリを
  ターゲットのスロットへ実体化して `navOrder` でソートします。サイドバーは
  さらにウィザードのエントリをプライマリアクションとして抜き出し、残りを
  4 つの固定グループ（portfolio / research / quality / system）に並べます。

2 つの凍結リテラルテストが結果をピン留めしているため、ナビには存在するのに
ルーターには存在しない（またはその逆の）ルートへドリフトすることはできません。
ここから落ちてくる実務規則:

- **ハッシュ URL はデプロイ契約です。** ユーザーがブックマークし、ドキュメントが
  引用するものなので、レジストリは歴史的な綴りを整理せず保存します（ウィザードは
  今も `#/new` へ遷移します）。
- **到達可能だが非掲載、を表現できます。** `#/paperbench/import|run|results` は
  ナビエントリを持たないルートとして存在し、ページ内部から開かれます。
- **未知のハッシュはエラーではなく Home へフォールバックします。** この
  フォールバックは、一方では設計上不可欠で、他方では既知の欠陥です。キル
  スイッチにとっては意図的です: v2 シェルをオフにしたとき、v2 専用ルートは
  未知のハッシュとまったく同じように解決されなければ、レガシーの面が欠けて
  しまいます（*capability とキルスイッチ*の節を参照）。一方、単なる打ち間違い
  にとっては欠陥です — 利用者は説明のないまま Home に着き、「このルートは存在
  しません」という明示的な解決画面は今も未着手です（`App.tsx` に `TODO` として
  記されています）。*run が無い*場合のほうは既に意図どおりです: `?run=` 無しで
  開かれた v2 ワークスペースは、グローバルな選択を黙って採用せず、明示的な
  プロンプトを表示します。

**レジストリが持たないもの。** `RouteDefinition` は誰も読まないフィールドを
2 つ宣言しています: `breadcrumbKey` と `requiredContext`。ダッシュボードの
どこにもパンくずコンポーネントは無く、ルートレベルの必須コンテキストガードも
ありません — 代わりに各 v2 ワークスペースが自前の「run が選ばれていません」
プロンプトを出します。GUI 刷新が定めたシェルの面のうち 2 つも同様に未実装
です: コマンドパレットも通知センターも存在しないため、ランやガバナンスの警告は
それを描画するページ上でしか見えません。ルートは権限述語も持たず、サーバーに
ユーザーモデルが無い限り必要にもなりません — bearer トークンは全か無かであり、
セッションとマルチユーザーは対象外です。capability によるゲートはマーカー
1 つだけです: レジストリエントリの `guiV2` と、`App.tsx` の `V2_ONLY_ROUTES`
ディスパッチ集合。

**エラーバウンダリはルートに 1 つだけ。** ダッシュボードの React エラー
バウンダリは `main.tsx` の 1 つだけで、ルーターの外、`Layout` の外にあります。
ルート内部の描画失敗は — `App.tsx` の `Suspense` がフォールバックは供給する
もののバウンダリは供給しないため、遅延チャンクのロード失敗も含めて —
サイドバーごとシェル全体を「ARI Dashboard Error」画面に置き換えます。スタックが
出るのは開発者モードのときだけで、復旧手段はページの再読み込みだけです。
リトライアクションを備えたルート単位のバウンダリは仕様にはありましたが未実装
であり、チャンクのロード失敗に対するテストもありません。

## 3. URL がナビゲーションの真実

ダッシュボードはハッシュルーターであり、*選択*はハッシュのクエリ文字列に住みます:
`#/overview?run=<run_id>`、`#/tree2?run=<run_id>&node=<node_id>`。ルートの
ディスパッチはクエリ文字列を無視するので、各 v2 ワークスペースが自分の
パラメータを所有します — マウント時に読み、`hashchange` で読み直し、選択の変更を
ハッシュへ書き戻します。

概念的に重要な理由: ワークスペースの描画内容はその URL だけの関数である、という
ことです。これによりあらゆるビューがリロード可能・ブックマーク可能・共有可能に
なります — 「ラン R1 のノード N7 を見て」はクリック手順ではなくリンクです。

レガシー経路がこの規則の動機となる対比です。レガシー Experiments の行から
レガシー Results ページへ至る経路は今も*暗黙の*受け渡し（`sessionStorage` の
キー + 裸の `#/results` ハッシュ）を通り、レガシーシェルはさらにプロセス全体の
*アクティブチェックポイント*を持ちます。どちらも v2 ワークスペースの妥当な入力
ではありません: v2 ルートは run を明示するからこそ、2 つのタブで 2 つのランを
開いても互いを踏まないのです — v2 の行は代わりに `#/results?run=<run_id>` へ
リンクし、Results ページはそのパラメータを権威として扱い、`sessionStorage` の
キーは古い呼び出し元向けのフォールバックとしてのみ残しています。

このキーには固定しておく価値のある名前があります。ページ内の私的なストレージ
ではなく、ページ間の契約だからです: `ari_selected_checkpoint`。レガシー
Experiments の行は `#/results` へ遷移する前にこれを書き、v2 の Projects の行も
明示的な `#/results?run=<run_id>` リンクと併せて今なおこれを書きます。Results
ページは、ハッシュに `?run=` が無いときに*だけ*これを読み、いずれの場合も
読み終えたら消します。もう 1 つのキー `ari_tree_nodes` は、レガシー
Experiments ページが `#/tree` へ遷移する前に書きますが、どこからも読まれません
— Tree ページはノードを共有のレガシーコンテキストから取るからです。これは死んだ
状態であり、この書き込みの削除は挙動の変更ではなくレガシーページ削除の一部です。

## 4. サーバー状態はランをキーとするキャッシュに住む

`/api/v1` のすべての読み取りは 1 つの react-query クライアントを通ります。クエリ
キーの形は `['v1', <projectId | runId>, <resource>]` — 識別子はキーの*内側*に
あります。

この 1 つの決定が 3 つの性質を買います:

- **2 つのランが混ざることは決してありません。** ラン単位のエントリは別々の
  キャッシュエントリなので、ランを切り替えても前のランのデータが現在のビューへ
  滲むことはありません。
- **無効化の粒度がちょうど正しくなります。** `['v1', runId]` を落とせば 1 ランの
  サーバー状態だけが落ちます; リソースに属するフィルタ（監査ログのレコード種別、
  エポック）もキーに入るので、それを変えると陳腐化したページ連鎖へ追記するのでは
  なく新しいページ連鎖が始まります。
- **鮮度ポリシーが 1 箇所に集まります。** クライアントの既定は `staleTime`
  5000 ms（従来のポーリング周期に合わせてあるので、その窓の内側での再マウントは
  キャッシュを返します）、リトライ 1 回、ウィンドウフォーカス時の再取得なし —
  ローカルダッシュボードがフォーカスのばたつきをチェックポイントスキャナへの
  リクエスト嵐に変えてはなりません。この 1 つの既定値が*ポリシーのすべて*でも
  あります: これを上書きするクエリは 1 つも無いので、ほぼ静的なスキーマ読み取りも
  生きたツリーとまったく同じに扱われ、鮮度バナーはリソースごとの経過時間では
  なく最後のスナップショット時刻を報告します。エンティティごとの stale time と
  エンティティごとの鮮度ラベルは刷新 GUI の仕様にはありましたが未実装です。

クライアント専用の状態（どのタブが開いているか、フィルタ欄のテキスト、サイドバー
幅）はこのキャッシュに*入りません*。分担はこうです: サーバー状態はキャッシュされ
無効化され、ビュー状態はローカルで刹那的、ナビゲーション状態は URL にある（§3）。

**mutation は決して optimistic ではありません。** 予測した結果をキャッシュへ
書き込む画面はありません。書き込みを送り、サーバーの答え — 新しい `revision`
か `409 revision_conflict` — を UI が採用し、該当するクエリキーを無効化するので、
次の描画は再取得したスナップショットから来ます。だからこそ競合した保存は黙って
勝つのではなく明示的な再読み込みの導線を出し、未保存の編集をローカルに保ちます。
そして、サーバーが受理していない状態が画面上に現れることはありません。

**`AppContext` はレガシー専用スコープです。** これはレガシー画面だけの
リモートデータストアであり — 5 秒ごとの `/state` ポーリング、ツリー WebSocket の
ミラー、プロセス全体のアクティブチェックポイント — v2 ワークスペースはこれを
import してはなりません: v2 は `useV1` フック経由で `/api/v1` を読み、run は
`?run=` から取ります。この規則はレビューではなく構造で強制されています —
`src/__tests__/` にあるソーススキャンが v2 コンポーネントディレクトリ配下の
非テストファイルをすべて読み込み、`AppContext` の import 指定子があれば失敗
します。ピン留めされた例外はちょうど 1 つ、IdeasV2 の研究ゴールカードで、
run 同一性チェックの後ろで `/state` からゴールを読みます（ゴールを返す
run スコープの v1 エンドポイントがまだ無いため）。この例外リストを縮めるのは
歓迎ですが、増やすのは退行です。v2 画面が依存している限り `AppContext` は
削除できないからです。

**永続的な設定にストアはありません。** ロケール（`ari_lang`、既定 `ja`）、
開発者モード（`ari_dev_mode`）、リモート用 bearer トークン（`ari_gui_token`）は、
いずれも直接 `localStorage` を触りますが、それぞれ 1 キー専用のアクセサ
（`i18n.storedLang()`、`useDevMode.isDevMode()`、`client.getGuiToken()`）の背後に
あります。Settings ページは今も `ari_lang` を自分で `localStorage` から読みます。
3 つをまとめる preference store の抽象も、これらのキーのスキーマも、マイグレー
ション経路もありません。したがって名前や型の変更はキーごとの編集になり、1 か所で
済ませる場所はありません。刷新されたシェルの仕様には preference 層がありましたが
未実装です。この 3 つのキー名を実際の契約とみなしてください。

## 5. エンティティモデルは 1 階層しかない

v1 のサーフェスは `project → run` の階層のかたちをしていますが、実在するのは
下の階層だけです。`GET /api/v1/projects` はちょうど 1 つのプロジェクト —
仮想の `default` — だけを返します。その `checkpoint_roots` は実在する
チェックポイント探索ベースであり、ラン一覧はそれら全体にまたがるチェックポイント
ディレクトリの走査（名前フィルタとスキップ集合はレガシーの一覧と同じ）です。
`GET /api/v1/projects/{project_id}/runs` は `default` 以外の id に対して型付きの
`404` を返し、Projects ワークスペースはそれ以上探さずに `projects[0]` を読みます。

設計時に前提としてはならない帰結が 3 つあります:

- **プロジェクトのライフサイクルは存在しません。** `ROUTES` テーブルに
  プロジェクトの作成・改名・削除はありません。プロジェクトを対象とする
  エンドポイントは他に `/api/v1/projects/{project_id}/config` の `GET` /
  `PATCH` があるだけで、どちらも `default` 以外の id を拒否します。読み書き
  されるのは単一のドキュメント `gui_store/project_config.json` です。
- **ランはプロジェクト単位に区切られていません。** ラン単位のエンドポイントは
  すべて `/api/v1/runs/{run_id}/…` でプロジェクトのセグメントを持たないため、URL や
  キャッシュキー（§4）に現れる `project_id` は何も絞り込みません。`default` は
  これらの形を安定させる固定のプレースホルダとして読むべきであり、ランどうしが
  隔離されている証拠として読んではなりません。
- **ラン*は*チェックポイントです。** `run_id` は文字どおりチェックポイント
  ディレクトリ名（`YYYYMMDDHHMMSS_<slug>`）です。チェックポイントは 1 つのランが
  複数持てる保存点としてはモデル化されておらず、ラン間の系譜を表す v1 の
  エンドポイントも DTO もありません — `meta.json` は `parent_run_id` を記録
  しますが、`/api/v1` 配下でそれを読むものはありません。

フィールドレジストリはプロジェクトより*上*の階層も名前だけ持っています。その
`scope` 語彙は `preference` / `installation` / `project` / `template` / `run`
（[設定](../reference/configuration.md) を参照）ですが、5 つのうち実際に
割り当てられるのは 3 つだけです: 現在レジストリが構築するリーフは、単一の
`installation` リーフ `llm.api_key` を除いてすべて `run` か `project` です。
しかもそのリーフは `secret_reference` なので、値は `/api/v1/secrets/*` の背後に
ある `.env` チェーンに住み、GUI ドキュメントには決して入りません。そもそも
ドキュメントストアには preference も installation も置き場所がありません:
保持するのは `project_config.json`、`run_templates/`、`run_drafts/`、
`launches/` だけです（§7）。

実在するプロジェクト（再利用可能な設定の境界）と、ラン（ライフサイクルの境界）と、
チェックポイント（保存点の境界）を分離することは、予約された設計であって実装では
ありません。ツリーの中にそれを実装したものはないので、すでにあるかのように
クライアントを書いてはなりません。

## 6. リアルタイムは無効化であって真実源ではない

`GET /api/v1/events/stream` はサーバー側で `run_id` / トピックをフィルタする
Server-Sent Events ストリームです。イベントは小さな通知
（`{event_id, run_id, topic, revision, occurred_at, kind, resource, payload}`）
であり、消費側の唯一の反応は一致するキャッシュキーを無効化して HTTP スナップ
ショットを再取得することです。

イベント*から*描画されるものは一切ありません。この設計の理由はその帰結にあります:

- **重複と順序入れ替えは無害です。** 何が真かを決めるのはスナップショット
  エンドポイントであり、イベントは*いつ聞き直すか*を決めるだけです。
- **ストリームの切断は鮮度の問題であって、状態変化では決してありません。**
  最後のスナップショットが陳腐化バナー付きで画面に残ります。切断が「ランが
  停止した」として提示されることはありません。
- **再接続は安価で有界です。** 指数バックオフ（1 秒 → 上限 30 秒）と
  `Last-Event-ID` カーソル; エラーが 1 分を超えて続くと接続は `offline` へ
  移り、これがサブスクリプション自身のスコープに対する有界な 10 秒ポーリング
  フォールバックを有効にする*唯一の*状態です。
- **バスは小さく保たれます。** イベントは固定上限を持つ追記専用のインメモリ
  リングバッファに住み、ハートビートコメントと有界なストリーム窓により、
  アイドルなプロキシや固まったクライアントがワーカーを永久に占有できないように
  なっています。

イベントは自身の `run_id` を持つので、ラン B のイベントがラン A のキャッシュ
エントリに触れることはありません — §4 と同じ隔離性が、キャッシュの書き込み側でも
強制されています。

**所有者は 1 つ、正直な例外が 2 つ。** `/api/v1` 上のリアルタイムの所有者は
ちょうど 1 つ、`shared/realtime/eventStream.ts` です。ページは
`subscribe(runId, topics, callbacks)` を — 通常は `useRunEvents` フック経由で —
呼ぶだけで、自分で `EventSource` を組み立てることはありません。だからバック
オフのスケジュール、`last_event_id` カーソル、3 状態の接続マシン、オフライン時の
ポーリング刻みは 1 箇所にだけ存在し、1 度だけテストされます。この所有権の外に
あり、かつそれ以前から存在するチャネルが 2 つあります: HTTP ポート + 1 の
レガシーツリー WebSocket と、ジョブ実行中に PaperBench のログストリームへ自前の
`EventSource` を開く PaperBench ジョブログビューアです。どちらも真似すべき
パターンではなく、削除の候補です。

**購読はマウントされたルートとその run に従います。** ページは自分の生存期間
だけ購読し、`run_id` / `topics` のフィルタはサーバー側で行われるので、ページが
描画しないイベントの代金を払うことはありません。ただし隠れたタブを絞る仕組みは
ありません: クライアントは `visibilitychange` を購読していないため、背面に回った
タブもストリームを開いたままバックオフで再接続を続け、10 秒のオフライン
ポーリングを刻み続けます。バックグラウンドタブの負荷制御は仕様にはありましたが
未実装であり、古いタブが複数あればそれぞれがストリームを 1 本ずつ保持します。

## 7. バックエンドのシーム

サーバーは 4 層であり、各層は 1 つ下の層についてだけ知ることが許されます。

このシームの下に Web フレームワークはありません。転送は Python 標準ライブラリ
です: `server.py` はホストごとに `ThreadingHTTPServer` を 1 つずつバインドし
（ループバック既定は両方のファミリを要求し、片方が使えなくても許容します。
2 つ目以降のサーバーはデーモンスレッド上で `serve_forever()` を回します）、
リクエストは `routes.py` にある唯一の `BaseHTTPRequestHandler` サブクラスが
処理します。旧来の面はリクエストパスに対する明示的な `if`/`elif` の連鎖で
ディスパッチされ、`/api/v1/` 配下は
宣言的な `ROUTES` テーブルへ委譲されます（`/api/v1/events/stream` だけは 1 つ
手前の分岐で捕まえます。ディスパッチャは dict を返すのに対し、SSE は長命な
ストリームを書き続ける必要があるためです）。asyncio なのはツリー WebSocket
だけです: `_main` が唯一の asyncio エントリポイントであり、ウォッチャと HTTP
サーバーをデーモンスレッドで起動したあとは、HTTP ポート + 1 の `websockets`
サーバー以外は何もホストしません。ここから 2 つの帰結が本節全体に効いてきます。
API 層がルーティングもエラーエンベロープも OpenAPI 生成も自前で持つのは、
継承元となるフレームワークが存在しないからです — 設定するのではなく、ここで
作られています。そして 1 本の接続は開いている間ずっとワーカースレッドを 1 つ
占有します: ハンドラが `protocol_version = "HTTP/1.1"` を設定するのは、短い
ポーリングが 1 本の接続を再利用してブラウザのオリジンあたりの接続プールを
枯渇させないためであり、一方で長命なストリーミング系エンドポイントは
`Connection: close` を返して keep-alive のスロットに居座らないようにします。
したがってハンドラ内でブロックする処理のコストは、コルーチンではなく
スレッドです。

| 層 | モジュール | 責務 |
|---|---|---|
| 転送 | `ari/viz/routes.py`（+ `auth.py`、`server.py`、`health.py`） | ソケットレベルのポリシー: same-origin CORS のエコー、SPA / 静的レスポンスへの `Content-Security-Policy` / `nosniff` / `Referrer-Policy`、非ループバックバインド時の bearer トークン認証、アクセスログ、`/health/live` と `/health/ready`。 |
| API | `ari/viz/v1/router.py` | `(method, path template, handler)` の宣言的な `ROUTES` テーブル 1 枚。ディスパッチごとに `request_id` を発行し、成功ペイロードまたは型付きエラーエンベロープへ通します; `PATCH`/`DELETE` で `If-Match` の楽観的並行制御を強制します; 同じテーブルがコミット済みの `openapi.json` を生成するため、契約がディスパッチャからドリフトすることはありません。 |
| 読み取りモデル | `queries.py`、`results.py`、`rqgm.py`、`logs.py`、`catalogs.py` | チェックポイントディレクトリから DTO への純粋関数。`viz.state` の変更なし、`os.environ` への書き込みなし、ファイル書き込みなし — GET に副作用はありません。 |
| 真実 | `{checkpoint}/…`、および GUI 専用文書のための `{workspace_root}/gui_store/` | コミット済み成果物。 |

このシームの 2 つの性質は侵食されやすいので明示しておく価値があります:

- **`GET` は副作用フリーです。** 読み取りモジュールは、読まれた副作用として状態を
  変更する旧ハンドラのようにサーバーのプロセス追跡状態を参照・剪定するのではなく、
  意図的にファイルシステムからラン状態を再導出します（pid プローブ → ツリーによる
  精緻化 → レビューレポート）。
- **書き込みは狭く明示的です。** GUI 自身の文書 — プロジェクト既定値、ラン
  テンプレート、ランドラフト、起動の冪等性レコード — はグローバルなホーム
  ディレクトリではなく `{workspace_root}/gui_store/` に住み、アトミック書き込みと、
  `ETag` / `If-Match` へ 1:1 対応する整数 `revision` を持ちます。これらは便宜層
  です: 起動時にすべての実効値がチェックポイントへ実体化されるため、CLI がランを
  再現するために `gui_store/` を読む必要は決してありません。

**このシームのブラウザ側には、意図的に統一されていない 3 つの転送レジームが
あります。** `services/api/client.ts` は 3 組のラッパーを公開していて、どの組を
使うかは契約の一部です。6 つのうち 5 つは 1 つの `request` プリミティブを共有
しますが、6 つ目の `v1Send` は意図的に自前の `RequestInit` を組み立てます —
このプリミティブのオプション形状自体が凍結されたレガシーのワイヤ契約の一部
なので、v1 のミューテーション転送は `If-Match` ヘッダも含めて `request` の中では
なく隣に置かれています:

- `get` / `post` は、2xx 以外なら
  `Error('<METHOD> <path> failed: <status>')` を throw します。レガシーの
  `useApi` フックとその呼び出し元は、この throw に依存しています。
- `pbGet` / `pbPost` は決して throw しません。PaperBench のハンドラは HTTP 200 と
  `{error: …}` ボディで答えるので、アプリケーションエラーはボディで届き、
  呼び出し元がその場で扱います。
- `v1Get` / `v1Send` はステータスにかかわらずパース済みボディで resolve します。
  `/api/v1` は本物の 2xx 以外のステータスを返し、そのボディ*こそ*が型付き
  エラーエンベロープだからです — throw するクライアントは、UI が必要とする
  ペイロードをまさに捨ててしまいます。そのうえで `services/api/v1.ts` が
  あらゆる失敗（型付きエンベロープ、ネットワークエラー、パースできないボディ）を
  1 つの throw される `ApiErrorV1`
  `{code, message, details, request_id, retryable}` へ正規化します。

この非対称性は整理されずに保存されています: 最初の 2 つのレジームは挙動を凍結する
テストでピン留めされており、統一すればレガシーの呼び出し元すべてが見るものを
黙って変えてしまいます。新しいコードは `/api/v1` のレジームを使ってください。

このクライアントには、無いこと自体をポリシーと取り違えやすい欠落が 2 つあります:

- **クライアント側の abort も timeout もありません。** 共有の `request`
  プリミティブも `v1Send` も `AbortSignal` を渡さず、期限も設定しません。
  したがって固まったリクエストはブラウザが諦めるまで固まったままで、ページを
  離れても実行中の fetch はキャンセルされません。リトライ方針は react-query の既定（1 回）に、
  エラーエンベロープ上のサーバー申告 `retryable` フラグを加えたものですが、後者は
  呼び出し元が参照できるだけで自動的に消費するものはありません。冪等性はメソッド
  メタデータではなくエンドポイント単位です: `idempotency_key` を持つのはラン起動
  だけで、レビュー承認ごとに 1 つ発行されるため、ダブルクリックやリトライは
  2 本目のランを産まず同じランを再生します。メソッド単位の
  abort / timeout / retry / 冪等性メタデータは仕様にはありましたが未実装です。
- **スキーマのドリフトはビルド時に捕まえ、実行時には捕まえません。** 生成 DTO
  モジュール `services/api/v1types.gen.ts` は `ari/viz/v1/openapi.json` から
  生成され、ドリフト検査テストがバイト単位で比較するので、再生成を忘れた契約変更は
  CI で落ち、出荷されません。実行時には互換性チェックがありません: 生成 DTO と
  一致しないレスポンスは検出されず、そもそもパースできないボディは
  `code: 'internal'` / `retryable: true` へ正規化されるため、転送の一時的な不調と
  区別がつきません。「このバンドルはこのサーバーと一致しません」という専用の互換性
  エラーは仕様にはありましたが未実装なので、バンドルとサーバーの不一致は普通の
  internal エラーとして、あるいはフィールド欠落による空白として現れます。

## 8. 読み取りモデルは使い捨ての射影

*読み取りモデル*とは、コミット済み成果物から要求時に計算される有界な射影です。
読み取りモデルをすべて削除しても情報は失われませんが、成果物を削除すればそれは
失われます。この非対称性こそが要点です。

ガバナンス読み取りモデルは最も厳格な実例であり、「射影」が実務上何を意味するかを
示します:

- **どの判断も再実行しません。** `ari/viz/v1/rqgm.py` は `ari.rqgm` を決して
  インポートしません。コミット済み成果物（`rqgm_state.json`、
  `rqgm_transitions.jsonl`、`rqgm_audit.jsonl`、`rqgm_registry.json`、ノード
  メトリクスのセンチネル…）をパースし、それらが言っていることを報告します。GUI が
  ガバナンスの評決を捏造できないのは、評決を生むカーネルを一度も実行しないから
  です。
- **コミット済みレコードのみ。** 現在状態は*コミット済み*遷移の replay です。
  途切れた末尾の JSONL 行は無視され、対応する commit を持たない prepare 以降の
  イベントは決して採用されません。rollup スナップショットは、replay と一致するか
  検証するためだけに読まれます。
- **壊れるのではなく縮退する。** 成果物が壊れていても存在しなくても HTTP 200 と
  正直なフラグを返します: 整合性は三値（`true` 検証済み / `false` 破損 / `null`
  ソース不在）で、`degraded_reasons` リストがペイロードに同行します。存在しない
  ソースがクリーンとして描画されることも、ゼロとして描画されることもありません。
- **構造上有界です。** 要約は埋め込みエントリ一覧ではなく件数を持ち、長いログは
  安定オフセット上のカーソルでページングされ、ファイルの*中身*がこれらの
  エンドポイントに乗ることはありません。

ダッシュボードを拡張する人への運用規則はこうです: GUI の表示を変えたいなら射影を
変えること — 成果物を変えてはならず、カーネルが既にコミットした判断を再計算しても
なりません。

## 9. capability とキルスイッチ

ダッシュボードは「これは利用できません」を 2 種類に区別し、どちらもエラーでは
ありません。

**サーバー capability — このビルドが提供するもの。** `GET /api/capabilities` が
`gui_v2` フラグ（`ARI_GUI_V2`、既定オン）を報告します。フロントエンドはマウント時
に一度取得し、取得の*失敗*をオンとして扱うため、API の一時的な不調でローカル
ユーザーがフォールバックシェルに取り残されることはありません。

**ラン capability — このランの成果物が支えるもの。** 成果物の存在のみから検出
されます: `rqgm_state.json` があるからランはガバナンス下であり、
`paper_archive_state.json` があるからアーカイブ論文モードです（両者は独立した軸）。
ガバナンスの無いランには、空画面や捏造されたゼロではなく、理由を挙げた
「このランではガバナンスが有効でない — これは capability の状態であってエラーでは
ない」というパネルが表示されます。

刷新された GUI で導入されたリスクのある挙動にはすべて環境変数のキルスイッチが
付属しており、リリースを巻き戻さずに 1 つの決定だけを戻せます。すべて
`scripts/setup/setup_env.sh` に文書化されています:

| 変数 | 既定 | オフにすると戻るもの |
|---|---|---|
| `ARI_GUI_V2` | オン | レガシーシェルのみ（v2 専用ルートは Home へフォールバック） |
| `ARI_GUI_BIND` | ループバック（`127.0.0.1` + `::1`） | より広いバインド。例: 全インタフェースの `::` |
| `ARI_GUI_TOKEN` / `ARI_GUI_AUTH` | 非ループバックバインドでは認証を強制 | 未認証のリモートバインド（例: 認証を行うプロキシの背後） |
| `ARI_GUI_CORS_ANY` | オフ（same-origin エコー） | レガシーの `Access-Control-Allow-Origin: *` ワイルドカード |
| `ARI_GUI_CSP` | オン | CSP / nosniff / Referrer-Policy ヘッダの無いレスポンス |
| `ARI_GUI_CHALLENGES` | オン | 確認チャレンジ無しの直接的な破壊的エンドポイント |
| `ARI_GUI_HEALTH` | オン | ヘルスプローブ導入前のレスポンス（diagnostics エンドポイント無し） |

これらのスイッチが守るセキュリティ既定値は一度述べておく価値があります: サーバー
はループバックのみにバインドするので、既定のローカル体験に認証は不要です; 非
ループバックバインドは bearer トークンを要求することで*フェイルセキュア*します
（未設定なら起動時に生成され一度だけ表示されます）; そして 3 つの破壊的操作
（チェックポイント削除、停止、GPU モニタ停止）はサーバー発行の単回使用確認
チャレンジを要求し、無い場合は `428` を返します。

## 10. フロントエンドのコードが置かれる場所

フロントエンドは*画面*単位でグループ化されており、その上にある合成層は
ルートレジストリだけです。`ari-core/ari/viz/frontend/src/` の下は次のとおりです:

| ディレクトリ | 置かれるもの |
|---|---|
| `app/` | どの画面も所有しないシェル配線: ルートレジストリ（§2）と react-query クライアント（§4）。 |
| `components/<Screen>/` | 画面ごとに 1 ディレクトリ。レガシーと v2 が並んで置かれ（`Tree/` と `TreeV2/`、`Results/` と `ResultsV2/`）、それぞれがレジストリの遅延ロード対象のページコンポーネントを export します。加えて表示用プリミティブの `common/` と、サイドバー・ヘッダーの `Layout/`。 |
| `context/` | レガシーの `AppContext` — `/state` ポーリングとプロセス全体のアクティブチェックポイント。 |
| `hooks/` | 画面横断のフック: `useV1`、`useRunEvents`、`useApi`、`useWebSocket`、`useDevMode`。 |
| `services/api/` | 1 つのトランスポートコア（`client.ts`）と、エンドポイントファミリごとの 1 モジュール。`services/api.ts` のバレルが再 export するので、古い import パスもそのまま解決します。 |
| `shared/` | 横断的なプラットフォームコード — 現時点では SSE クライアントである `realtime/` のみ。 |
| `i18n/`、`styles/`、`types/` | 3 言語の文字列表、CSS のトークン／レイアウトシート、共有 DTO 型。 |
| `__tests__/` | どの画面も所有しないアプリ全体のガードスイート: ルート↔ナビのパリティ、App 全体のルート描画、シェルの a11y、開発者モードのゲーティング、生成型のドリフト。 |

`pages/` 層はありません。レジストリエントリの `load` サンクが画面コンポーネント
を直接 import するので、ルートの合成*そのもの*がレジストリエントリです。

**feature / entity への分割は仕様化されましたが、作られていません。** GUI 刷新は
さらに `features/` と `entities/` へ分けること、そして feature は他の feature の
internal module を import せず、entity / shared の contract、あるいはそれらを
合成する page を介すること、を求めていました。そのどれも存在しません: `features/`、`entities/`、`pages/` の各
ディレクトリは無く、再利用のほうが安いところではツリーが既に画面境界を跨いで
います — `ConfigStudio` は `ConfigBrowser` の読み取り専用 config テーブルを
（2 つの config 面がドリフトしないよう意図的に）import し、`Monitor` と `TreeV2`
はどちらもレガシーの `Tree` ビジュアライゼーションを import しています。

レイヤ境界を強制する仕組みもありません。フロントエンドの `package.json` には
lint ステップも lint 依存も無いので、ツリーにある唯一の構造的 import ガードは
テストです — `src/__tests__/appContextScope.test.ts` が v2 画面ディレクトリ配下の
非テストファイルをすべて走査して `AppContext` の import 指定子を探し、ピン留め
された 1 つの例外を超えるものがあれば失敗します。このガードが守るのはレガシー
削除ゲートであって feature / entity 境界ではなく、画面間の import を制約する
走査はいっさい存在しません。

この分割は、ツリーが従っている構造ではなく進むべき方向として読んでください。
今日実際に守られているのはもっと浅い配置規則です: 表示用プリミティブは
`components/common/`、横断的なプラットフォームコードは `shared/`、シェル配線は
`app/`、そして画面ディレクトリが所有するのは自分の画面だけ、というものです。
