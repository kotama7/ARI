# 研究状態とガバナンス状態

ARI のランは任意の時点で複数の状態を持ち、それぞれ別の問いに答えます。
「このランはまだ実行中である」「このランは論文段階に到達した」「このランの
ガバナンス記録は縮退している」「このノードのスコアはもう数えられない」——
これらは 4 つの独立した事実です。どの 2 つを混同しても、ARI が裏づけられない
主張ができあがります。

このページはそれらの区別が住む概念的な場所です。ダッシュボードの真実規則 —
ラベル、行を分けること、1 本の連続したスコア線を引くのを拒むこと — はここから
導出されており、チェックポイントを手で読む人にも等しく当てはまります。

関連ページ: UI でこれらの規則がどう強制されるかは
[ダッシュボードアーキテクチャ](gui_architecture.md)、ガバナンス成果物を
生成するカーネルについては
[Constitutional ARI-RQGM アーキテクチャ](rqgm_architecture.md)。

---

## 1. 状態機械は 1 つではなく 4 つ

| 状態機械 | 答える問い | スコープ | 存在する範囲 |
|---|---|---|---|
| ランライフサイクル | このランは今実行中か？ | 1 ラン | すべてのラン |
| 研究フェーズ | 研究パイプラインのどこまで進んだか？ | 1 ラン | すべてのラン |
| ガバナンス段階 | どのガバナンス下エポックとスコアポリシーが有効か？ | 1 ラン | `ari_rqgm` ランのみ |
| ノードスコア状態 | このノードのスコアはまだ有効か、どのポリシーの下でか？ | 1 ノード | `ari_rqgm` ランのみ |

これらは別々の理由で、別々のタイミングで進み、どれも他を含意しません。ランは
フェーズ未設定のまま `running` でありうるし、ガバナンス記録が縮退したまま
`completed` でありうるし、ガバナンスが健全なまま特定の 1 ノードのスコアだけが
無効化されていることもあります。

---

## 2. ランライフサイクルと研究フェーズ

いずれもコミット済み成果物から読み取り専用で導出されます — ダッシュボードが
ライフサイクルやフェーズを*記録*することはありません。

**ランライフサイクル**はチェックポイントディレクトリごとに導出されます:
そのランの生きたプロセスがあれば `running`; そうでなければノードツリーが決めます
— 生きたプロセスが無いのにツリーがまだ `running` と言っていれば孤児化した
`stopped`、それ以外で内容のあるツリーは `completed`、`review_report.json` の
存在も `completed` と読まれます。判断材料が何も無ければ、正直な答えは
`unknown` です。ただし、これら全てに優先する層が 1 つあります: 永続化された
ビルドロックと run-integrity 成果物から導かれる終端判定が最後に適用されます。
レビューが存在していてもその後に公開がブロックされることはあり得ますし、
strict な claim gate はビルドロックが作られる前にパイプラインを止め得るからです。

| 値 | 意味 |
|---|---|
| `running` | このランの生きたプロセスが見つかった |
| `stopped` | ツリーはノードが実行中と言うが、プロセスが生きていない（孤児化） |
| `completed` | 実行中ノードの無い内容のあるツリー、またはレビューレポートが存在する |
| `blocked` | 論文ビルドロックが公開ブロックを報告している — 上の層を上書きする終端判定 |
| `failed` | ビルドがコンパイルに失敗した／読めない、または終端の run-integrity 判定が失敗した |
| `unknown` | 証拠が足りない — 意図的に「completed」へ既定させない |

**研究フェーズ**は成果物の存在からの別の導出です: レビューレポートがあれば
`review`; 論文（または開始済みパイプライン）があれば `paper`; アイデア成果物が
あれば `bfts`; まだ何も無ければフェーズ自体がありません。UI が描画する凍結
フェーズ語彙は `idle`、`starting`、`bfts`、`paper`、`review` で、「まだフェーズ
が導出されていない」は `idle` として表示されます。

両者は意図的に直交です。`stopped` + `paper` は完全に整合的な状態であり
（論文執筆後にパイプラインが中断された）、`running` + `idle` も同様です
（ランが始まったばかりでディスク上にまだ何も無い）。

## 3. ガバナンス段階は別のタイムライン

`ari_rqgm` 実行モードで実行されたランには*ガバナンス段階*も存在します:
現在開いているエポックと有効な utility ポリシーハッシュで、コミット済み
ガバナンス遷移の replay から読まれます。

これが別の状態機械であることから従う規則:

- **独立したラベル付きの行として描画され**、研究フェーズに統合されることは
  ありません。ランのフェーズはそのエポックについて何も語らず、エポックは
  フェーズについて何も語りません。
- **`simple_bfts` ランには存在しません。** ここでの不在は capability の状態 —
  理由付きの「このランではガバナンスが有効でない」— であり、エラーでもゼロでも
  ありません。
- **ガバナンス受理 ≠ 研究完了。** ガバナンス遷移が成功裏にコミットされたことは、
  制度が自らの規則に従ったことを意味します。科学が上手くいったかどうかについては
  何も主張しません。
- **実行モードと論文モードは独立した軸です。** ランはガバナンス下かどうか
  （`ari.mode`）とは別に、アーカイブ論文フローか linear かを使います;
  4 通りの組み合わせすべてが有効です。

### 「ガバナンスがブロックされている」が意味**しない**こと

ガバナンス読み取りモデルが縮退理由や失敗した整合性チェーン（遷移チェーン、
レジストリスナップショット、監査チェーン — それぞれ三値: 検証済み / 破損 /
ソース不在）を報告したとき、ダッシュボードはガバナンスのブロッカーを提示します。
これは最も誤読されやすいシグナルの 1 つなので、はっきり述べます。

ガバナンスブロッカーが意味するのは: **ガバナンス記録の一部が欠落している、
不整合である、またはハッシュチェーン検証に失敗している**ことです。これは
ガバナンス*成果物*についての言明です。

以下は意味**しません**:

- 研究ランが失敗した、または悪い結果を出した;
- ランが停止した、または詰まっている;
- 構成要素が制裁・隔離・排除された（それらは独自の status を持つレジストリの
  ライフサイクルイベントです — §4）;
- ページの他所に表示されている結果が誤っている。

逆向きの誤読も同じく誤りです: **記録された攻撃が 0 件であることはデータ点で
あって、健全性の証拠ではありません。** 研究生成役は現在、ノードへ一度だけ
付与する作成来歴から責任対象になり得ますが、攻撃の発火、裁定、同一期の来歴
一致が必要です。古いノードや曖昧なノードは対象なしのままです。したがって、
被覆範囲と来歴の情報なしに、沈黙から健全性を推論できません。

## 4. レジストリのライフサイクル対ノードのスコア状態

この 2 つはどちらも「status」と呼ばれることがあるため、最も混同されやすい語彙
です。両者は別の状態機械であり、1 つのフィールドに混在させることはありません —
API では 2 つの別々の閉じた型なので、ノード状態のフィールドにレジストリ status
を*表現すること自体*ができません。

**レジストリ構成要素のライフサイクル** — *ガバナンス下の構成要素またはプロンプト*
（あるロールの実装）の状態です。カーネルの宣言順をそのまま写した 10 値の閉じた
語彙: `candidate`、`validated`、`shadow`、`probationary_active`、`active`、
`warning`、`probation`、`quarantine`、`retired`、`banned`。おおまかに前半 5 つが
参入経路、後半 5 つが制裁経路です; それらの間の遷移はカーネル規則であって UI の
関心事ではなく、ダッシュボードはコミット済みのものを replay するだけです。

**ノードのスコア状態** — *1 ノードのスコア*の状態で、5 値の語彙です:

| 状態 | 意味 |
|---|---|
| `computed` | そのエポックのポリシー下で通常どおり採点された |
| `recomputed` | 生き残った入力から再採点された（レコードがエポックを挙げる） |
| `stale` | retire された構成要素に汚染された — フロンティア採点にもベストノード選択にももう寄与しない |
| `invalidated` | スコアが形成された際のポリシーが supersede された |
| `removed` | フロンティアから引き上げられた |

アカウンタビリティ側にはさらに 2 つの規律規則があり、慣習ではなく構造的に
強制されます:

- **生攻撃は決して数値を持てません。** 生の敵対的主張と裁定済みのものは別の
  レコード種別であり、生の種別はスコア・ペナルティ・確信度のフィールドを一切
  持ちません。その「主張された深刻度」は攻撃者の主張であってペナルティでは
  ありません。ペナルティを駆動できるのは裁定済みの検証済み攻撃だけです。
- **現在状態はコミット済みの replay です。** rollup スナップショットは replay と
  一致するかを確認するためだけに読まれ、未コミットの末尾が採用されることは
  決してありません。

## 5. スコアが比較可能なのは 1 つのポリシーの内側だけ

ダッシュボードが表示するすべてのスコア観測は、それが行われた**utility ポリシー
ハッシュ**を伴います。このハッシュは正準ポリシー本体のコンテンツハッシュなので、
2 つの異なるハッシュは文字どおり 2 つの異なる採点関数を意味します。

これは表示上の気配りではありません。`ari_rqgm` モードではエポック境界が utility
関数そのものを書き換えられ、その帰結として*スコア全体が書き換えられます* —
一度も攻撃されなかったノードについてもです。ポリシー `A` の下で計算された数値と
ポリシー `B` の下で計算された数値は、1 本の曲線上の 2 点ではありません; 2 つの
異なる計測器による 2 つの測定です。

そこから従う規則:

- **ポリシー同一性なしにスコアを表示しません。** 裸の数値ではなく
  「ポリシー `<hash>` 下のスコア」と示します。
- **異なるポリシーハッシュはファセット化され、決して結合されません。** 各ハッシュ
  が自分のグループを持ち、ポリシー変更をまたぐ 1 本の連続系列は存在せず、
  エポック横断のスコア比較はそもそも提供されません。
- **2 つの系譜チャネルは分離されたままです。** チャネル 1 はエポック*内部*の
  敵対的ペナルティ（ベーススコア → 検証済みペナルティ → 最終スコア。裁定済み
  レコード id を証拠として伴う）。チャネル 2 はエポック境界のポリシー書き換えです。
  どの消費者も誤って 1 本の履歴に統合できないよう、まさにそのために別リストに
  なっています。
- **2 つの再計算経路を明示します。** スコア済み証拠が stale になった場合、
  penalty utility は元のエポックの凍結重みで生存入力から再計算されます。
  policy 自体が supersede された場合、境界は保存済みで policy-independent な
  raw axis を新基準で再スコアし、新しい policy hash を刻印します。古い composite
  を変換することはなく、raw axis が無ければノードを無効化します。

## 6. stale、invalidated、removed、deleted — 4 つの別物

この語彙では「deleted」という語を禁じます。4 つのうち 3 つは削除を一切伴わない
からです。ガバナンスによる消去は**論理的なものに限られます**: 物理的に削除も
書き換えもされません。証拠はディスク上に残り、変わるのはそれが何かに影響を
及ぼしてよいかどうかだけです。

| # | 状態 | 実際に起きたこと | どこに存在するか | 可逆か |
|---|---|---|---|---|
| 1 | **stale（陳腐化）** | retire された構成要素によって生成された、または実質的に依存するレコード。フロンティア採点とベストノード選択への寄与を止める。 | ツリーを通じて永続化される追加的なノードセンチネル（`_stale`、`_valid_for_frontier`、`_stale_reason`、`_erasure_event_id`）と、監査ログ内の選択的消去イベント | はい — レコードとその来歴は無傷 |
| 2 | **invalidated（無効化）** | スコアが形成された際の utility ポリシーが supersede されたため、スコア自体がもはや成り立たない。 | 同じセンチネルチャネル（別の stale 理由付き）と、消去イベントの無効化ノード一覧 | はい — 生き残った入力での再計算は通常の帰結 |
| 3 | **removed（除去）** | ノードが探索フロンティアから引き上げられた（展開されなくなる）。 | フロンティア再構築イベントが除去ノードと復帰ノードを列挙する | はい — 復帰は普通のイベント |
| 4 | **物理削除** | チェックポイントディレクトリとそのログがディスクから消えた。 | 何も無い — 上記すべての不在がこれ | **いいえ** |

破壊なのは 4 番目だけであり、システムが危険と扱う唯一の操作です: ダッシュボード
からのチェックポイント削除は、そのパスに束縛されたサーバー発行の単回使用確認
チャレンジを伴わない限り拒否され、削除は `checkpoints/` ディレクトリの内側に
スコープされます。

論理 / 物理の分離がもたらす実務上の帰結:

- stale / invalidated なノードも依然として**監査可能**です。何をしたのか、なぜ
  stale 化されたのか、どのイベントが stale 化したのかを今も読めます。それこそが
  要点です: 結果の撤回が、それを生成したという記録を破壊してはなりません。
- stale 理由は**診断用の来歴**です。人間 — あるいはラベルを描画する読み取り
  モデル — がノードが stale 化された*理由*を言えるように存在するもので、カーネルは
  そこから制御判断を行いません。
- **証拠を遡及的に書き換えることはありません。** 既存ランをガバナンス付きへ
  改変せず、supersede されたレコードは上書きせずディスクに残します。ライブな
  境界は、保存済み raw axis を新たに採用された policy で再構成してフロンティア
  スコアを意図的に置き換えることがあります。erasure event が記録するのは
  再スコアされたノード一覧と *retire された* policy hash で、新たに採用された
  hash は再スコアされた各ノードに刻まれます。両 policy identity は、read model
  がその event を境界 transition と join することで復元されます。

## 7. 語彙クイックリファレンス

| 用語 | これに使う | これには使わない |
|---|---|---|
| ランライフサイクル | プロセスが生きているか / 終了したか | 研究の質 |
| 研究フェーズ | パイプライン上の位置（bfts / paper / review） | ガバナンスの進捗 |
| ガバナンス段階 | 現在のエポック + 有効なポリシー | 研究の成否 |
| 実行モード / 論文モード | 軸を限定した名前 — `ari.mode` が実行モード、`paper.mode` が論文モード | 裸の「モード」という語: 両者は独立した軸であり、限定されないラベルはどちらを指すか言えない |
| ガバナンスブロック | ガバナンス成果物が縮退している / 整合性検証に失敗している | 失敗した実験や停止したラン |
| レジストリ status | ガバナンス下構成要素のライフサイクル（candidate … banned） | ノードのスコア |
| ノードスコア状態 | 1 ノードのスコア（computed … removed） | 構成要素のライフサイクル |
| 生攻撃 | 未裁定の敵対的主張 | 数値的なもの一切 |
| 検証済みペナルティ | 裁定済みでスコアに影響する帰結 | 攻撃者が主張した深刻度 |
| stale / invalidated / removed | 完全に監査可能な論理状態 | 「Deleted」 |
| deleted | チェックポイントのディスクからの物理的除去 | あらゆるガバナンス状態 |
| プロジェクト既定値 / ランテンプレート / ランドラフト / 実効設定 / シークレット | 読み書きしている 1 つの設定面 | 設定全般を指す総称としての「設定（Settings）」 |

この表のうち 2 行 — モードの行と設定面の行 — は状態語彙ではなく命名規則であり、
いずれも部分的にしか成立していません。

モードの規則は、ラン単位の 2 軸については成立しています。Configuration Studio
の Execution セクションは 2 つのコントロールを*実行モード*と*論文モード*と
ラベルし、Governance ワークスペースは同じ 2 つのラベルを*モードソース*の隣に
繰り返します。それでも裸の**モード**ラベルは 2 箇所の legacy 画面に残っています
— ウィザードのリソースステップと、legacy な `#/settings` 画面の Container
カードです。そこではコンテナランタイム（`container_mode`）を指しており、これは
まさにこの規則が分離しようとしている第 3 の軸です。この 2 つのラベルを限定名に
することは**既知のギャップ**です。

設定の規則は Studio と run 設定ブラウザについては成立しており、各文書をその
スコープで名指します: プロジェクト既定値、ランテンプレート、ランドラフトは
3 つの別文書であり、実効設定はそれらの読み取り専用の解決結果、シークレットは
常に参照と準備状況フラグにすぎません（[Configuration Studio ガイド](../guides/configuration_studio.md)
の「3 つのスコープ」と「ブラウザ上のシークレット」を参照）。一方「設定
（Settings）」は legacy な `#/settings` 画面の名前として残っています — そこでは
画面名であってスコープではなく、Studio のどの文書も覆うものとして読んでは
なりません。
