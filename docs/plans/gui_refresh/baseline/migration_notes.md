gui_refresh program で導入する user 可視の挙動変更（behavior change）の告知台帳。1 変更 = 1 entry（MN-n）。各 entry は before/after、根拠（risk register / ADR）、影響 endpoint、user 可視の影響、rollback 手順を記録する。互換 freeze の対象外（P0 修正）も本台帳で告知する。

## MN-1: workflow write endpoints require an active checkpoint（Wave 2a）

| 項目 | 内容 |
|---|---|
| 種別 | Behavior change（P0 修正、互換 freeze 対象外） |
| Before | active checkpoint 不在時、`POST /api/workflow{,/flow,/skills,/disabled-tools}` は同梱 `ari-core/config/workflow.yaml` を黙って書き換え「成功」を返していた（以後の全 CLI/GUI run の既定 pipeline を無警告で変更） |
| After | active checkpoint 不在時、上記 4 endpoint は **400 で拒否**し何も書かない。応答は frozen payload `{"ok": false, "error": "No active project. Select a checkpoint before editing the workflow (the bundled default workflow.yaml is read-only from the GUI)."}`。active checkpoint がある場合の per-checkpoint copy への write は従来どおり |
| Rationale | risk register **RR-P0-1**（同梱 workflow.yaml の silent rewrite） |
| ADR | **ADR-10**（同梱 `workflow.yaml` write guard の意味論。reject 案を採用、opt-in / draft redirect は不採用） |
| 影響 endpoint | `POST /api/workflow`、`POST /api/workflow/flow`、`POST /api/workflow/skills`、`POST /api/workflow/disabled-tools`（GET 系は不変：read の bundled fallback は正当） |
| 実装 | `ari/viz/api_workflow.py` の共有 guard `_workflow_write_guard()`（4 handler すべてが write 前に通過。将来の write endpoint も同 guard を継承する）。negative test: `ari-core/tests/test_gui_workflow_write_guard.py` |
| User 可視の影響 | GUI の workflow editor（React Flow / skill phase / disabled tools）は **active project の選択が必須**になる。project 未選択のまま保存すると上記 error message が表示される。先に run/checkpoint を作成・選択すれば従来どおり編集できる |
| Rollback | 該当 commit を revert するのみ。data migration は不要（guard は書込拒否のみで file format・保存先を変更しない） |

## MN-2: `GET /api/env-keys` の secret 平文応答を廃止（redaction + readiness API）（Wave 3a）

| 項目 | 内容 |
|---|---|
| 種別 | Behavior change（P0 修正、互換 freeze 対象外） |
| Before | `GET /api/env-keys` は名前に `API_KEY`/`SECRET`/`TOKEN` を含む全 env 値を**平文**で source file path とともに返していた。Wizard StepResources の developer-mode「Auto-read」はこの値を API-key field へ prefill していた |
| After | (1) `GET /api/env-keys` は **redacted**: 非空 value は `***configured***`、空 value は `""`、`source` map は不変、top-level `"redacted": true` marker を追加（shape 互換 adapter として存続）。(2) 新設 **`GET /api/v1/secrets/status`** が allowlist 済み name（`ari.viz.v1.secrets.SECRET_NAMES`）の `{name, configured, source_class, last_updated}` のみを返す（value field は構造的に不存在）。(3) `POST /api/env-keys` の write 挙動は不変だが、name allowlist（`^[A-Z][A-Z0-9_]{0,63}$`、newline/control character 拒否）に違反する名前は **400** |
| Rationale | risk register **RR-P0-2**（secret 平文応答）、plan 09 §Secret policy（「API は secret value を返さず configured / source class / last updated のみ返す」「key name は allowlist に限定」） |
| ADR | **ADR-11**（readiness API の shape と旧 endpoint の閉鎖手順。deprecation 期間なしの即時 value 閉鎖を採用） |
| 影響 endpoint | `GET /api/env-keys`（redaction）、`GET /api/v1/secrets/status`（新設）、`POST /api/env-keys`（name allowlist のみ追加、happy path 不変）。settings POST の api-key 書込 flow は不変 |
| 実装 | `ari/viz/api_settings.py`（`ENV_KEY_REDACTED`、`_env_chain()`、name allowlist）、`ari/viz/v1/secrets.py` + `v1/dto.py`（`SecretV1`/`SecretStatusV1`）+ `v1/router.py`/`v1/openapi.json`。negative test: `ari-core/tests/test_gui_secret_readiness.py` |
| User 可視の影響 | developer-mode の「Auto-read」は**値を field に流し込まなくなり**、`configured (source_class)` / `not configured` の readiness 表示に変わる（`StepResources.tsx`）。configured の場合は field を空欄のままにすれば launch 時に `.env` の値が使われる。手動入力と Settings 画面からの key 保存（POST）は従来どおり |
| Rollback | 該当 commit を revert するのみ。data migration は不要（`.env` の format・保存先・write path は不変。redaction は read 応答のみの変更）。revert は RR-P0-2 を re-open するため G3 exit とは両立しない |

## MN-3: Workflow Studio の 2 秒 blind-overwrite autosave を廃止（weak revision + 409 conflict）（Wave 4d）

| 項目 | 内容 |
|---|---|
| 種別 | Behavior change（欠陥修正、plan 07 §Workflow Studio の non-negotiable「autosave は revision/ETag を用い、2 秒 timer の blind overwrite を廃止する」に基づく） |
| Before | Workflow Editor の autosave は編集の 2 秒後に**ディスク上の内容を一切見ずに** `POST /api/workflow/flow` で上書きしていた（別 tab / 別 user / 外部 process の変更を無警告で破壊）。skill phase / disabled tools の保存も同様の last-write-wins |
| After | (1) `GET /api/workflow` が additive key `revision`（配信した workflow.yaml bytes の sha256[:12]）を返す。(2) 4 write endpoint（`POST /api/workflow{,/flow,/skills,/disabled-tools}`）は OPTIONAL `base_revision` を受け、stale なら frozen payload `{"ok": false, "error": "workflow changed on disk since you loaded it (revision mismatch); reload before saving"}` + **HTTP 409** で拒否し**何も書かない**（CoW seed も走らない）。一致時は書込み後の新 `revision` を応答に含める。`base_revision` 無しの legacy caller は従来どおり last-write-wins（additive opt-in）。(3) GUI の WorkflowPage は debounce 保存（従来と同じ 2 秒 cadence）で毎回 `base_revision` を送り、dirty / saving / saved / conflict を明示。409 で conflict banner を表示して保存を**完全停止**し、明示的な Reload（未保存 local 編集は破棄、silent な再適用は無し）まで再試行しない |
| Rationale | plan 07 §Workflow Studio（blind overwrite 廃止、conflict 明示）。RR-P0-1/ADR-10 の write guard（400）とは独立で、guard が先に評価される |
| 影響 endpoint | `GET /api/workflow`（additive `revision`）、`POST /api/workflow`、`POST /api/workflow/flow`、`POST /api/workflow/skills`、`POST /api/workflow/disabled-tools`（OPTIONAL `base_revision` + 成功応答に additive `revision`）。endpoint の追加・削除は無し |
| 実装 | `ari/viz/api_workflow.py`（`workflow_revision` / `_served_workflow_path` / `_workflow_revision_guard`）、`ari/viz/api_settings.py`（GET revision + `POST /api/workflow` の guard 配線）、`frontend/src/services/api/workflow.ts`（`base_revision` 送出 + `isWorkflowRevisionConflict`）、`frontend/src/components/Workflow/WorkflowPage.tsx`（save state machine + conflict banner）。tests: `ari-core/tests/test_gui_workflow_revision.py`、`frontend/src/components/Workflow/__tests__/WorkflowPage.revision.test.tsx` |
| User 可視の影響 | Workflow Editor に保存状態 chip（Unsaved changes / Saving / Saved / Conflict）が表示される。別所で workflow が変更された場合、保存は成功したふりをせず conflict banner（「Workflow changed on disk」+ Reload button）になる。Reload は最新のディスク内容を読み直し、未保存の local 編集は破棄される（banner に明記）。競合が無い通常の編集体験は従来どおり（2 秒 autosave） |
| Rollback | 該当 commit を revert するのみ。data migration 不要（`revision`/`base_revision` は additive で、workflow.yaml の format・保存先は不変）。revert すると blind overwrite が復活するため plan 07 の non-negotiable を re-open する |

## MN-4: GUI server の loopback bind 既定化 + same-origin CORS（Wave 5a）

| 項目 | 内容 |
|---|---|
| 種別 | Behavior change（P0 修正、互換 freeze 対象外） |
| Before | (1) HTTP server（`_DualStackServer("", port)`）と WebSocket server（`ws_serve("", port+1)`）は**全 interface** に bind し、LAN/cluster network から無認証で全 endpoint に到達できた。(2) `_json`・OPTIONS preflight・SSE stream（`/api/logs`、paperbench job logs、`/api/v1/events/stream`）・手動 binary 応答（`/memory/`、`/codefile`、paper.pdf/tex、file/raw）・ollama proxy は無条件に `Access-Control-Allow-Origin: *` を返し、任意 origin の page が応答を読めた |
| After | (1) **bind は loopback 既定**（`127.0.0.1` + 可能なら `::1`。localhost が ::1 に解決される distro も従来どおり動く）。env `ARI_GUI_BIND` で override（`'::'` = 旧 all-interfaces dual-stack、`'0.0.0.0'` = IPv4 wildcard、単一 address も可）。(2) **CORS は same-origin echo のみ**: request `Origin` が server 自身の origin（`Host` header 一致、または loopback 形 `localhost`/`127.0.0.1`/`[::1]`:server port）に一致する場合のみその Origin を echo（+ `Vary: Origin`）。不一致なら ACAO header 無し（browser が応答を遮断）。OPTIONS preflight は不許可 origin に対して bare 204（Access-Control-* 無し）。env `ARI_GUI_CORS_ANY=1` で旧 wildcard を復元。歴史的に ACAO-less の `/state` と `GET /api/gpu-monitor` は不変 |
| Rationale | risk register **RR-P0-3**（全 interface bind × 認証不在 × ACAO:* の組合せ）、plan 09 §Deployment trust modes（「loopback bind を既定とする」「remote bind option を明示しない限り LAN へ公開しない」「strict same-origin local policy」）。**注意: RR-P0-3 の authentication/session sub-scope は本 MN の対象外**（ADR-05 auth は別途 G5 判断。row は bind+CORS のみ close し auth は open のまま） |
| 影響 endpoint | 全 endpoint（bind）。CORS header は `_Handler._json` 経由の全 JSON 応答、OPTIONS preflight、SSE 3 系統、手動 binary 応答（`/memory/`、`/codefile`、`/api/checkpoint/*/paper.*`、`file/raw`）、`/api/ollama/*` proxy。endpoint の追加・削除・payload 変更は無し（header のみ） |
| 実装 | `ari/viz/server.py`（`resolve_bind_hosts` / `_make_http_server` / `_http_thread` / `_main` の ws bind、ADR-07 docstring）、`ari/viz/routes.py`（`_origin_allowed` / `_cors_wildcard_enabled` / `_Handler._cors_origin` / `_send_cors_headers` / `do_OPTIONS`、ADR-07 docstring）、`ari/viz/api_ollama.py`。tests: `ari-core/tests/test_gui_bind_cors.py`（+ `test_server.py` の OPTIONS 2 test を same-origin 方針に更新） |
| User 可視の影響 | 既定設定の loopback 利用（`http://localhost:8765`、SSH tunnel の local forward、Vite dev proxy :5173）は**従来どおり**（dev proxy は same-origin 転送なので wildcard 不要なことを検証済み）。LAN の別 host から直接 `http://<server-ip>:8765` を開く運用は、`ARI_GUI_BIND` を設定しない限り接続不能になる。Origin が server と一致しない cross-origin 埋め込み/portal は `ARI_GUI_CORS_ANY=1` を設定しない限り応答を読めない |
| Rollback | env のみで可（redeploy 不要）: `ARI_GUI_BIND='::'` で旧 bind、`ARI_GUI_CORS_ANY=1` で旧 wildcard CORS。両方設定すれば pre-MN-4 挙動に一致。revert は RR-P0-3（bind+CORS 部分）を re-open する |

## MN-5: `GET /codefile` の path 境界 canonical 化 + `/api/ollama/*` proxy の 403 gate（Wave 5a）

| 項目 | 内容 |
|---|---|
| 種別 | Behavior change（P0 修正、互換 freeze 対象外） |
| Before | (1) `GET /codefile?path=` は絶対 path を受け、「active checkpoint 配下 **または path 文字列のどこかに `checkpoints` component を含む**」だけで任意 file を配信した（`/tmp/fake/checkpoints/x` のような偽装 path や symlink 経由の tree 外読出しが可能）。(2) `GET/POST /api/ollama/<path>` は**任意の path** を、ollama_host 未設定でも**暗黙の `http://localhost:11434`** へ無条件に中継した（backend が ollama でなくても localhost の任意 HTTP service への relay として機能） |
| After | (1) `/codefile` は resolved canonical path（`Path.resolve`、symlink 解決済み）が **active checkpoint dir または checkpoint search base（`checkpoint_finder._checkpoint_search_bases`）の resolve 済み prefix 配下**にある regular file の場合のみ配信。`..` segment は解決前に拒否、symlink escape は resolve 比較で拒否、directory/missing は 404。20MB cap・content-type・404/500 の status 体系は不変。(2) `/api/ollama/<path>` は (a) path が allowlist `{/api/tags, /api/show, /api/generate, /api/chat, /api/ps}` にあり、かつ (b) target が明示設定済み（settings `ollama_host` または env `OLLAMA_HOST`。cli-shim-with-ollama 構成を含む）**または** effective llm backend が `ollama`（この場合のみ従来の localhost:11434 既定を維持 = local dev flow 保存）の場合のみ中継。それ以外は upstream 接続を開かず **403** `{"error": ...}` |
| Rationale | risk register **RR-P0-5**（緩い path 境界）/ **RR-P0-7**（reverse proxy）、plan 09 §Project, run, and filesystem isolation（「resolved canonical path が管理 root 配下か検証」「`..`、absolute path、symlink escape を negative test」） |
| 影響 endpoint | `GET /codefile`（境界のみ変更。React frontend の正当な利用 — Results/FiguresSection/EarSection/PaperWorkspace が real checkpoint dir 配下の artifact を配信する flow — は search base + active checkpoint 経由で従来どおり）、`GET/POST /api/ollama/<path>`（allowlist + 403 gate。frontend は proxy を直接呼ばず `GET /api/ollama-resources` のみ使用（grep 検証済み: `services/api/resources.ts` が唯一の caller）。allowlist は legacy dashboard/ops flow が使った標準 Ollama API 5 path） |
| 実装 | `ari/viz/routes.py`（pure `_codefile_resolve` + `/codefile` branch）、`ari/viz/api_ollama.py`（`OLLAMA_PROXY_ALLOWED_PATHS` / `_explicit_ollama_host` / `_ollama_proxy_refusal` + module docstring の policy 記録）。negative tests: `ari-core/tests/test_gui_path_proxy_hardening.py`（`../` traversal、symlink escape、`/etc/passwd`、`/tmp/fake/checkpoints/x` 偽装、directory、未設定 host での no-connect 403、非 allowlist path 403）+ `test_ollama_gpu.py` の localhost 既定 test を「backend=ollama の場合のみ」に更新 |
| User 可視の影響 | 既定 checkpoint 配置（`workspace/checkpoints`、`checkpoints/`、`ari-core/checkpoints`、cwd 配下）と active checkpoint の artifact 表示は**従来どおり**。checkpoint tree 外の絶対 path を `/codefile` に渡す非正規利用は 404 になる。Ollama proxy は backend が ollama の local 構成では従来どおり。backend が ollama 以外で proxy を使いたい場合は Settings の `ollama_host` か env `OLLAMA_HOST` を設定する（それが opt-in） |
| Rollback | **traversal 修正（/codefile）に rollback は無い**（純粋な security fix。env kill-switch も設けない）。ollama gate の「rollback」は target の明示設定（`ollama_host` / `OLLAMA_HOST`）そのもの — allowlist 外 path の中継は復元手段を提供しない。revert は RR-P0-5/RR-P0-7 を re-open する |

## MN-6: destructive operation に server-issued confirmation challenge を必須化（Wave 5a）

| 項目 | 内容 |
|---|---|
| 種別 | Behavior change（P0 修正、互換 freeze 対象外） |
| Before | destructive operation の確認は client-side のみ: `POST /api/delete-checkpoint` は body の path を無確認で rmtree（`window.confirm` 相当のみ）、`POST /api/stop` は pkill を含む全 process 停止を無確認で実行、`POST /api/gpu-monitor` の `stop` も直接実行。GPU monitor `start` の `confirmed: true` は API layer に**ハードコード**されていた |
| After | (1) 新設 **`POST /api/v1/challenges`** `{action, target}`（action は `delete-checkpoint` / `stop-all` / `gpu-monitor-stop` のみ）が single-use の確認 grant `{challenge_id: "chg-<12hex>", action, target, expires_at, ttl_seconds: 60}` を発行（in-memory deque cap 100、TTL は `time.monotonic()` 基準 60 秒 — 壁時計 jump で延命しない。発行/消費/拒否は active checkpoint の `viz_access.jsonl` に `challenge_*` event として監査記録）。(2) `POST /api/delete-checkpoint`（binding: action `delete-checkpoint` + 送信 path）、`POST /api/stop`（`stop-all` + `"*"`）、`POST /api/gpu-monitor` `action=stop`（`gpu-monitor-stop` + `"*"`）は body の `challenge_id` が「未使用・未失効・action+target 一致」の場合のみ実行。それ以外は frozen payload `{"ok": false, "error": "confirmation challenge required or invalid"}` + **HTTP 428** で拒否し破壊的処理を一切行わない。(3) GUI は two-step 化: challenge を取得し、confirm dialog に server が echo した target を impact preview として表示してから destructive call に `challenge_id` を添付。`gpuMonitorAction` の `confirmed: true` ハードコードは撤去（start は caller の明示確認後にのみ渡す） |
| Rationale | risk register **RR-P0-6**（delete=rmtree / stop=pkill が server-side challenge なし）/ **RR-P0-9**（確認が client-side のみ）、plan 09 §Dangerous operations（「server が short-lived confirmation challenge を発行し、対象 ID/action と bind する」「UI は impact preview を表示」「audit event を必須にする」） |
| 影響 endpoint | `POST /api/v1/challenges`（新設）、`POST /api/delete-checkpoint`、`POST /api/stop`、`POST /api/gpu-monitor`（`action=stop` のみ。`start`/status は不変）。応答 shape は成功時従来どおり（拒否時のみ新 428 payload） |
| 実装 | `ari/viz/v1/challenges.py`（store/issue/consume/`require_challenge` + ADR-07 docstring）、`ari/viz/v1/{router,dto,openapi}.py` + `openapi.json`、`ari/viz/checkpoint_lifecycle.py`・`ari/viz/api_process.py`（enforcement）、`ari/viz/routes.py`（3 branch の `_status` pop）、frontend `services/api/{challenges,checkpoints,experiment,resources}.ts` + `SettingsPage.tsx` / `MonitorPage.tsx` / `GpuMonitor.tsx`。tests: `ari-core/tests/test_gui_confirmation_challenges.py`、`frontend/src/__tests__/devModeAndDangerousOps.test.tsx` |
| User 可視の影響 | 既定設定の local 利用では project 削除・experiment 停止は従来どおり 1 回の confirm dialog（内部が two-step になり、dialog に server echo の削除対象 path / 停止対象が表示される）。Stop ボタンは新たに confirm dialog を表示する。`curl` 等で旧 endpoint を直接叩く自動化は challenge 取得を先行させるか `ARI_GUI_CHALLENGES=0` を設定しない限り 428 になる |
| Rollback | env のみで可（redeploy 不要）: `ARI_GUI_CHALLENGES=0` で 3 endpoint とも legacy 直接実行に戻る（challenge 発行 endpoint は残るため two-step client はそのまま動く）。revert は RR-P0-6/RR-P0-9 を re-open する |

## MN-7: CDN script 除去 + GUI index/static への CSP・nosniff・referrer policy 付与（Wave 5a）

| 項目 | 内容 |
|---|---|
| 種別 | Behavior change（P0 修正、互換 freeze 対象外） |
| Before | (1) `frontend/index.html` が `https://cdn.jsdelivr.net/npm/d3@7` を `<script>` load（npm bundle の d3 と二重・supply chain 露出。`window.d3` の利用箇所は 0 — 全 d3 consumer は npm import）。(2) SPA index / `/static/` 応答に CSP・`X-Content-Type-Options`・`Referrer-Policy` header なし。(3) `dangerouslySetInnerHTML` が `StepScope.tsx` の scope summary（local numeric state の文字列組立）に 1 箇所 |
| After | (1) CDN `<script>` を削除し bundle 一本化（`npm run build` 再生成で `static/dist/index.html` からも消える）。(2) `_serve_spa_index` と `/static/` branch が `Content-Security-Policy`（`default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data:; connect-src 'self' ws://<host>:<port+1> wss://<host>:<port+1>; frame-src 'self'; frame-ancestors 'none'`。ws source は request Host header の hostname から純関数 `_csp_policy` が導出 — tree stream が HTTP port+1 で listen するため `'self'` では足りない。Host 不明時は loopback alias 3 種、port 不明時は ws source 省略 = polling fallback）+ `X-Content-Type-Options: nosniff` + `Referrer-Policy: no-referrer` を送出。API/JSON 応答は対象外。(3) `dangerouslySetInnerHTML` は inventory の結果 1 箇所のみで、素の JSX に置換し **SPA から全廃**（sanitizer 依存の新規追加なし — raw な remote/LLM content を HTML として挿入する箇所は存在しない） |
