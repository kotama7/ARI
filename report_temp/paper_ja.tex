\begin{abstract}
大規模言語モデル（LLM）によるベストファースト木探索（BFTS）では、親の実行可能 workspace に加えて、
外部評価器の客観的 Evidence と親 LLM の自己報告を子へ継承できる。本稿は、\armW（明示的な親 report なし）、
\armE、\armS{} という 3 種類の bundled policy を比較する。Self-Report は親モデルによる作業記述、
懸念、次手提案であり、親自身のツール出力や自己テストは参照し得るが、外部評価器の結果を入力として生成しない。
\texttt{gemm}、\texttt{spmm}、\texttt{stencil} について、同じ seed を持つ 3 方針の別実行を
1 block とする 30 matched seed block、計 270 run を A64FX 上で実施し、選択候補を別 seed・各ケース
15 反復で再測定する。

本稿はあわせて、この比較を成立させるための評価系を示す。予備実験の監査により、分母が naive 実装である
こと、作業集合が最終段キャッシュに収まること、計上時間に wall clamp を掛けること、OpenMP thread team を
計測窓の内側で生成することが、いずれも条件差と同程度以上の系統差を生むことが判明した。そこで分母を
competent な凍結参照に置き換え、キャッシュに収まらない問題サイズを選び、計上時間を候補の内部タイマに
一本化し、team 生成を計測窓の外へ出す。偽装は、候補のカーネル時間を測っていない wall 下界ではなく、
export 記号・初期化フックの制限と依存記号の検査によって構造的に防ぐ。

本設計が同定するのは、自然言語を完全除去した介入ではなく、評価後の Self-Report を明示的に常時追加する
policy bundle の end-to-end 効果である。意味内容、文脈長、品質、workspace 内の自然言語は独立には
同定できない。
\end{abstract}

\section{はじめに}
高性能計算（High Performance Computing; HPC）に対する LLM コードエージェントは、編集・ビルド・計測を
反復しながら候補を探索する。
BFTS では高得点ノードを展開し、子は親のコードと workspace を引き継ぐ。ここへ評価結果を追加すれば、親コードの
正当性、ケース別性能、失敗理由を明示できる。さらに親 LLM の作業記述、懸念、次手提案を渡せば、探索を
方向付けられる可能性がある。一方、workspace 自体もコメントや追加ファイルとして自然言語を保持し得る。
本稿では、実装上 ``Reflection'' と呼ばれていた 3 フィールドを、その生成過程に即して
\emph{評価後の親 Self-Report} と呼ぶ。これは評価器が当該ノードを採点した\emph{後}に、
その判定を入力として生成される。

本研究の中心課題は、\textbf{実行可能な親 workspace に明示的な客観 Evidence を追加する end-to-end 効果と、
さらにその Evidence に対する LLM の解釈をすべての handoff に追加する増分効果}である。
Self-Report は評価器の判定を見た後に生成するため、\armS{} と \armE{} は\emph{同一の客観的証拠}を持ち、
差は解釈の有無だけになる。すなわち \armS{}$-$\armE{} は「客観的証拠の上に LLM の解釈が何を足すか」を測る。

当初の実装は Self-Report を評価\emph{前}に生成しており、その場合の対比は「証拠＋判定を見ずに書いた自己記述」
対「証拠のみ」となる。これは分離としても不完全であった。エージェントの自己テストは採点対象と同じ形状を測り、
課題文はその値を参照値で割ればスコアの良い近似になると明示しているため、自己記述は判定を知らないわけでも
なかった。評価後に移すことで、両腕が同じ証拠を持つ設計になる。

代償として、解釈が判定の数値をそのまま繰り返せば \armS{} は \armE{} の言い換えになりうる。
そこで生成 prompt は測定値の再掲を禁じ、結果が\emph{コードについて何を含意するか}のみを求める。
提案が実際に子コードへ到達したかは、提案を受けていない条件での基底率と対比して事後に測る
（表~\ref{tab:trajectory}）。

本稿の貢献は次の通り。
\begin{enumerate}
  \item Evidence と、その Evidence に対する LLM 解釈を分離し、後者の常時追加だけを変える主要対比を定義する。
  \item handoff 方針を run 単位で固定した 270 run の対応実験により、end-to-end の探索性能を評価する。
  \item 予備実験の監査から、分母・問題サイズ・計上時間・thread team 位置が条件差と同程度以上の系統差を
    生むことを実測で示し、これらを比較可能性の前提条件として評価系に組み込む。
  \item token、実行時間、Self-Report の欠損・品質、\armW{} の自然言語漏洩、絶対性能を事後監査し、
    主介入の同定範囲を明示する。
\end{enumerate}

\section{関連研究}
最も近い先行研究 AIDE~\cite{aide} は ML エンジニアリングをコード空間の木探索とし、各ノードを完全な
スクリプトと要約 $\Sigma(T)$ で表すが、要約中の客観的証拠と LLM 解釈を分離していない。
CodeTree~\cite{codetree}、LATS~\cite{lats}、GIF-MCTS~\cite{gifmcts}、Tree of Thoughts~\cite{tot} は
critic、scoring、探索方策を扱うが、handoff の情報成分を比較しない。Reflexion~\cite{reflexion} は言語的反省を
記憶するのに対し、本研究は客観的証拠と、その証拠に対する親の解釈を分離する。すなわち自己反省の有用性全般ではなく、
それをすべての handoff に追加する bundled policy が \armE{} を上回るかを問う。KernelBench~\cite{kernelbench} は
GPU カーネルの逐次改良であり、分岐木上の親子継承を対象としない。本研究は、Evidence と Self-Report を分離し、
run 単位で統制したうえで複数の HPC カーネルを同じ原則で評価する。

LLM 以前から、ATLAS~\cite{atlas}、FFTW~\cite{fftw}、OpenTuner~\cite{opentuner} は実機測定に基づく
自動チューニングを行い、TVM~\cite{tvm} は学習したコストモデルで低水準プログラム探索を高速化する。
Kokkos~\cite{kokkos} は異種 many-core 環境での performance portability を扱う。これらは、有効な最適化が
課題とアーキテクチャに依存することを示す。本研究は既存 autotuner の代替ではなく、LLM 探索で実測情報を
試行間にどう伝えるかを対象とする。HPC 向け LLM 評価~\cite{cuihpc} と MARCO~\cite{marco} は、性能 feedback の
可能性と同時に、正当性・並列化・アーキテクチャ理解の失敗を報告する。本研究は model、tools、評価器、計算機、
探索予算を固定し、親子間情報の性質だけを ablation する。

近年は、VibeCodeHPC~\cite{vibecodehpc} が複数 agent による HPC 反復 tuning、AutoPass~\cite{autopass} が
compiler artifact と runtime evidence に基づく性能調整、compiler--LLM cooperation~\cite{compilerllm} が
compiler 構成要素を tool とする最適化を扱う。PerfCodeBench~\cite{perfcodebench} は baseline、参照最適化、
実行可能な正当性検査を備えた system-level 評価を提案し、実機性能を reward とする online RL~\cite{hpcorl} も
報告されている。これらが feedback を利用した性能向上を問うのに対し、本研究は feedback 内の機械生成 Evidence と
評価後 Self-Report という明示的 channel を ablation する。

\section{対象システム}
\paragraph{構成}
実験システムは、ベストファースト木探索（BFTS）、各 node 内の ReAct~\cite{react} ループ、Model Context
Protocol（MCP）で公開するコード操作用ツール、固定した非 LLM 評価器からなる。入力は最適化課題と初期 workspace
であり、アイデア生成、文献調査、論文生成は実行しない。

\paragraph{run、node、workspace}
1 \emph{run} は、1 課題、1 乱数 seed、1 handoff 条件で別個に実行する BFTS 木を指す。
\emph{node} は木中の 1 回の最適化試行であり、各 node は専用の \emph{workspace} を持つ。workspace は候補
C ソース、候補用コンパイルフラグ、Makefile、自己テスト用ファイルからなるディレクトリである。各課題の root
workspace には、正しい naive 実装と自己テスト用足場を配置する。子 node では、親の候補ソースとビルド設定を
複製し、親候補を初期状態として次の最適化を行う。したがって \armW{} は、コメントを除去した純粋な code token
ではなく、この実行可能 workspace と「明示的 parent-report message なし」を意味する。

\paragraph{1 node の実行}
図~\ref{fig:system} に処理順を示す。まず実験制御器は、課題記述、利用可能なツールのスキーマ、条件に応じた親 handoff
を LLM へ与える。LLM は ReAct 形式で workspace を読み書きし、ビルドと自己テストを反復する。終了後、LLM から
独立した非 LLM 評価器が候補だけを別途コンパイルし、正当性と性能を測る。実験制御器は評価値を node のスコアとして保存し、
完了 node を展開候補集合（frontier）に加える。空き探索枠が生じると、BFTS は frontier 中で最高スコアの親を選び、
その workspace と、実験条件で許された handoff から子を生成する。

\paragraph{環境情報の経路}
エージェントへ渡す環境カタログについて、予備実験には 2 つの欠落があった。第 1 に、本サイトの module tree は
2 段構成であり、素の \texttt{module avail} は entry module のみを列挙する。この平坦な一覧にはコンパイラが
1 つも現れず、ベンダコンパイラは entry module を load して初めて可視になる。したがって予備実験の
エージェントはその存在を知り得なかった。本条件では entry module を部分シェル内で load して差分のみを
報告する（実際に load すると、記述対象であるノードの構成を変えてしまう）。第 2 に、本機は
\texttt{lscpu}・sysfs・\texttt{getconf} のいずれもキャッシュ容量を報告せず（sysfs は L2 を 48 コア共有と
誤って報告する）、ブロッキング因子をキャッシュに合わせるという操作が原理的に不可能であった。
本条件ではポインタチェイスにより階層を実測し（本機で line 256\,B、L1d 64\,KiB、段差 4096\,KiB、所要 0.66\,s）、
その結果をカタログに含める。機種固有の値をコードへ埋め込まないため、他機でも正しい値が得られる。
最後の段差 4096\,KiB は公称の CMG あたり L2 容量 8\,MiB と一致しないが、これは実測が
\emph{単一スレッドが実際に依存できる}容量を返すためである。実測した遅延は 1024\,KiB までの 28\,ns から
2048\,KiB で 31\,ns、4096\,KiB で 46\,ns と漸増し、公称容量ちょうどの 8192\,KiB では 106\,ns と
主記憶並みに達する。ブロッキング因子を合わせるべき値は後者ではなく前者であり、
本稿の評価ケースはいずれも両者を大きく超える。

\paragraph{記録と情報経路}
各 node の終了時に、実験制御器は \texttt{node\_report.json} と full trace を保存する。前者は node ID、
評価状態、ケース別結果、変更ファイル、LLM の自己記述を生成元別に保持する。さらに
\texttt{measurement\_audit} に各反復の入力 seed、候補・baseline の内部時間と wall time、
wall 下界とその比（v2 では棄却に用いず診断値として記録する）、
残差、採否、実効・拒否コンパイルフラグを保存する。full trace は ReAct の全メッセージ、ツール入出力、および
step 上限到達後に Self-Report を補完する別 LLM 呼出しの prompt と応答を保存する。これらは監査用であり、
許可した Evidence 以外は子へ渡さない。

\section{実験設計}
\paragraph{探索と handoff 条件}
各 node のエージェントは最大 20 ReAct step で上記ツールを用い、候補コードを作る。
予備実験では 25 step としていたが、node が自身の最良結果に到達した step は
p50=3、p90=13、p95=15、p99=20 であり、上限を 25 から 40 へ引き上げても改善した node は
線形外挿の 101 ではなく約 28 にとどまった。あわせて、作業ディレクトリの一覧、継承した候補ソース全文、
現行コンパイルフラグ、および実測した環境カタログをプロンプトへ前置する。予備実験ではこれらの再取得に
全 step の 27.5\,\%（約 12{,}749 step）を費やしており、いずれもエージェント自身のツールで到達できる
情報であるため、前置は新たな情報を与えず往復のみを削る。
固定した非 LLM 評価器が全ノードを採点し、BFTS は最高得点のフロンティアノードを展開する（本実験では
$N=10$ ノード/run）。これは LLM が最適化する root 1 試行と子 9 試行の合計であり、未変更 root の後に
10 個の子を作る設定ではない。子は常に親 workspace を複製し、追加文脈だけを次の 3 条件で変える
（図~\ref{fig:method}）。
\begin{enumerate}
  \item \textbf{\armW}: workspace のみで、明示的 parent-report message はない。
  \item \textbf{\armE}: workspace と、評価器・ハーネスが確認した客観的証拠。
  \item \textbf{\armS}: \armE{} に、評価後の親 Self-Report を追加。
\end{enumerate}
\armS{} では利用可能な全親子 handoff に Self-Report を注入するため、失敗時だけの選択方針ではなく
\emph{always-on} policy bundle を評価する。以下、完全な 3 方針を W、E、S と略す。1 run には
1 方針だけを適用し、探索木は共有しない。同一 seed の 3 run は matched block だが、親 workspace、prompt、
model sample、探索軌跡を共有しない。推定対象は固定親からの局所差ではなく、handoff 方針を通した end-to-end の
run 差であり、主要対比は E--W と S--E である。

BFTS は、外部評価結果を持つ frontier node を優先し、その中で非正規化の幾何平均 speedup が最大の node を選ぶ。
同点なら現在の frontier で先に現れる node を選び、適格な限り同じ親を再展開できる。子が親を厳密に上回れば親を
retire する。無変更子は sterile として測定を保持するが、再展開、親 retire、最終選択から除く。測定 invalid node は
score 0 で記録され、高得点の有効 node がなければ debug 用の親になり得る。最終候補は有効かつ非 sterile の最大値とし、
完全同点では辞書順に並べた report path の先頭を採る。1 node の再展開上限は 999 で、10-node run では到達しない。

workspace の複製では、候補ソース、ビルド設定、自己テスト足場を継承する一方、\texttt{results.json}、
評価結果、標準出力・標準エラー、生ログ、\texttt{node\_report.json}、環境プローブ結果を除く。さらに、過去
node の要約を検索・注入する cross-node memory と、BFTS の子生成プロンプトを作るプランナが親レポートを付与する既定経路を、
全条件で無効化する。これにより \armW{} に別経路から親の測定値や説明が流入することを防ぐ。ただし、親 LLM が
ソースコメントまたは任意の非除外ファイルへ書いた文章は、コード成果物の一部として残りうる。

\begin{tikzpicture}[font=\footnotesize,

\paragraph{Evidence と Self-Report の生成}
表~\ref{tab:handoff-fields} に子プロンプトへ出力するフィールドを示す。Evidence は、制御器、評価器、
ハーネス、ファイル hash 比較が機械的に確認した 7 フィールドだけから生成する。
\texttt{evaluation\_cases} はケースごとの \texttt{valid} と \texttt{measurements} を持ち、測定名は
各ハーネスが定義する。\texttt{known\_failures} は測定無効時の評価器理由から機械的に導出し、LLM の懸念を
参照しない。反復ごとの生時間とコンパイルフラグを持つ \texttt{measurement\_audit} は監査専用であり、
Evidence へ含めない。

Self-Report は、親 LLM が node 終了時に記録した作業解釈、残る懸念、次の最適化案から成る。両 Evidence 条件は
同じ見出しとレンダリング関数を使う。同一 report を入力したときの客観部分は byte 単位で同一であり、
\armS{} はその末尾へ Self-Report だけを追記する。実際の条件間では探索木を別個に実行するため値自体は異なる。
handoff は子の最初の LLM 呼出しに独立メッセージとして注入する。\armW{} ではこの
メッセージを生成せず、raw report、監査記録、full trace は全条件で注入しない。
監査可能性のため Self-Report 記録自体は全条件で生成する。通常は親の finish JSON として外部評価前に生成され、
\texttt{run\_bash} 等の自己テスト出力は参照し得るが、後続の外部評価値は参照できない。20 step 到達時は ReAct 終了後に
tool なしの補完呼出しを 1 回行う。この呼出しは制御器側評価の後になる path もあるが、prompt は評価前 ReAct trace の
末尾だけであり、外部評価結果を含まない。補完呼出しは 20 step の外側だが、token、call 数、wall time に含める。
いずれの Self-Report も同一 node の行動 loop へ戻さない。したがって比較するのは評価後 Self-Report の
\emph{注入効果}であり、外部 Evidence を読んだ解釈や生成省略による運用コストではない。

\paragraph{課題と採点}
3 課題はいずれも、正当性を満たした候補の\emph{参照実装}比 speedup を最大化する（表~\ref{tab:tasks}）。
参照実装は naive ではなく、同じ契約（plain C、OpenMP、コンパイルフラグのみ。intrinsics・アセンブリ・
外部ライブラリは不可）で書かれた competent な実装である。分母を naive に取ると、スコアは「候補が何もしない
状態からどれだけ離れたか」を測ることになり、最適化の質を測らない。

ここで competent の水準は、実測で定義する。予備実験の corpus では \texttt{gemm} の上位 1 割が
ブロッキング定数を 1 つも持たず、教科書どおりの \texttt{ikj} ループにベクトル化フラグを加えたものが
最良であった。したがって参照は少なくともこの実装に負けてはならない。この検査を 3 課題すべてに対し、
予備実験でエージェントが実際に生成した最高スコア候補を用いて行った。候補ソースはそのコンパイル
フラグごと corpus から取り出し、採点経路で分母と比較した。参照比は \texttt{spmm} が 6 ファミリで
0.613--0.871、\texttt{stencil} が 0.771／0.783／0.812 であり、参照がそれぞれ 1.15--1.63 倍、
1.23--1.30 倍速い。

\texttt{gemm} の参照比は 0.777／0.861／0.823 であり、3 形状すべてで参照が 1.16--1.29 倍速い。

\paragraph{採点形状は分母ではなく分散で決まった}
この \texttt{gemm} の第 3 形状は当初 $500\times500\times2000$ であり、そこでは参照が \texttt{ikj} に
1.313 倍\emph{劣って}いた。ブロッキングが並列反復数を $\mathrm{MR}$ で割るため、$n=500$ ではタイルが
125 個しかなく 48 スレッドを満たせない。参照が持つ行並列経路へ分岐させると 1.021 まで回復するが、
独立に 10 回採点したときの計上時間のばらつきが 0.76\,\% から 11.87\,\% へ、反復数の根拠である
band 指標が 0.46\,\% から 2.27\,\% へ悪化した。レジスタブロッキングを保ったまま $\mathrm{NC}$ を
下げて並列単位を増やす案は速度・安定性の両方でさらに悪く（$\mathrm{NC}=256$ で 5.565\,ms／9.28\,\%、
$128$ で 5.722\,ms／11.33\,\%）、この形状で両立する分解は見つからなかった。

原因はカーネルではなく形状であった。$n=500$ は 48 スレッドに対し 10.4 行/スレッドであり、
候補が実際に書く \texttt{ikj} を含めて\emph{あらゆる}行並列実装がここでは不安定になる。すなわち
分母を安定側に固定しても、\emph{候補側}のスコアが揺れる問題は残る。$n$ を上げるだけでは足りず
（$1000\times600\times2000$ で \texttt{ikj} はなお 4.34\,\%）、$1500\times600\times1500$ で解決した。
同形状では参照が 7.341\,ms／0.18\,\%、\texttt{ikj} が 8.871\,ms／3.37\,\% であり、
\emph{安定な経路が同時に速い経路になる}。長い縮約という regime（$p/m=2.5$）と、作業集合が
最終段キャッシュを超えるという制約は保たれている。

したがって採点形状の選択は、問題規模やキャッシュ収まりだけでなく、\emph{候補が書くであろう実装が
その形状で安定に測れるか}によっても決まる。この基準は本稿の設計から事後的に得られたものである。

\paragraph{問題サイズの選択}
gemm の作業集合は、予備実験で用いた $512^3$ では 6.0\,MiB であり CMG あたり L2（8\,MiB）に収まっていた。
この条件では、独立に書いたレジスタブロッキング実装と、ブロッキングだけを外した実装との比が
1.046 倍にとどまる。予備実験の測定バンド（同一対象を独立に 2 回採点したときの $|\Delta|$ の p95）は
探索が用いた反復数で 4.6\,\% であり、この 4.6\,\% の利得はちょうど分解限界に等しい。
すなわち探索はブロッキングの効果を分解できなかった。作業集合が L2 を離れる本条件では
同じ比が 1.289 倍となる。SVE を有効にした対でも同様で、$512^3$ の 0.988 倍に対し本条件では 1.229 倍である。
すなわちブロッキングという最適化を目的関数が識別できるかどうかは、問題サイズによって決まる。
$m$ を 32 の倍数としないのは、$B$ の列ストライドが L1 のセットにエイリアスしうるためであるが、
本機では効果を確認できなかった。$m$ だけを変えた対（$2048$ 対 $2040$、$1024$ 対 $1016$）を、
アクセスパターンの異なる 3 実装（凍結参照、ブロッキングを外した \texttt{ikj}、$B$ を
ストライド参照する naive \texttt{ijk}）について採点経路で実測すると、比は 0.98--1.08 倍に収まり、
$B$ をストライド参照する naive でも $2048$ で 1.01 倍（235.9\,s 対 234.6\,s）であった。
この制約は採点ケースが既に満たしているため保持するが、根拠は実測に基づかない。

stencil の掃引回数 $n_t$ を 240 とするのは、候補が自前で ping-pong バッファを確保する仕様に由来する。
268\,MB 分の first touch に伴うページフォルトが計測窓の内側に入るため、$n_t=30$ では計測窓 78.5\,ms のうち
50.6\,ms（64\,\%）が掃引以外であった。計測窓は $n_t=30,60,120,240$ の実測に対し $50.57 + 0.9298\,n_t$ [ms]
に適合し（最大残差 0.4\,\%）、$n_t=240$ ではこの比が 18.5\,\% となる。

評価器は候補と凍結 baseline を別々にコンパイルし、fp64 参照解と要素ごとに照合する。出力要素 $z$ の許容誤差は
\begin{equation*}
 |z_c-z_r|\le
 \begin{cases}
 c_\epsilon\,\gamma(p)\,(|A||B|)_{ij}, & \texttt{gemm},\\
 c_\epsilon\,\gamma(\operatorname{nnz}_i)\,(|A||X|)_{ij}, & \texttt{spmm},\\
 c_\epsilon\,\gamma(7)\max(n_t,1)\max|u_0|, & \texttt{stencil},
 \end{cases}
\end{equation*}
とする。ここで $\gamma(k)=ku/(1-ku)$、$u$ は fp64 の unit roundoff、$c_\epsilon$ は固定安全係数、
$p$ は縮約長、$\operatorname{nnz}_i$ は第 $i$ 行の非零数である。

各反復で新しい入力を生成し、候補と参照を交互順で対応実行する。奇数反復で一方が1回多くなるため、
開始順を seed の奇偶で反転し、30 seed 全体では各条件の実行順を釣り合わせる。
計上時間は候補プロセスの内部タイマとし、wall clock による clamp は行わない。
wall 下界 $t_{c,\mathrm{wall}}-(t_{b,\mathrm{wall}}-t_b)$ は候補のカーネルについて何も測っていない。
差し引く $t_{b,\mathrm{wall}}-t_b$ はプロセス起動・問題読込・出力書出しであり、本機では
\texttt{gemm} 18.9--21.1\,ms、\texttt{spmm} 56.5--91.3\,ms、\texttt{stencil} 109.0--127.0\,ms を占める。
これは凍結参照の wall 全体の \texttt{gemm} で 80--88\,\%、\texttt{spmm} で 81--94\,\%、
\texttt{stencil} で 32--34\,\% にあたる。すなわち下界の大半はカーネル外の量で決まり、
参照の overhead が候補の wall 全体を上回れば負にもなる。
閾値による救済も成立しない。予備実験の構成での実機検証では、閾値 0.50 が本研究の選抜候補自身を
3 反復中 2 反復で棄却し、0.02 でも棄却した。カーネルが実際に速くなるほど（当該構成で 0.8--1.5\,ms、
下界は約 60\,ms）正直な比は 0.015 程度まで下がるためで、速い正直なカーネルと偽装を分ける閾値は存在しない。
偽装は代わりに構造的に防ぐ。候補オブジェクトは所定のカーネル記号のみを export でき、
\texttt{.init\_array}/\texttt{.preinit\_array}/\texttt{.ctors}/\texttt{.fini\_array}/\texttt{.dtors} と
IFUNC を持つ場合、および \texttt{fopen}/\texttt{open}/\texttt{atexit}/\texttt{system}/\texttt{fork}/
\texttt{exec*}/\texttt{dlopen} 等を参照する場合は無効とする。
また OpenMP の thread team はタイマ開始前に生成する（候補カーネルは呼ばない）。
この 1 点だけを戻した対照を実測すると、凍結参照の内部時間から 48 スレッドの team 生成に相当する
時間が一律に外れる（\texttt{gemm} で 3.06--3.12\,ms、\texttt{spmm} で 2.86--3.27\,ms）。v2 の参照は
この時間が無視できる規模ではなく、割合では \texttt{gemm} で 37.5--54.3\,\%、\texttt{spmm} で
14.0--41.9\,\% を占める。\texttt{stencil} ではさらに大きく、計測窓が 214\,ms から 437--549\,ms へ
2 倍以上に伸びる。しかもこの 2 倍は形状によらず一定ではない。反復ごとに別プロセスで実行しているにも
かかわらず、ある形状では最初の 3 反復が 437\,ms、以降の 4 反復が 216\,ms となり、ノード側に持ち越された
状態に依存した（この形状の変動係数は 35\,\% であり、タイマ前生成では 0.2\,\% である）。
すなわち予備実験は pin されていない参照を pin された候補と比較しており、
本条件の speedup は予備実験の値と比較できない。
正当性と時間検査を通ったペアだけを採用する。ケース $i$ の速度比 $g_i$ は
採用ペアの $t_{b}/t_{c}$ の中央値とし、\mbox{過半数未満なら無効}とする。
全評価ケースが有効な場合だけ
\begin{align*}
 \mathrm{valid}
   &= \mathrm{compiles}\wedge\bigwedge_i
      \big(\mathrm{valid}_i\wedge g_i>0\wedge\mathrm{finite}(g_i)\big),\\
 g &=
 \begin{cases}
 \exp\!\left(k^{-1}\sum_{i=1}^{k}\log g_i\right), & \mathrm{valid},\\
 0, & \mathrm{otherwise}
 \end{cases}
\end{align*}
と採点する。無効ケースを部分点として幾何平均へ混ぜない。$g$ は探索中の BFTS 順位付けと候補選択に
そのまま用いる。親との hash 差分がない no-op 子は、測定値と \texttt{valid} 判定を客観的記録として保持する一方、
探索適格性を示す \texttt{\_sterile} を付けて再展開、親の retire、最終候補選択から除外する。
探索深さ上限は 10 に固定し、root を含む 10 node を各 run に要求する。readable な
\texttt{node\_report.json} が 10 件に満たない run は、条件依存の計算量差として扱わず
\texttt{infrastructure\_error} とする。
探索終了後、最大 $g$ の有効な非 no-op 候補を別 seed（run seed $+10^6$）、各ケース 15 反復で再測定し、
この再測定値を run の主要アウトカムとする。再測定で無効なら $0$ とする。

\paragraph{測定防御と最適化フラグ}
採点ハーネスと baseline は node workspace 外に置き、manifest の sha256 と一致しない場合は
\texttt{infrastructure\_error} として run を停止する。評価には workspace の候補実装だけを取り込み、
各反復を新しい入力・プロセスで実行する。出力は NaN で初期化し、参照解との不一致、短い出力、異常終了、
および内部時間が非有限または非正である反復を fail-closed で棄却する。wall 下界との比は棄却に用いず、
診断値としてのみ記録する。1 プロセスの実行上限は 120 秒に固定し、
候補の超過は \texttt{candidate\_invalid}、凍結 baseline の超過は \texttt{infrastructure\_error} とする。
いずれか1ケースで候補が無効なら、全ケース必須の採点は既に無効なので残りのケースを実行しない。
課題契約は外部の既製カーネルへの処理委譲を禁じ、
リンク・include 用フラグも拒否する。

候補はコードとコンパイル最適化フラグを探索できるが、baseline は既定フラグに固定する。allowlist は最適化・
チューニング用フラグだけを許可し、外部リンク、include path、出力先、ツールチェーンの変更を拒否する。
実効・拒否フラグ、評価設定、ハーネスの sha256 を記録する。

\texttt{stencil} の band は予備実験の測定系で $2.633$\,\%、すなわち目標の $24.6$ 倍であった。
本稿の測定系では $0.149$\,\% である。同じ band ツール・同じ統計量（$12$ 試行の p95、最悪 1 点のみ
除外）で測っており、\emph{外れ値そのものが出ない}。12 試行は $0.99841$--$1.00111$ に収まり、
予備実験で見えていた $1.0272$ に相当する試行はない。

\paragraph*{何がぶれていたか}
機構は特定した。ぶれるのは掃引ではなく\emph{固定項}である。採点対象バイナリを直接反復すると測定は
\begin{equation}
t = 50.566 + 0.9299\,n_t \quad [\mathrm{ms}]
\label{eq:stencil_fit}
\end{equation}
に $0.03$\,\% で従い（$n_t=1,30,120,240$、各 20 プロセス）、掃引 1 回あたりの費用はこの全域で
再現する。一方、掃引が測定の $1.8$\,\% しかない $n_t=1$ では 100 プロセスの範囲が
$33.9$--$52.0$\,ms と $34$\,\% に広がる。固定項は、候補が自身の $268$\,MB を確保し first touch
する費用が計測窓の内側にあることそのものであり、3 課題で \texttt{stencil} だけが持つ構造である。

その固定項を跳ね上げるのは\emph{ページキャッシュの冷えである}。14 回連続採点（反復数 15、3 形状）
では、中央値を $5$\,\% 超えた反復 31 件が\emph{すべて最初の 2 採点に集中}し、3 回目以降は 0 件で
あった（最大 $2086$\,ms、通常 $214$\,ms）。参照解は 1 形状 1 反復あたり $134$\,MB の \texttt{npy}
として共有ファイルシステムに置かれ、合計 $5.1$\,GB を読み込むまで、親の入出力が子の計測窓を止める。
実際、採点前にこの $5.1$\,GB を読んでおく（$2$\,s）だけで最初の 2 採点の外れ値は消え、採点 1 が
$2.1$--$5.3$\,\%、採点 2 が $1.3$--$1.8$\,\% に収まる。

\emph{しかしこれは score をぶらさない}。冷えたキャッシュは候補と参照を同じ反復の中で同じだけ
遅らせるため、比では相殺する。band 測定の試行 1 は $105.0$\,s と他の $97$\,s より長いのに score は
$1.00111$ であり、$14$ 回連続採点でも外れ値を含んだまま速度比は $0.9986$--$1.0024$、band は
$0.218$\,\% であった。予備実験で band が $2.633$\,\% だったのは、credited 時間が壁時計由来で
あった測定系では、この共通項が相殺しなかったためと解釈できる。本稿の測定系は credited を
カーネル内部タイマとしており、相殺が成立する。

したがって band は 3 課題とも目標の $1.4$ 倍以内に入る。ただし\emph{達成したとは主張しない}
——\texttt{gemm} $1.06$ 倍、\texttt{spmm} $1.005$ 倍、\texttt{stencil} $1.40$ 倍はいずれも目標超で
ある。band 未満の兄弟選択は分解できていないものとして解析する。主要対比は 30 seed block の対応差に
対する検定であって単一兄弟の選択ではないため、この限界は主結論より探索経路の解釈に効く。
また目標値は\emph{予備実験の}兄弟間差から導いており、分母を替えた本条件で同じ差の分布になる保証は
ない。本条件での兄弟間差は再取得したデータで測り直す。

\paragraph{絶対性能と、到達可能な天井}
speedup は比であり、それ自体は「妥当なほど性能が出ているか」に答えない。そこで機械の
到達可能な演算天井を\emph{実測}し、参照の絶対性能をその比として報告する。

天井は SVE intrinsics（\texttt{svmla\_f64\_x}）で $N_a=16$ 本の独立な蓄積器を回して測る。
各スレッドは $I$ 回の反復で $N_a$ 個の FMA を発行し、1 FMA は 1 レーンあたり 2\,flop、
レーン数 $L$ は実行時に \texttt{svcntd()} で取得する（本機で $L=8$）。$T$ スレッド、経過 $t$ 秒として
\[
  \mathrm{GF/s} \;=\; \frac{2\,N_a\,L\,I\,T}{t}\times 10^{-9}
\]
とする。ループ内はレジスタのみで、メモリ参照も分岐もない。$I=2\times10^{7}$、$T=48$、
$t=0.097$\,s で $2534$\,GF/s を得た。測定コードは \texttt{workspace/tools/measure\_fma\_ceiling.c}
として成果物に含める。\textbf{clang もしくは \texttt{fcc -Nclang} でビルドする必要がある}
（gcc 8.5 には \texttt{arm\_sve.h} が無い）。

この値には 2 つの検査を課す。第 1 に \texttt{objdump} で SVE の FMA が実際に発行されていること。
ここで clang が出すのは \texttt{fmla} ではなく \texttt{fmad}（例: \texttt{fmad z23.d, p0/m,
z24.d, z25.d}）であり、\texttt{fmla} だけを検索すると 0 命令と誤判定する。第 2 に反復数 $I$ を
倍にしても GF/s が変わらないこと（$2532.7$ に対し $2536.2$、$0.14$\,\%）。前者は自動ベクトル化に
頼った版が SVE の FMA を 1 つも発行せず、後者はデッドコード除去が起きうるためである。実際、
この 2 つを課す前の 6 版はいずれも\emph{参照より低い}天井を報告しており、天井が下界を割るという
矛盾で誤りを検出できた。同様に周波数の測定コードも
\texttt{workspace/tools/measure\_clock.c} として含める。

動作周波数も実測する。本機には \texttt{perf} バイナリが無く、\texttt{cpu0} 配下に
\texttt{cpufreq} ディレクトリも無く、\texttt{/proc/cpuinfo} は BogoMIPS $200$ しか報告しない。
しかし PMU 自体は \texttt{/sys/bus/event\_source/devices/armv8\_pmuv3\_0} として公開され、
\texttt{perf\_event\_paranoid} は $0$ であるため、\texttt{perf\_event\_open(2)} を直接用いれば
非特権プロセスからサイクルを数えられる。1 コアを固定して busy 状態で計数すると $1.9984$\,GHz、
1 秒区間と 3 秒区間で $0.00$\,\% の一致であった。欠けていたのは計数機構ではなく計測ツールである。

\emph{ここで本稿は当初、計測手段が \texttt{perf\_event\_open} しかないと記述していた。これは
誤りであり、探し方が狭かったことによる。} \texttt{perf}／PAPI／likwid を module 名で探して
いずれも見つからなかったことから「プロファイラが無い」と結論していたが、PAPI は
\texttt{/usr/bin/papi\_avail} として導入されており、Fujitsu 純正の \texttt{fapp}／\texttt{fipp}
（および \texttt{fapppx}、\texttt{fipppx}、\texttt{hwpfctl}）は、本稿が候補に選択させている
\texttt{fcc} と\emph{同一のディレクトリ} \texttt{/opt/FJSVstclanga/cp-1.0.30.01/bin/} に存在する。
コンパイラをそこから起動しておきながら、同じ場所を見ていなかった。\texttt{fapp}
（Version 4.2.6）は GFLOPS とその理論ピーク比、メモリスループットとその理論ピーク比、
SIMD 命令率、SVE 演算率、IPC を名前付きで直接報告する。本稿が \texttt{objdump} と反復試行で
確認した「自動ベクトル化が SVE を発行していない」という事実は、\texttt{fapp} では
\texttt{SVE operation rate} の 1 行で得られる。

したがって理論ピークは 48 コア $\times$ $1.9984$\,GHz $\times$ 8 レーン $\times$ 2\,flop
$\times$ 2\,FMA パイプ $=3070$\,GF/s となる。実測天井 $2534$\,GF/s はその $82.6$\,\%、
すなわち 1 サイクルあたり $1.65$\,FMA であり、intrinsics で書いても 2\,FMA/cycle には届かない。
凍結参照は \texttt{gemm} の 3 形状で $382$／$388$／$368$\,GF/s、理論ピーク比 $12.4$／$12.6$／
$12.0$\,\%、実測天井比 $15.1$／$15.3$／$14.5$\,\% である。

参照は契約内（plain C、OpenMP、コンパイルフラグのみ）で書かれており、intrinsics も
アセンブリも用いない。したがってこの水準は参照の実装品質だけでなく\emph{契約そのものの上限}を
反映する。実測でも、自動ベクトル化に依存する限り SVE の FMA が発行されないことが 2 つの
コンパイラで確認されており（gcc は蓄積器を退避し、clang は SVE FMA を 0 命令）、候補が
到達しうる性能はコンパイラの自動ベクトル化能力に律速される。予備実験に対する
「生成コードの性能が低すぎる」という指摘は、探索の失敗としてではなく、まずこの構造として
説明される。

\paragraph{コンパイラの選択と固定}

に示す。効果は\emph{課題によって向きも大きさも変わる}。gcc に対し clang は \texttt{gemm} で差がなく
（1.0018 対 1.0048、ばらつきはいずれも 1\,\% 未満）、\texttt{spmm} では 3\,\% 遅い。

\texttt{stencil} では \texttt{clang} と \texttt{fcc} の測定が成立しなかった。3 回の値が
1.127／2.255／1.128 のように\emph{ちょうど 2 倍}に分かれ、幅は中央値の 100\,\% に達する。
同じノードで \texttt{gcc} は 0.4\,\%、また \texttt{gemm} と \texttt{spmm} では \texttt{clang} も
0.3--0.6\,\% に収まるため、ノード不調でもコンパイラ固有の不安定性でもない。\texttt{stencil} は

\emph{この解釈は方向としては正しかったが、制御していない要因があった。} 本機の Fujitsu 環境には
ラージページ確保方針を定める環境変数 \texttt{XOS\_MMM\_L\_PAGING\_POLICY} があり、静的領域・ヒープ・

選ぶ。\texttt{prepage} では\emph{並列 first touch ループが走る前に}ページが確保されるため、確保した
スレッドの CMG に全て載り、4 CMG 構成での NUMA 配置が成立しない。この変数を読むのは
\texttt{/opt/FJSVxos/mmm/lib64/libmpg.so.1} であり、\texttt{ldd} で確認すると\emph{Fujitsu
コンパイラでビルドしたバイナリにのみ}リンクされる。gcc ビルドでは誰も読まないので設定は無効である。

凍結参照を用いて実測すると、gcc ビルドは 3 設定いずれでも $n_t=1$ で約 $50$\,ms、$n_t=240$ で約
$273$\,ms と区別できないのに対し、\texttt{fcc -Nclang} ビルドは未設定で $n_t=240$ が $1375$\,ms、
\texttt{demand:demand:demand} を与えると $232$\,ms となり\emph{$5.9$ 倍}動く。固定項も $30.0$ から
$16.8$\,ms へ $44$\,\% 減る。しかも $232$\,ms は gcc ビルドの $273$\,ms を $15$\,\% 上回る。

影響は \texttt{stencil} に限られる。同じ設定で \texttt{fcc -Nclang} を候補として採点すると、
\texttt{gemm} は未設定 $1.1375$／$1.1481$ に対し \texttt{demand} で $1.1359$／$1.1365$、
\texttt{spmm} は $0.9746$／$0.9590$ に対し $0.9608$／$0.9521$ で、いずれも測定幅の内側である。
3 課題のうち候補が自身の $268$\,MB を確保し first touch を計測窓の内側で行うのは \texttt{stencil}
だけであり、他の 2 課題は問題データを外から受け取るのでラージページ確保方針が計測窓に入らない。

したがって表~\ref{tab:toolchain} の \texttt{gemm} と \texttt{spmm} の値は影響を受けない。
一方 \texttt{stencil} の測定不成立は、この変数を制御せずに測ったものであり、\emph{そのまま
信頼できない}。ただし観測された「ちょうど 2 倍」の分裂（$1.127$／$2.255$／$1.128$）は上記の
$5.9$ 倍とは比が異なり、同一の現象と断定はできない。\texttt{stencil} の非既定ツールチェーンは、
この変数を固定したうえで測り直す必要がある。候補は \texttt{candidate\_cc.txt} に \texttt{gcc}／\texttt{clang}／
\texttt{fcc} のいずれかを書く。候補プロセスは凍結 driver を含めて選択したコンパイラでビルドする
（オブジェクトを混ぜると OpenMP ランタイムが混在し、計測窓の外で生成する thread team が
カーネルと別ランタイムになる）。\emph{分母は動かさない}。参照は常に既定ツールチェーンでビルドし、
スコアは 1 つの固定された対象に対する比であり続ける。

\paragraph*{分母を 2 つ測る}
ただしこの分母だけでは、候補が非既定コンパイラを選んだ瞬間に\emph{コンパイラ境界を跨いだ比較}になる。
境界の片側だけに作用するものは、どちらのプログラムも変えずに比を動かす。前述の
\texttt{XOS\_MMM\_L\_PAGING\_POLICY} がその実例で、候補側（Fujitsu ビルド）だけを $5.9$ 倍動かし、
参照側（既定ツールチェーン）には触れない。反復ごとの対測定は\emph{時間変動する}条件を相殺するが
——冷えたページキャッシュが $214$\,ms を $2086$\,ms にしても比では消える——2 つのビルドの間の
非対称は相殺できない。

そこで同一の凍結ソースから\emph{2 つ目の分母}を作る。候補が選んだのと同じコンパイラ・同じフラグで
参照をビルドし、同じ反復の中で測る。得られる比では、片側だけに効く要因が両側に効いて消える。
2 つの比は置き換えではなく併記であり、\texttt{speedup} は従来どおり anchor（既定ツールチェーン）比で
あり続ける。

\begin{itemize}
\item \textbf{anchor 比}——コンパイラ選択を含む end-to-end の結果。本稿のスコアはこれである。
\item \textbf{matched 比}——コードの寄与のみ。同一コードなら $1$ になる。
\item 両者の商——ツールチェーンが買ったもの。
\end{itemize}

凍結参照を候補として採点して検証すると、matched 比は 3 課題 $\times$ 2 コンパイラで
$0.9914$--$1.0055$ に収まる（同一プログラムなので $1$ が正しい）。同じ実行の anchor 比は
$0.1735$--$1.0906$ と $6.3$ 倍に散らばり、\emph{その全部がツールチェーンとフラグの寄与であって、
コードの寄与ではない}。従来の測定はこの 2 つを分離していなかった。

\emph{この anchor 幅そのものが運用設定に依存する。}上記は
\texttt{XOS\_MMM\_L\_PAGING\_POLICY} を固定せずに測ったもので、同じ検証を
\texttt{demand:demand:demand} を与えて再実行すると matched は $0.9966$--$1.0047$ と変わらないのに、
anchor は $0.4702$--$1.1155$、すなわち $6.3$ 倍ではなく $2.37$ 倍になる。差は \texttt{fcc} の
\texttt{stencil} 一点に集中しており、$5.9$ 倍の変数が候補側だけを動かすという前述の観測と一致する。
本稿がこの 2 つを条件付きで併記するのは、条件を書かない比率が\emph{まさに本節の主張する誤り}
だからである。matched 比が両条件で $1$ の近傍に留まることが、分離が働いているという主張の本体であり、
anchor 幅はその対比として読むべき量である。検証は
\texttt{workspace/tools/check\_matched\_denominator.py} で再実行でき、分離が壊れると非零で終了する。
コストは候補が非既定コンパイラを選んだ反復でのみ実行が 2 回から 3 回に増える。

\paragraph*{測定条件そのものを記録し、照合する}
2 分母は 1 回の採点の\emph{内部}にある非対称を扱う。残るのは、採点と採点の\emph{間}で条件が
動く場合である。$5.9$ 倍の変数は運用設定であって実験設計ではないから、管理者が既定を変えれば、
月曜のシャードと金曜のシャードは別の条件で測られる。このとき何も失敗しない。全シャードが採点され、
全数値がもっともらしく、条件間の対比だけがエージェントと無関係な因子を吸収する。反復ごとの対測定は
1 回の採点の\emph{内側}で変動する条件を相殺するが、採点の\emph{間}で変わった条件は相殺しない。

そこでハーネスは、測定に関わる環境変数を採点のたびに記録し、その要約（\texttt{sha256}）を結果に
付す。捕捉は名前の列挙ではなく接頭辞の走査で行う。手書きの名前リストは\emph{誰かが思いついた変数}
しか記録しないためで、実際、本研究のスタディ manifest は 24 変数を名前で固定していたが
\texttt{XOS\_MMM\_L\_PAGING\_POLICY} はその中になかった——後から見つかった変数だからである。
逆にハーネス側は BLAS 系スレッド変数を捕捉しておらず、\emph{2 つの部分的な記録が併存し、どちらも
他方を含んでいなかった}。部分的な記録が 2 つあるのは 1 つより悪い。どちらも完全に見えるからである。
両者は単一の捕捉に統合した。値は記録するが\emph{制限はしない}。接頭辞の外にある変数は捕捉もされず、
無害と分かってもいない——記録はその旨を明示して保存する。

記録は照合しなければ意味を持たない。\texttt{workspace/tools/check\_environment\_drift.py} は
スタディ配下の全 digest を数え、複数あれば差分変数を提示して非零で終了する。判定はしない。
「その変数が測定に届くか」は事実ではなく判断だからである。記録が 1 件も無い場合も clean とは
報告しない——捕捉前の古いスタディと捕捉が壊れたスタディは、外からは区別できない。
実機検証では、$5.9$ 倍の変数のみを変えた 2 回の実採点が異なる digest を生み、検査器がその 1 変数を
特定した。

フラグ許可リストはベンダの名前空間 \texttt{-K*}／\texttt{-N*} を含む。これは形式的な追加ではない。
同一の fcc が、\texttt{gemm} では既定フラグで参照比 0.217、\texttt{-Nclang} を加えると 1.484 となり 6.8 倍動く。
すなわち \texttt{-Nclang} を拒否していた当初の許可リストは、fcc を\emph{測定によってではなく構成によって}
劣位に固定していた。さらにベンダ推奨の \texttt{-Kfast,openmp} は 0.245（反復数 5 での 1 回測定）と最も遅い部類であり、
「ベンダコンパイラをベンダ推奨フラグで使う」が最悪の選択となる。許可リストは形ではなく挙動で
危険を定義する。ハーネスの再定義（\texttt{-I}/\texttt{-D}/\texttt{-include}）、数値ライブラリのリンク
（\texttt{-l}/\texttt{-L}/\texttt{-Wl} および富士通 \texttt{-SSL2}/\texttt{-SCALAPACK}）、出力先の変更、
ツールチェーンの差し替え（\texttt{-B}/\texttt{-specs}/\texttt{-fplugin}）、反復間に状態を持ち越すもの
（\texttt{-fprofile-*}、\texttt{-Nfjprof}）、記号検査を無効化するもの（\texttt{lto}）、
OpenMP を無効化するもの（\texttt{-fno-openmp}、\texttt{-Knoopenmp}）を拒否する。

選択は許すが\emph{バージョンは固定する}。ハーネスは \texttt{cc} を PATH から解決するため、実際の
コンパイラは job の module 環境に依存し、本機ではこれが固定量ではない。ログインノードの \texttt{cc} は
GCC 11.5.0、計算ノードは GCC 8.5.0 であり、ベンダの entry module を load して初めて \texttt{fcc} が
可視になる。270 run を多数の job として時間をかけて投入する以上、一部の job だけ module 状態が異なれば
コンパイラは条件と交絡する。そこで各 node report に解決後のパスと \texttt{--version} を記録し、
さらに期待バージョンを環境変数で宣言した場合は不一致を\emph{インフラ障害}として停止する
（候補は合法な系統を要求しており、別物を供給したのは環境だからである）。候補が選ぶ変動は探索軸、
環境が押し付ける変動は交絡、という区別に基づく。ただしエージェントと評価器は同一 uid で動作し、
OS レベルの隔離はない。この防御は改変検出と結果検証であり、悪意ある候補に対する完全な containment ではない。

\paragraph{モデルと実行環境}
モデル endpoint は \texttt{cerebras/gpt-oss-120b} に固定し、OpenAI 互換 LiteLLM client で推論する。
temperature は 0.7、context 長は 32768 token、client retry は 1 回とし、run seed を API へ渡す。
top-$p$ と最大 completion token は明示指定せず provider default を用いた。immutable な重み・serving revision、
量子化、provider 側精度、endpoint が seed を deterministic に扱ったかは trace に残っていない。したがって API
seed は best-effort の要求であり、同一 completion の保証ではない。1 課題・1 条件・1 seed の run を
別々の Slurm array element として \texttt{sbatch} し、各 element の探索、ビルド、計測、採点を
\texttt{fx700} 1 ノード（\texttt{aarch64}、48 物理コア、
\texttt{OMP\_NUM\_THREADS}$=48$）内で完結させる。計測対象の OpenMP は
\texttt{OMP\_PROC\_BIND=spread}、\texttt{OMP\_PLACES=cores}、
\texttt{OMP\_DYNAMIC=FALSE} に固定する。

ページ配置に関わるカーネル設定は測定して記録する。本機は NUMA 4 ノード構成で、
\emph{NUMA 自動バランシングが有効}である（\texttt{numa\_balancing}$=1$、scan delay 1000\,ms、
scan period 1000--60000\,ms）。すなわちカーネルはアクセス局所性に応じて\emph{実行中に}ページを
移動させる。実際にこのノードの累積で $1.6\times10^{7}$ ページが移動している
（\texttt{/proc/vmstat} の \texttt{numa\_pages\_migrated}）。透過的巨大ページは無効
（\texttt{never}）であり、\texttt{zone\_reclaim\_mode}$=0$ である。

この設定は \texttt{stencil} の測定不安定性の候補説明であったが、\emph{実測により否定した}。
同一ビルドを 14 回採点し、各採点の前後で \texttt{numa\_pages\_migrated} の増分を読むと、
中央値付近の 12 回では 295 ページ移動しているのに対し、5\,\% 以上外れた 2 回は\emph{いずれも 0} で
あった（比 $0.00$）。移動が原因なら外れた採点でこそ多いはずで、観測は逆である。カウンタは
システム全体であり他ジョブの寄与を含むため、この向きの結果は雑音では説明できない。
なお本稿の他の測定でも、同一ビルドの外れ値は $338$\,ms と $486$\,ms のように複数の水準を取り、
単一の二状態遷移でもない。他ジョブとの同居による干渉も原因ではない。計算ノードは排他確保であり
（partition の \texttt{OverSubscribe=EXCLUSIVE}、各 job が 48 CPU 全数を確保）、1 ノードに 1 job しか
載らない。機構は最終的に、\emph{採点に使うバイナリそのものを反復実行する}ことで特定した（後述）。

まず本稿が検討し\emph{棄却した}説明を列挙しておく。査読者が同じ経路を辿り直す必要がないように
するためである。(i) 特定ノードの不調——同一ノードで \texttt{gcc}、および
\texttt{gemm}／\texttt{spmm} は $0.3$--$0.9$\,\% に収まる。(ii) 候補と参照の実行順序——候補先行
96 回の中央値 $1.1342$ に対し参照先行 72 回で $1.1386$。(iii) NUMA 自動バランシングによるページ移動
——上記のとおり比 $0.00$。(iv) 他ジョブとの干渉——ノードは排他確保である。(v) カーネル計算そのもの
——参照の確保・first touch・掃引だけを複製した独立プログラムを 20 プロセス走らせると全て
$230.6$--$236.8$\,ms に収まり、外れ値は一度も再現しない。掃引 1 回は $0.92$\,ms で 240 回とも
一定であり、最初の 10 回と最後の 10 回の比は $0.98$ で劣化もない。確保を計測窓の内側に移して
30 プロセスで測り直しても、確保は $0.037$--$0.042$\,ms（全体の $0.02$\,\%）で、
$229.5$--$238.1$\,ms に収まる。(vi) driver 側の入出力——後述の内部タイマがこれらを含まない。

\paragraph*{機構——計測窓内の確保と first touch}
複製ではなく採点対象そのものを測ることで機構が定まった。採点に使う \texttt{stencil\_main.c} と
参照カーネルをハーネスと同じフラグで構築し、実際の \texttt{problem.bin} に対して反復実行して、
ハーネスが採点に用いるのと同じ内部タイマ（\texttt{timing.bin}）を読む。この内部タイマは問題
ファイルの読込・出力の書出し・プロセス起動を\emph{含まない}。掃引回数を変えて各 20 プロセス測ると
式~\eqref{eq:stencil_fit} となり、ハーネスに記録された $50.57 + 0.9298\,n_t$ を有効数字 4 桁で再現する（$n_t=1,30,120,240$
の 4 点とも残差 $0.03$\,\% 以下）。すなわち固定項 $50.6$\,ms は入出力ではなく、\emph{計測窓の
内側}で参照が自身の $268$\,MB を確保し first touch する費用である。

分散はこの固定項に集中している。$n_t=1$ では掃引が測定の $1.8$\,\% にすぎないが、100 プロセスの
範囲は $33.9$--$52.0$\,ms（中央値 $51.2$、p95 $|x-\mathrm{med}|$ が $4.73$\,\%）と $34$\,\% に
広がる。対して $n_t=240$ では 60 プロセスが $270.7$--$279.0$\,ms（p95 $1.07$\,\%）に収まる。
掃引 1 回あたりの費用は $n_t=1$ から $240$ まで $0.03$\,\% で再現するのだから、ぶれているのは
掃引ではなく確保と first touch である。別の 20 プロセスの組では $n_t=30$ で $+38.3$\,ms、
$n_t=240$ で $+28.1$\,ms の遅い外れ値が出ており、超過は $n_t$ に比例せず\emph{ms でほぼ一定}で
ある。これも出所が固定項であることを示す。本稿が当初この説明を棄却した根拠は「超過が掃引回数に
対し $6.6$ 倍に増える」という\emph{採点水準}の観測であった。採点対象バイナリの直接掃引はその増大を
再現しない一方、ぶれる成分が確保と first touch であることは上のとおり直接示されるので、\emph{棄却は
撤回する}。

振幅を採点時の水準まで押し上げる条件も特定した——\emph{ページキャッシュの冷えである}。素のバイナリ、
$268$\,MB を常駐させた親からの起動、単発の採点呼出しの 3 条件を各 40 プロセス測っても最大の超過は
$+7.7$\,\% が 1 件にすぎず、いずれも再現しない。再現したのは\emph{3 形状を通しで 14 回連続採点した}
ときだけで、そこでは中央値を $5$\,\% 超えた反復 31 件が\emph{すべて最初の 2 採点に集中}し、3 回目
以降は 0 件であった（最大 $2086$\,ms、通常 $214$\,ms）。単一形状の反復では 370 プロセス測っても
一度も出ない。形状を切り替えて初めて、参照解 $5.1$\,GB 全体を読むことになるからである。

予測を立てて検証した：採点前にこの $5.1$\,GB を読んでおけば、最初の 2 採点の外れ値は消えるはずである。
$2$\,s の事前読み込みを足した 14 回連続採点では、採点 1 が $2.1$--$5.3$\,\%、採点 2 が
$1.3$--$1.8$\,\% に収まり、全 630 反復の範囲は $200.5$--$278.7$\,ms（事前読み込みなしでは
$200.5$--$2085.8$\,ms）となった。形状別の採点間ばらつきは $78.4$\,\%／$104.1$\,\% から
$0.42$\,\%／$0.33$\,\% へ下がる。

独立プログラム (v) が再現できなかった理由も同じ測定で説明がつく。そのプログラムの first touch は
$7.1$--$10.3$\,ms であったのに対し、採点経路では同じ処理が $50.6$\,ms かかる。採点用 driver は
\texttt{jacobi} を呼ぶ時点で既に \texttt{u0} と \texttt{u} の $268$\,MB を常駐させており、その上で
カーネルがさらに $268$\,MB を確保する。確保と first touch の費用はプロセスの既存常駐量に依存する
ため、常駐のない複製では再現しない。\emph{複製による反証は、複製しなかった条件の分だけ弱い}。

この結果は測定手順に反映した。配列の各要素は別ノードで走り、ページキャッシュはノード毎であるから、
事前読み込みを入れなければ\emph{全 run が冷えた状態で最初の採点を行う}。本稿の測定は各要素の冒頭で
当該課題の参照解を読み込む（実測 $2$--$19$\,s）。

したがって \texttt{stencil} だけが分解帯を満たさない理由は課題の構造にある。3 課題のうち
\texttt{stencil} だけが、候補自身の $268$\,MB の確保と first touch を計測窓の内側に置く。
$n_t=240$ という選択はこの固定項の\emph{比率}を $64.4$\,\%（$n_t=30$）から $18.5$\,\% へ
下げるが、固定項そのものは消えない。参照解を計算する制御器側の BLAS は 1 thread に制限し、
参照計算の worker が直後の候補計測と競合することを防ぐ。各 run 内の BFTS node は直列実行し、兄弟 node の
自己テストと評価を重ねない。array の並行数は投入時の空きノード数から決め、
条件数 9 の倍数に切り下げる（上限は空きノード数ではなく LLM endpoint の同時接続で決まる。
実際に用いた値は manifest に記録する）。低い array index が先に割り当てられる可能性に
備え、seed ごとに各条件が各 index 位置へ順に現れるよう配置を循環する。この循環により、\emph{並行して
走るどの集合も各条件を同数含む}——270 element の写像を全数検査し、各セルがちょうど 1 回現れること、
各 index 位置で条件が均衡すること、並行数 $9$／$18$／$27$ のいずれでも各波が均衡することを確認した。
並行数の上限はノード数ではなく LLM endpoint の同時接続で決まる：終端まで再試行を使い切った
rate limit は node 予算を 1 消費し、node 水準の再試行は存在しない。
候補と baseline は同一 allocation 内で対として測る。
job ID、array index、node 名、CPU 数を manifest に保存し、条件別 node 割当も報告する。

各 array element は自ノードのページキャッシュへ当該課題の参照解を先に読み込む（実測 $2$--$19$\,s）。
ページキャッシュはノード毎であり、これを行わないと\emph{全 run が冷えた状態で最初の採点を行う}
（前掲のとおり外れ値はそこに集中する）。
handoff 関連の外部環境変数は run 起動前に消去し、解決後の設定を記録する。

\paragraph{解析方法と実装凍結}
解析単位は 1 課題・1 seed・1 条件の BFTS run である。各課題・各条件を 30 seed で別個に反復し、全体で
$3\times3\times30=270$ run とする。主要対比は E--W と S--E の 2 つである。同一 seed は matched block とし、
model API に同じ seed を渡し、\texttt{stencil} の探索入力を固定する。\texttt{gemm} と \texttt{spmm} の探索時
generator は固定設定を使い、全課題の最終再測定は block 内で同じ $s+10^6$ を使う。seed は Slurm node を
決めず、3 方針の実現した軌跡も共有しない。

主要推定量は、無効な最終再測定を $0$ とした native speedup の seed 内算術平均差である。これは科学的失敗を含む
all-run outcome を保つためであり、0 で未定義となり失敗を条件付けで除外する log ratio を主解析にしなかった。
20,000 回の両側 sign-flip test は、効果 0 の帰無仮説下で matched difference の符号が対称・交換可能であることを
仮定する。5,000 回の seed-pair percentile bootstrap 95\%信頼区間も報告する。有効率は exact McNemar 検定と
対応リスク差、両条件で有効かつ正値の pair に限定した大きさは log-speedup 差と幾何平均比（GMR）として分けて報告する。
最終結果は全て有効だったが、GMR の「条件付き」という位置付けは事前の失敗規則による。
3 課題$\times$2 主要対比の permutation $p$ 値へ Holm 補正を適用する。探索中の親子改善率、
親破壊率、node 有効率は副次解析とし、親子率からは no-op 子を除外する。

科学的無効は \texttt{candidate\_invalid} または \texttt{measurement\_invalid} と記録し、$0$ を与える。

\texttt{infrastructure\_error} は測定値ではない。非零終了と出力欠損も含めて解析から除外し、条件別件数を報告する。
主要対比では、いずれか一方が infrastructure error の seed block を除き、除外 seed を明示する。

ここで「凍結」は外部 preregistration ではなく実装凍結を指す。3 条件のスキーマ、プロンプト、ツール、
モデル、$N=10$、ReAct 上限、seed 0--29、評価器、ハーネス、主要解析コードを 1 つの commit で固定し、
最初の confirmatory root をその後に開始する。予備実験ではこれを commit \texttt{cff60a7}
（2026-07-29 21:16:49 JST）で行い、最初の root を 21:19:18 JST に開始した。本稿の条件では、
評価器・ハーネス・解析コードのいずれも予備実験以降に変更している（分母、問題サイズ、計上時間、
thread team 位置、公開ツール、および sign-flip 区間の追加）ため、凍結 commit は本稿の条件で
最初の run を開始する時点のものとなる。
run ごとに実験 driver、解析・batch script、制御コード、
課題ハーネス、設定、git status、binary diff と各 hash を bundle 化した。先行 smoke run は実行可能性と
収集経路の確認だけに用い、効果推定にも seed 数の決定にも用いていない。投入時に共通 source fingerprint を固定し、
各 worker の開始前・終了後と集計時に照合した。不一致 run は解析対象外とした。

30 block は formal power calculation から決めておらず、事前に実用上最小の効果量または同等性幅も定めていない。
したがって、非有意差を同等性の証拠とは解釈しない
~\cite{lakens}。また、percentile bootstrap 区間と sign-flip 検定の見かけ上の不整合を解消するため、査読後の
事後解析として、同じ算術平均対応差に対する 500,000 回 sign-flip 検定を反転した 95\%区間を追加する。
凍結済みの $p$ 値と Holm の検定族は変更しない。さらに 30 個の対応差をすべて図示する。

\section{考察}

\begin{quote}\itshape
\textbf{結果に依存する記述は保留。}本節のうち、条件間比較の帰結を述べる部分は、破棄した予備実験の
測定値に基づいていた。本稿の条件によるデータ取得後に記述する。以下には、測定結果によらず本稿の
設計から定まる部分だけを残す。旧本文はコメントとして保存する。
\end{quote}

\paragraph{本実験が支持しうる範囲}
本設計は同等性幅を事前に定めていないため、条件差が有意でない場合も「Self-Report は既定値にすべきでない」
という一般的判断は導けない。逆に有意差が出た場合も、それは本稿の bundle・model・課題における効果であり、
handoff 一般の性質ではない。採用判断には、許容する token・金額・待ち時間・失敗率と、最小限必要な改善率を
事前に定める必要がある。本稿の設計から得られる手続き上の含意は、Evidence と Self-Report を別 channel に
保ち、後者を測定可能な介入として扱うことに限られる。

\paragraph{Self-Report は探索経路をどう変えたか}
最終スコアだけでは「Self-Report が効いたか」に答えられず、機序を伴わない主張になる。そこで予備実験の
corpus に対し、親の \texttt{next\_steps\_hints} を最適化カテゴリへ分類し、親子のソース差分を同じ
カテゴリへ分類し、提案カテゴリが子の差分に現れた場合を\emph{採用}と数えた。これは意図の読み取りでは
なく代理指標なので、\emph{提案を一切受け取っていない}他 2 条件で同じカテゴリが親子間で変化する割合、
すなわち基底率を併記する。基底率なしでは、最適化エージェントが元来行う操作を採用と誤読する。

表~\ref{tab:trajectory} に結果を示す。基底率を明確に上回るのは prefetch だけであり
（29.9\,\% 対 11.0\,\%／7.6\,\%）、ブロッキングとベクトル化は数ポイントの上乗せにとどまる。
スケジューリングは 335 回提案されながら採用率 15.8\,\% で、\emph{提案を受けていない} \armE{} の
基底率 23.0\,\% を下回る。first touch は 12.1\,\% で基底率 7.4\,\%／3.7\,\% を上回る。
したがって「Self-Report が探索方向を決める」という描像は、prefetch と first touch では
弱く支持され、スケジューリングでは支持されない。分類の粒度でしか言えない主張であることを強調する。

この表の first touch 行は当初 0\,\% と報告していた。分類器が \texttt{\#pragma omp parallel for} の
\emph{直後の 1 行}にのみ書込みを探しており、宣言や開始波括弧を挟む通常の書き方を全て見落として
いたためである。凍結参照自身の touch ループすら検出できておらず、それに気づいたのは同じ分類器を
参照実装に当てたときであった。窓を数行に広げて再解析した値が表の値である。
採用の有無で子スコアの対親変化を比べても中央値 $-0.72$\,\% 対 $-0.33$\,\% であり、採用側が
優位ではない。

この解析は予備実験の corpus に対するものであり、本稿の条件で再取得したデータに対して同じ手続きを
適用する。カテゴリ分類は正規表現による代理指標であって意図の読み取りではないため、
分類器と全対を成果物として公開する。

\paragraph{同定できない機序}
Evidence+Self-Report は意味内容と文脈長を同時に増やす。長さを揃えた placebo、shuffled Self-Report、
短縮 Self-Report がないため、有益な内容が注意分散で相殺された場合、提案品質が低い場合、Evidence の言い換えに
留まる場合を分離できない。事後監査は不適合提案と明示的不整合を数えるが、Self-Report 品質別の因果効果は推定しない。
探索方向の固定化も現在の指標では直接測定していない。したがって本稿の結果は、害または利益の機序ではなく、
明示的な bundled policy の end-to-end 比較として解釈する必要がある。

\section{限界}
\begin{enumerate}
  \item \emph{本稿の測定値自体が、環境記録より前に測られている。}第~\ref{sec:envrecord}
    節は、測定条件を記録せずに得た比率は運用設定の関数だと主張する。本稿が報告する band、
    実測天井、ツールチェーン表、$5.9$ 倍、$1.313$ 倍、$6.8$ 倍は、その記録機構を実装する前に
    測ったものであり、条件は digest ではなく作業記録から分かるにすぎない。既知の依存軸
    （コンパイラ、\texttt{-Nclang} の有無、ラージページ方針）については本文中に条件を明記したが、
    \emph{当時気づいていなかった変数について同じ保証はない}。以後の測定は digest を伴う。
  \item \armW{} でも親コード中のエージェント記述コメントはそのまま継承される（除去処理を置いていない）。
    したがって自然言語を除去した対照ではなく、明示的 report channel を除いた対照である。
  \item Self-Report の内容と入力長を分離していない。placebo、shuffled、短縮条件が必要である。
  \item 同一 uid で動く候補と評価器の間に syscall・filesystem containment がなく、静的検査と hash 検査だけでは
    悪意ある改変を完全には防げない。とくに計上時間は候補プロセス内の計測に依存し、これを外側から数値的に
    反証する機構は置いていない。
  \item 非有意差は効果ゼロの証明ではない。同等性幅を事前指定していない。
  \item \textbf{探索予算は node 数 10 に固定しており、予算を変えたときの感度を測っていない。}
    handoff の効果が「同じ予算でより良い解に届く」ものか「同じ解により少ない node で届く」ものかを
    本稿は区別できない。予算を $10$ から $20$ へ動かした比較は、1 条件あたり $30$ seed $\times$ 3 課題を
    再度要するため本稿の範囲外とした。実測では確定構成 1 run が \texttt{gemm} $4.8$ 分、
    \texttt{spmm} $19.5$ 分、\texttt{stencil} $51.4$ 分であり、予算を倍にした比較は
    $114$ node 時間の追加を意味する。
  \item \textbf{handoff は毎 node 常時発火する固定 policy であり、いつ渡すかを学習・選択する機構は
    置いていない。} 親が渡す内容をスキルとして蓄積・再利用する構成（過去 node から再利用可能な
    手順を抽出し、後続に提示する）は、本稿の 3 条件のいずれでもない。これは handoff 経路の
    \emph{内容}を変える設計であって\emph{有無}を変える設計ではないため、本稿の対照
    （\armW{}／\armE{}／\armS{}）では分離できない。
  \item 単一 model endpoint、sampling 設定、A64FX、3 kernel、10 node に限られる。
    $N=5,20$、expert-tuned baseline、実アプリケーションは新しい実験を要し、既存 trace から復元できない。
  \item immutable model revision、provider 精度、価格、latency、SpMM の最終 nnz、hardware counter を記録していない。
  \item 親子改善・破壊率は探索木内で依存し、探索方向の固定化を直接測る指標ではない。
  \item 性能測定には残留ノイズがあり、選択的または外部検証付き Self-Report も評価していない。
  \item \textbf{\texttt{stencil} の測定は絶対時間では大きく揺れる。} 個々の反復は
    $214$\,ms のところ $2086$\,ms まで飛ぶことがある。原因はページキャッシュの冷えであり、参照解
    $5.1$\,GB を読み終えるまで親の入出力が子の計測窓を止める（外れ値 31 件が\emph{すべて最初の
    2 採点に集中}し、事前に $5.1$\,GB を読む $2$\,s を足すだけで消える）。比では相殺するため score
    への影響は小さいが、\emph{絶対時間で報告する量には効く}。また各配列要素は別ノードで走り
    ページキャッシュはノード毎であるため、事前読み込みを入れない限り\emph{全 run が冷えた状態で
    最初の採点を行う}。本稿の測定はこの事前読み込みを行う。
  \item 反復数 15 の測定 band は 3 課題いずれも目標未達である（\texttt{gemm} $1.06$ 倍、
    \texttt{spmm} $1.005$ 倍、\texttt{stencil} $1.40$ 倍。表~\ref{tab:band}）。すなわち
    予備実験と同じ兄弟間差の分布を仮定する限り、探索は band 未満の差にある兄弟を分解できていない。
    主要対比は 30 seed block の対応差に対する検定であるためこの限界は主結論より探索経路の解釈に
    効くが、\emph{兄弟選択が偶然を含む}という前提で読む必要がある。
  \item ベンダコンパイラの可用性は job の module 環境に依存する。全 run で同一の module 状態を
    保たなければ、選択肢の有無が条件と交絡しうる。ハーネスは選択できなかった事実を記録して
    既定へ退避するため取り違えは起きないが、可用性そのものは投入側の責任である。
  \item Self-Report を評価後に生成する設計は、内省が評価値をそのまま繰り返せば \armS{} を
    \armE{} の言い換えに縮退させうる。prompt で測定値の再掲を禁じ、提案の採用率を無提案条件の
    基底率と対比して事後に測るが、言い換えの度合いを直接定量する指標は置いていない。
  \item 凍結参照は採点する問題サイズ向けに調整されており、他のサイズでの性能を代表しない。
    たとえば $2048$ 立方では蓄積ブロックが L1d 全体を占め、ブロッキングを外した実装に 4.6 倍劣る。
    本稿のスコアは採点ケースにおける比としてのみ解釈できる。
\end{enumerate}

\section{結論}
親コード継承下の handoff を \armW{}、\armE{}、\armS{} に分解し、3 HPC カーネル上で比較する実験設計を示した。
本稿の寄与は、この分解自体と、それを測定可能にするための評価系にある。すなわち、naive ではなく competent な
凍結参照を分母に置くこと、作業集合が最終段キャッシュに収まらない問題サイズを選ぶこと、計上時間を候補の
内部タイマに一本化し thread team 生成を計測窓の外に出すこと、そして偽装を wall 下界ではなく構造的制約で
防ぐことである。これらは予備実験で条件差と同程度以上の系統差を生じることが実測されたため、
比較可能性の前提条件として設計に組み込んだ。

評価系については、設計から演繹するのではなく\emph{実測して初めて分かった}要件が三つあった。第 1 に、
分母が competent であることは宣言ではなく検査を要する。当初の \texttt{gemm} 参照は 3 形状のうち 1 つで
教科書どおりの実装に 1.313 倍劣っており、エージェントが実際に生成した候補と突き合わせて初めて判明した。
第 2 に、採点する問題サイズは規模とキャッシュ収まりだけでは決まらない。$n=500$ は 48 スレッドに対し
10.4 行/スレッドであり、候補が書くであろう行並列実装がその形状では安定に測れない。形状を
$1500\times600\times1500$ に替えて偏りと分散が同時に解消した。第 3 に、ツールチェーンは探索空間の一部で
あって固定すべき定数ではない。同一の \texttt{fcc} が \texttt{-Nclang} の有無で 6.8 倍動き、その差は
フラグ許可リストの書き方だけで塞がれていた。いずれも「測定できているか」を測る手続きを置かなければ
気づけない種類の欠陥であり、本稿はその手続きを成果物として公開する。

条件間比較の結果は、本稿の条件で再取得したデータにより記述する。得られる結論は、Self-Report 品質のばらつき、
意味内容と文脈長の交絡、\armW{} に残る source comment channel を含む、明示的 always-on handoff policy の
比較として解釈されるべきものである。さらに次の実験では、長さを揃えた対照、事前の実用閾値、探索予算感度、
実アプリケーションを導入する必要がある。
